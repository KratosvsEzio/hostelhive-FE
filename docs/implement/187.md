### The ticket

A manager whose role lacks a stay-move permission gets a 403 (CanCan in the backend). Every stay move then shows the generic `hostBookings.moveNotAccepted` ("The server did not accept that. Please try again."). That invites a pointless retry, when the real cause is a missing permission.

**Fix direction:**
- map a 403 to a new translated key (e.g. `hostBookings.notAllowed`, "You don't have permission to do that.") in 18 locales, for every stay move;
- **optionally**, hide or disable moves the signed-in role can't perform, if the FE knows the role's permissions.

**Acceptance:**
- a 403 on any stay move shows the permission message, translated, once, where the host pressed;
- other refusals are unchanged;
- the parity spec covers the new key.

### What we already decided in this area

- **Refusal copy:** comes from `bookingMoveFailureKey`, which classifies by status and `bookingRefusal` (`serverMessages`), never `message` (#151/#159).
- **Where a refusal shows:** the dialog, the allocation, the panel footer, or one toast, decided at reply time (#173, #175). A 401 never toasts.
- **Plan refusals** (400 subscribe, 403 `crm_required`) are recorded by `hostAccessInterceptor`, so the console's plan lock reacts. #175's PM noted those currently read `moveNotAccepted` too.

### Synthesized understanding

Two parts:
1. **The message.** Map a **permission** 403 to a new key. Not every 403 is a permission refusal: the backend's `crm_required` (plan) is also a 403. Telling them apart needs either the response body (`serverMessages` or a code) or the host-access interceptor's classification.
2. **Optional: prevention.** `session.hasPermission(flag)` already gates nav entries and routes. Whether stay-move permissions (e.g. `mark_as_confirmed`) are among the flags the FE receives decides whether moves can be hidden up front.

## Root cause

Skipped — not a bug ticket (an improvement filed from #175's decision D2); the behaviour is the designed generic fallback for an unrecognised refusal.

## Plan

1. **Shared rule** (`core/host-access/host-access.ts`): export `isCrmRequired(err)` (403 with `code === 'crm_required'`, or the CRM message), and have `classifyHostAccess` use it, so the plan check exists once.
2. **`booking-move-failure.ts`:** a private classifier for a 403. A 403 with **no server code** (`code` is the `'unknown_error'` fallback) is a **permission** refusal; `crm_required` is a **plan** refusal; any other coded 403 (e.g. Rack::Attack `forbidden`) stays `moveNotAccepted`. Applied in `bookingMoveFailureKey`, `releaseFailureKey` and `crossPayInvoiceFailureKey`. No call-site changes (every stay move already opts out of the global toast and reports where the host pressed).
3. **i18n:** the new key(s) in 18 locales; `TRANSLATED_KEYS`.
4. **Specs:**
   - unit specs for the classifier and for `isCrmRequired`;
   - page specs for the panel, dialog, allocation, toast, release and the cross-pay invoice half;
   - the invoices-page booking half;
   - plan refusals pinned.
5. **KB:** the permission-403 rule, and why moves aren't hidden by permission.

### Principal Engineer report (condensed)

- **Every 403 on these routes** (backend `origin/main` 38ff508, code-proven). The checks run in this order: auth → `validate_hostel!` → active → `require_crm!` → CanCan.

  | Source | Body | `ApiError` | Reachable by |
  |---|---|---|---|
  | **CanCan** (`api_controller.rb:20-23`) | `{success:false, error:"You are not authorized to access this page."}` | `serverMessages` = that text; `code` `'unknown_error'` | every move except release (no CanCan on `booking_occupancies_controller`); also the cross-pay invoice half (`renter_bills_controller` has CanCan) |
  | **Not host or manager** (`host_controller.rb:14-16`, `render_403`) | `{errors:[same text]}` | the same | every move incl. release, only if the manager was removed mid-session |
  | **`crm_required`** (`host_controller.rb:21-25`) | with `code:"crm_required"` | `code` `crm_required` | every move, if CRM was lost mid-session |

- **The rule:** `403 && !isCrmRequired`. Exclude rather than match the English text. Don't change `bookingRefusal`, which handles 422s only and is shared with the guest screens.
- **The mapping:** one helper used in all three key functions. The Invoices-page booking half (`invoices.ts:1168`) reads right with the key as `{{reason}}`.
- **Plan refusals:** leave them unchanged and file a follow-up. The shell's `<hh-access-lock>` replaces the page, but toasts survive next to it.
- **Prevention: out of scope.**
  - The `host:Booking:*` flags have never been used by the FE.
  - Grants aren't verified in data.
  - The FE ignores the parent `manage` grant that the backend honours; admins aren't bypassed.
  - **Release must never be gated.**
- **Same shape elsewhere:** `isSubscriptionError` (`util/subscription-error.ts:22`) reads a CanCan 403 as a subscription problem. A manager whose create is refused gets the renewal prompt in the booking drawer, and list loads elsewhere misread it the same way.
- **Wording:** "You don't have permission to do that." (neutral), with 17 translations proposed.

### Product Manager report (condensed)

- **Roles:** Host and Manager are global, platform-wide roles, editable only by HostelHive admins. **An owner can't change what their manager may do.** A hostel has at most one manager. Owners can hit this too: new actions' permission rows exist only after a manual `rake permission:reload` plus an admin tick, unless the role holds "Manage Bookings".
- **Impact:**
  - pointless retries;
  - a typed reason looks lost;
  - the cross-pay invoice half says "Open the invoice and mark it paid there", but the Invoices page hides Mark paid without `host:RenterBill:mark_as_paid`.
- **Wording (house pattern: the plan lock's owner and staff variants):**
  - manager (no `host` role): "You don't have permission to do this. Ask the hostel owner.";
  - owner (`host` role): "Your account doesn't have permission to do this. Contact HostelHive support.";
  - plan: "This hostel's plan doesn't include CRM.";
  - fallback: one neutral key.
- **Classification:**
  - `crm_required` → plan key;
  - a 403 with **no** code → permission;
  - any other **coded** 403 (Rack::Attack `forbidden`) → `moveNotAccepted`;
  - everything else unchanged.
- **AC1–AC14:**
  - footer, toast, dialog (reason kept), allocation (picks kept), release, and the cross-pay invoice half (never "open the invoice");
  - the Invoices-page booking half;
  - plan → plan key; other coded 403 → generic; others unchanged;
  - once, no server text;
  - the session is untouched;
  - 18 locales;
  - the role variants.
- **Prevention:** show-and-explain only. Hiding risks hiding working buttons ("Manage" parent vs children; the decision `permission-children-are-the-grant.md` may be out of date against the current serializer). Release has no flag. Tooltips fail on touch.
- **Out of scope** (one sibling card): create/edit booking 403, opening a booking 403, the list 403, the Invoices page's own Mark paid, 400 offline.
- **Risks:**
  - never strip a permission from the live global Manager role to test; use a DevTools response override;
  - the support channel is unconfirmed.
- **Backend candidates** (code-proven, not live; the house rule says don't send yet):
  - the CanCan 403 should carry a machine code;
  - release has no `authorize`;
  - `permission:reload` is manual.
