### The ticket

`no-raw-error-message.spec.ts` › "has no message read beyond what the allowlist names" fails on `main` (`611f523`). It flags six reads added by `7c76573` (KratosvsEzio/hostelhive-FE#181, Trello #174 PR A):
- `features/host/subscription/billing-page.html`: allowlisted at **3**, holds **4** (`:21`, `:57`, `:170`, `:179`; PR A added `:57`).
- `billing-return-states.ts:365` and `billing-return.ts:167`: new in PR A, **not allowlisted**.

**Acceptance:**
- the guard passes on `main`;
- each allowlist entry says why its `.message` is safe;
- no entry is broader than the reads it covers.

### Where each read's text comes from (code-traced by `context-gatherer`, on `main`)

| Read | Source |
|---|---|
| `billing-page.html:21` `cardChangeError`, `:57` `savedCardError`, `:170` `view.changeError` | `PlanChangeError.message`, from `showChangeError` (`billing-page.ts:626-638`): `serverMessages?.[0]` only on a 422 or 404 (`stale`); a 403 gets our key |
| `billing-page.html:179` `view.error` | `CheckoutError.message`, from `showCheckoutError` (`:678-685`): the server's text unless forbidden |
| `billing-return-states.ts:365` `n.message` | `StartNote.message`, built only by `startFailureNote` (`billing-return.ts:162-168`) from `payErrorOutcome` |
| `billing-return.ts:167` `outcome.message` | `payErrorOutcome` (`safepay-checkout.ts:314-327`) reads only `{ status, serverMessages }`, and `serverMessages[0]` only on a 422; anything else gets `failed` / `forbidden` / `notFound` with no message |

**No read carries `ApiError.message` (the diagnostic) or a plain `Error`'s text.** All six are billing's own view-model fields carrying the server's refusal text, which billing shows verbatim by product rule:
- `area/host-billing-and-subscription.md:18`: "shows a 422's `errors[0]` verbatim";
- `96.md:1048` (R4);
- `174.md:148`, `:464`;
- `safepay-checkout.ts:294`.

### Principal Engineer report (condensed)

- **Trace confirmed:**
  - `serverMessages` comes only from `extractServerMessages(err.error)` (`error-interceptor.ts:120`, `api-error-message.ts:32-39`);
  - a network failure, a `TimeoutError`, a plain `Error` or `badCheckoutUrl()` has none, so every producer gives null or `failed`;
  - `payErrorOutcome` is pinned by `safepay-checkout.spec.ts:804-813`, including `new Error('boom')` → `failed`.
- **Types don't protect the field** (`string | null`), but the protection is structural. The writers (`billing-page.ts`, `safepay-checkout.ts`) are scanned with 0 allowed, so an `err.message` written there fails the guard. The known hole: a safe read swapped for an unsafe one in an allowlisted file keeps the count, which applies to every entry.
- **The existing `:49` comment is wrong for all three names it gives:** `view.message` (`payment-return-states.ts:436`) and `o.message` (`payment-step.ts:178`) also carry `payErrorOutcome`'s 422 text.
- **Replicated scan:** `main` gives 4/3, 1/0 and 1/0 offending, with nothing stale. With the fix, 0 offending and 0 stale, on `main` **and** on the `feat-174` uncommitted tree (reads at `:21`, `:57`, `:211`, `:220`). PR B's new `startSubscribe` error path also goes through `showCheckoutError`.
- **Risk 3 (pre-existing, out of scope):** `showCheckoutError` shows `serverMessages[0]` on **any** non-403 status, so a 5xx carrying an `error` body would be shown verbatim. The plan-change path deliberately shows our key on a 500 (`billing-page.spec.ts:1569-1592`). The FE behaviour is code-proven; whether the backend sends such a 5xx body is unverified. Fixing it touches `billing-page.ts`, which collides with `feat-174`.
- **Prevention options:**
  - **A (recommended):** make every focused run also include the source-reading specs, selected mechanically by the grep above (27 files, about 10% of the suite).
  - **B:** move the guard to a lint rule. Not now.
  - **C:** get CI running again, then make `main` a required check.
