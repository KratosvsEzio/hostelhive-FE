### #160 (as written)

> **Found while planning #128/#130. Reproduced in a real browser on 2026-10-11.**
>
> On `/en/search/lahore`, pan the map far away (I tested longitude ~97). The heading still reads "Lahore", robots is `index, follow`, and the canonical is `https://hostelhive.com/en/hostels/lahore`, over an area that isn't Lahore. `/en/search?place=Lahore&lat=…&lng=…` does the same, so the slug isn't the cause.
>
> Today this is by design: the heading names the search the visitor made, and a pan refines inside it (`locationName` / `canonicalPlace` in `search-map.ts`; the count text deliberately says "within map area"). It still leaves shared links carrying viewport keys (`ne_lat` …) indexable, pointing their signal at a landing page for unrelated content.
>
> **Decide:** Should a search URL carrying viewport keys be `noindex`, with no canonical? And/or should the heading stop naming the place once the map no longer frames it?
>
> **Acceptance**
> - [ ] A product decision is recorded. If it changes behaviour: a panned `/search/lahore?ne_lat=…` far from Lahore no longer claims Lahore in an indexable head.

### The user's decision (2026-10-18, at request time)

Both:
- **A.** A search URL carrying viewport keys is `noindex`, with no canonical.
- **B.** The heading stops naming the place once the map no longer frames it, and reads "This map area" instead. This reuses #172's keys `searchUi.mapArea`, `seo.mapAreaTitle` and `seo.mapAreaDescription`, already in all 18 locales.

### What the code shows

`SM` = `apps/web/src/app/features/public/search/search-map/search-map.ts`.

- **Viewport keys.** There are exactly four: `ne_lat`, `ne_lng`, `sw_lat`, `sw_lng` (`SM:115-118`, nulled together as `VIEWPORT_KEYS_NULLED` in `search-scope.ts:11-16`).
  - `lat`, `lng`, `zoom`, `place` and `city` are *place* keys, not viewport keys.
  - `urlBounds` (`SM:379-388`) needs all four, finite, with an area.
  - `mergeSearchParams` doesn't check them.
- **The map writes them itself.** On the first `moveend`/`resize` after load, and after every pan, `captureMapBounds` sets `mapBounds` and calls `syncBoundsToUrl` (`SM:1851-1906`), which writes the four keys with a same-path `replaceUrl`.
  - So **every** search URL in a browser carries viewport keys moments after it opens, including a pristine `/search/lahore`.
  - Every link copied from the address bar carries them.
  - During SSR nothing is written.
- **Heading.** `locationName` (`SM:282-294`) is the first of: `place`/`city`, the curated slug place, the unslugified slug, `null` when `areaChosen` (#172), or the home country.
  - `null` renders `searchUi.mapArea` ("This map area"; `search-map.html:198-208`).
  - `areaChosen` (`SM:441`) is consulted only when no place is named. It is set once from `urlBounds() !== null` and by `leftHomeCountry()` (drag start, user zoom), and it never resets.
- **Head effect** (`SM:939-995`, runs on the server too). It reads only `canonicalPlace`, `hasFilters`, `locationName` and `unbounded`, never the viewport. It has three branches:
  1. worldwide: noindex;
  2. `filtered || !place`: noindex, no `path`; with `name === null` it uses the map-area title and description;
  3. the indexable branch, with `path: '/hostels/<slug>'`.

  `Seo.apply({ noindex: true })` without a `path` already removes the canonical, the hreflang alternates and `og:url` (`core/seo.ts:154-177, 242-247`). **A extends branch 2's condition.**
- **The place's geometry is only a centre and a zoom.** There is no bounding box anywhere.
  - A curated slug resolves to `{name, lat, lng, zoom}`, with zoom 11 for a city and 13 for a campus (`landing/search-slug.ts:18-49`).
  - A picked place carries `lat`/`lng`/`zoom` in the URL, and Photon's extent is reduced to a zoom.
  - An uncurated slug has no coordinates at all.
  - Available: `mapBounds` (live), `center()` (`SM:343-355`) and `placeZoom()` (`SM:357-361`). `mapBounds` is null before the first settle and after `recenterTo`.
- **SSR.** `/search` and `/search/<slug>` render per request (`app.routes.server.ts:57`), so a shared link's noindex lands in the raw HTML.
  - The sitemap lists no search URLs (`sitemap-urls.ts:14-17, 63-77`).
  - robots.txt must keep allowing search, or crawlers can't read the noindex (`robots.ts:6-10`).
- **GA.** The place name feeds no event parameter. `search_performed.query` comes from the `city` param.
  - `page_view.page_title` is `document.title`, read once on arrival, so arrivals by a far-viewport link will record the map-area title.
  - A pan is not a page view.
  - GA is live in production, so annotate the deploy date.
- **Specs pinning today's behaviour.**
  - `search-map.spec.ts:1871-1877`: "keeps naming the place path after a pan (Trello #160 is a separate decision)". It calls `leftHomeCountry()` with no bounds.
  - e2e `search-everywhere-from-slug.spec.ts:24,68` and `search-new-place-and-landing-head.spec.ts:47` expect the place name after the first settle, or after Back onto a `replaceUrl`'d entry that frames the place. `landing-place-and-everywhere.spec.ts:34` expects it before any settle.
  - So "framed" must hold for the first settle, after `recenterTo`, and while bounds are null.
  - `head-canonical-and-structured-data.spec.ts` (`NOINDEX_PAGES`, `:13-18`) is where a raw-HTML viewport case belongs.
  - The e2e `dragMap` moves only 300 by 100 px (about 0.2° at zoom 11), which is not "far".

### Understanding

Today the heading and the head name the search the visitor *made*, whatever the map now shows. A shared link with a far viewport is indexable and canonicalised to the place's landing page, over unrelated content. After this change:
- **(A)** Any search URL that carries a viewport is a view, not a place page. It gets `noindex` with no canonical, server-rendered as well.
- **(B)** Once the map no longer frames the place, the heading and title read "This map area" instead of the place name.

A pristine place search (no viewport in the link, map on the place) stays exactly as it is: heading "Lahore", indexable, canonical to `/hostels/lahore`.

## Plan

### Merged plan

**A: links that carry a viewport are views.** An `arrivedWithViewport` signal holds `urlBounds() !== null`:
- It is set at construction.
- It is re-read on every `NavigationEnd` except the page's own same-path refinements, using `isSamePageRefinement(router.lastSuccessfulNavigation())` with the id check GA already uses.
- `isSamePageRefinement` moves unchanged from GA to `core/navigation/same-page-refinement.ts`, so that analytics and SEO share one definition.
- Back/Forward and language switches count as arrivals, so one URL gets one verdict. A crawler sees only the request URL, so the server verdict is the arrival verdict.
- "Carrying" means all four keys valid (`urlBounds`). Partial or garbage keys read as absent, and the map overwrites them on its first settle anyway.

**B: the heading follows the map.** A `placeFramed` computed delegates to a pure `framesPlace(view, centre, zoom)` in a new `search-framing.ts`. `locationName` returns the named place only while `placeFramed()`, otherwise `null`, which makes the h1 "This map area" and the map-area title.
- Null bounds (before the first settle, after `recenterTo`, a just-picked place) count as framed.
- A missing centre (uncurated typed text, `?place=` without coordinates) counts as always framed.
- The rule for whether the map frames the place:
  - Longitudes are unwrapped to the copy of the place nearest the view.
  - The place is **out** of frame when the view is wider than 32 tiles at the place's zoom. Only the longitude span counts, so tall phone or crawler viewports don't trip it.
  - Otherwise it is **in** frame when its centre is inside the view, or the view's centre is within 2 tiles of it.

**Head effect, new order:**
1. seed: return.
2. Not ready: return.
3. Unbounded: worldwide (unchanged).
4. `name === null`: map-area title and description, noindex, default image.
5. Curated, unfiltered place: `searchTitle{place}`, `placeSocialImage(slug)`, and `arrivedWithViewport ? { noindex: true } : { path: '/hostels/<slug>' }`.
6. Otherwise: today's filtered or uncurated branch.

No noindex branch passes a `path`, so there's no `og:url`, which Facebook would treat as canonical.

**Unchanged:**
- the Where inputs;
- the count copy;
- `syncBoundsToUrl`, `recenterTo` and `startSearch` behaviour;
- bare `/search` (#172);
- the sitemap and `robots.txt` behaviour;
- no new i18n keys;
- no backend change.

**Tests:**
- unit: `search-framing.spec.ts` as a table, a moved `same-page-refinement.spec.ts`, and new cases in `search-map.spec.ts` for heading, server head and browser head (including **the map's own landed write on a pristine page stays indexable**, mutation-checked against a live `urlBounds()` predicate);
- e2e: a framing viewport link in `NOINDEX_PAGES`, a far-link raw-HTML case, and a new `search-viewport-head.spec.ts` (live head after the settle, a zoom-out to map area and back, a reload).

### Principal Engineer report

**Brief premises corrected.**
- **`mapBounds` on the server.** It is seeded from `urlBounds()` on both platforms (`SM:391`), so a viewport link is judged for B against its own box on the server, and a far link server-renders "This map area".
- **Line numbers.** `robots.ts:10-13` and `sitemap-urls.ts:22-24`.
- **The other session's spec** is now **open PR #175** (`test/157-161-search-trigger-e2e`, opened 16:14Z). It also touches `search-bar.ts` and KB line 67.
- **Angular is 21.2.9**, not 22. `Router.currentNavigation` and `lastSuccessfulNavigation` are `Signal<Navigation | null>`.

**Current behaviour.**
- **The map writes the viewport itself.**
  - `captureMapBounds` runs on `moveend`/`resize` only (`SM:1244-1251`); nothing listens to `move`, so nothing updates mid-drag.
  - It calls `syncBoundsToUrl`, a same-path `replaceUrl` merge of the four keys.
  - The first settle always happens: a zero-offset `panBy` fires `moveend` in Leaflet 1.9.4, and `whenSized` has a 2 s fallback.
- **The page's own writes are already recognisable.** GA's `isSamePageRefinement` (`google-analytics.service.ts:95-113`) treats an imperative, same-path `replaceUrl` with a previous navigation as a refinement, id-checked per `NavigationEnd` (`:250-264`).
  - On the search route, the only such writes are SearchMap's own: `searchEverywhere` in place, `recenterTo`, `syncBoundsToUrl` and `stripCorrections` (`SM:1716, 1800, 1904, 1924`), checked by grep.
  - `LocaleStore.switchTo` pushes under the new prefix, and SearchMap is reused because `:locale` is a route param.
- **No JSON-LD.** SearchMap writes none, so `Seo.clearUnclaimed` is unaffected.

**Design question A.**
- **a1, the live URL: rejected.** The map's first-settle write would flip every search page's DOM to `noindex, nofollow`. That includes Googlebot's evergreen-Chromium render, where the map builds: Leaflet is DOM and CSS tiles with no WebGL, and `whenSized` falls back after 2 s. Pristine place searches would be de-indexed.
- **a2, the arrival URL, is robust.** The server's request URL is the arrival URL, so a1, a2 and a3 agree there. In a JS render of a pristine URL, the camera opens on the place.
- **The hook.** `NavigationEnd` plus `lastSuccessfulNavigation()` with `isSamePageRefinement`. Rejected alternatives:
  - `searchTrigger`, which is set only by `startSearch` and the header bar;
  - `navigationId`, which says nothing about who wrote an entry;
  - a lazy `computed` over `currentNavigation()`, which would be null by the time it is read.
- **Back/Forward** onto a `replaceUrl`'d entry counts as arriving with a viewport (trigger `popstate`). That gives one verdict per URL, the same rule GA uses, and no `history.state` tagging to keep in sync.
- **Language switch** is re-read. Filter Apply, sort and amenity changes are pushes carrying the keys, so they become noindex, which is harmless.
- **Partial or garbage keys** are not a viewport: the map opens on the place, so the canonical to the landing page is truthful.

**Design question B (b3).** The rule is the `framesPlace` pseudo-code in the merged plan, built on `tile = 360 / 2^z` degrees of longitude per 256 px tile:
- **City (z 11):** the view's centre may be about 0.35° (~33 km) off, and the view up to 5.6° (~530 km) wide.
- **Campus (z 13):** about 0.088° (~8 km), and up to 1.4°.
- **Outcomes:**
  - the ticket's longitude-97 pan and a whole-Pakistan view are not framed;
  - zooming into DHA with the city centre off-screen is framed;
  - the first settle is framed even on a 3844 px pane (2.6° against a 5.6° cap);
  - a desktop box restored on a phone is framed;
  - `recenterTo`, a just-picked place and Back onto a framing entry are framed;
  - one 616 px `dragMap` drag is framed, and two drags are not.

Why each part of the rule:
- **Unwrapped longitudes.** Leaflet's `getBounds` doesn't wrap, and there's no `maxBounds`/`worldCopyJump`.
- **The longitude span only.** It covers tall phones and possibly tall crawler viewports (the latter unverified).
- **b1 (centre in view only): rejected.** It keeps "Lahore" over a country view and drops it inside a neighbourhood.
- **The `areaChosen` fallback when no centre is known: rejected.** It never resets, so a reused page inherits a previous pan, and these searches never framed their place anyway.
- **No hysteresis or debounce.** `mapBounds` changes only on a settle, and `placeFramed` is a boolean computed.

**Edge cases.**
- **Filters plus a viewport:** noindex as today; the heading follows B.
- **Everywhere:** branch 1 first, unchanged.
- **University slugs:** always noindex; B changes only their heading and title (z 13).
- **A picked place:** uses its coordinates and zoom. With no zoom, only the centre-in-view test applies.
- **Language switch:** A is re-read; B carries the live box.
- **A reused page changing place.** The head effect (`SM:939`) runs before the recentre effect (`SM:1108`) in the same tick, so it may write the map-area title once before it is corrected in the same change detection. GA reads a macrotask later. Before `ready()`, a pick can read "This map area" until the first settle; that is a pre-existing race with the camera, not fixed here.
- **Hydration.** `fitBounds` makes the view at least as wide as the URL box, so the heading can flip right at the threshold. This is rare with the 32-tile cap.
- **Mobile.** The h1 is hidden below 950 px.

**Technical requirements.**
1. A server render with `urlBounds() !== null` is noindex, with no canonical, `og:url` or hreflang, even when the box frames the place.
2. Pristine `/search/<curated>` stays indexable with the `/hostels/<slug>` canonical **after** the map's own writes.
3. A same-page refinement `NavigationEnd` never changes `arrivedWithViewport`; every other one re-reads it.
4. The indexable branch omits `noindex` (specs assert `toBeUndefined()`), and every noindex branch omits `path`.
5. `framesPlace` treats null bounds and a missing centre as framed, wraps longitudes, caps on the longitude span only, and keeps the first settle framed for panes from 390 to 3844 px.
6. Bare `/search` keeps #172's semantics exactly.
7. The place inputs are unchanged.

### Product Manager report

**Intent.** A pristine `/en/search/lahore` is a place page: indexable, with its canonical at `/hostels/lahore`. Once the map leaves Lahore, it is a view of some other area, yet the heading, the title and an indexable canonical all still say "Lahore". Under the user's decision, a link that carries a viewport is a view (A), and the heading and title follow what the map shows (B). `/hostels/<slug>` stays the one indexable place page. #128's acceptance wording was already "don't claim Lahore unless the map is on Lahore".

**Affected.**
- **Desktop searchers.** The h1 is hidden below 950 px, so phones see only the tab title change.
- **Shared-link recipients.** Every copied link carries keys. The preview title follows B, and the image changes too unless the place's picture is kept.
- **Crawlers.** Keyed URLs get `noindex, nofollow` in the server HTML, while pristine place searches must stay exactly as they are, both raw and rendered.
- **GA (live).** Arrivals on far-viewport links, refreshes after a far pan, and Back/Forward onto such entries record the map-area `page_title`. No event parameter changes. Annotate the deploy date.

**Q-A, what counts as "a URL carrying viewport keys".**
- *Live URL*: **rejected**. It de-indexes every place search in a crawler that runs JavaScript, because the rendered page says noindex while the raw HTML says index.
- *Arrival only*: close, but after a far pan the title says "map area" while the canonical still says `/hostels/lahore`.
- **Recommended: arrival, or the map no longer frames the place.**
  - *Arrival* means the URL of the navigation that brought the visitor to this entry: SSR, load, refresh, push, or Back/Forward. The map's own `replaceUrl` writes (`syncBoundsToUrl`, `recenterTo`, `stripCorrections`, in-place "everywhere") are not arrivals.
  - *A viewport* means one the search can use (the `urlBounds` test: all four keys, finite, with an area). A partial or garbage viewport reads as absent.

**Q-B, "no longer frames".**
- **Recommended: the place's centre is off the map, or the view is zoomed far out.** "Far out" means the view's shorter side is more than 4 times the place's own frame. The frame is the span a 1024 px map shows at the place's zoom.
  - Lahore at zoom 11: the frame is about 0.7°, so the threshold is about 2.8° (roughly 265 km). At 1400 by 900, zoom 9 still says Lahore and zoom 8 or wider says map area.
  - A campus (zoom 13): the threshold is about 66 km, so a whole-Lahore view still names the campus.
- **Viewport source.** The URL's box for a keyed arrival; the live camera once the visitor moves the map (drag, touch, wheel, the +/- buttons, **keyboard arrows**). Leaflet arrow-key pans fire no `dragstart`, and `shared-map.ts:53-58` leaves the keyboard on.
- **Camera moves the app makes never count**: the initial open, the fit to results, a recentre, framing the country. Null bounds count as framed.
- **Which place.** The place the heading names (query `place`/`city` wins over the slug). Its position comes from the URL's `lat`/`lng`/`zoom`, otherwise the curated table. With no zoom, use the first settled frame.
- **No known position** (an uncurated slug or `?place=` with no coordinates): follow #161's rule. The name holds until the visitor moves the map, or straight away when the link carried a viewport. These pages are already noindex. "Unchanged" is the acceptable minimal alternative.
- **The Where inputs** (mobile field, header bar) keep "Lahore": they are inputs showing the search made, and changing them would fight #130.
- **Panning back** restores "Lahore". **Filters**: B still applies. It is judged on settle only, never mid-drag.

**Predicate as landed.** `framesPlace(view, centre, zoom)`:
- A null view or null centre returns true.
- The place's longitude is unwrapped to the copy nearest the view's centre.
- `inView` is the containment test. With no zoom, it returns `inView`.
- With a zoom, `tile = 360 / 2^zoom`, and it returns false if the view is wider than `CAP_TILES * tile` (longitude only).

### A keyboard pan is undone by the next results (finding; not this ticket)

Seen live in 5e on `/en/search/lahore`, live LAN API, with real results. Arrow keys pan the map, but the camera then snaps back to the results.

- **Mechanism (from the code):** `userInteracted` is set only on `dragstart` and on a user `zoomend` (`search-map.ts`, around `:1328-1340`). A Leaflet keyboard pan fires neither. Its `moveend` refetches, and the new results refit the camera because the visitor is still "not interacted".
- **Effect:** keyboard users can't browse the map away from a place, which is an accessibility gap.
- **Status:** it predates this change. #160's heading followed the camera correctly throughout.
- **Candidate follow-up card:** count a keyboard pan (`keydown` on the map container, or any `movestart` not marked programmatic) as interaction.

### The map doesn't always write its viewport on load (correction to the plan's premise)

The plan, the PE report and the first KB draft said every search URL carries the viewport keys a moment after it opens. That's true when something moves the camera: a fit to results (seen live in 5e) or a visitor's move. It's **not** true for a place search whose camera never moves, such as the e2e lane's empty stubbed results (e2e round 1).

The design doesn't depend on this either way: the arrival basis keeps a pristine page indexable whether or not the write happens. The KB wording is softened to match (see QA results and Summary).
