### #176 (as written)

> The search reads its filters through `mergeSearchParams`. That reader already ignores an unknown `gender`, and since #171 a `sort` the type can't use. `roomType` and `propertyType` are not checked at all.
> - `?roomType=bogus`: `SearchMap.query()` sends it raw as `f[room_types.occupancy_type]` (`listings-api.ts` ~359), a term no document has, so the list narrows to zero.
> - `?propertyType=bogus`: goes raw into `f[property_type]` (~348), with the same narrowing.
>
> In both cases the Filters badge counts the value (`activeFilterCount`), and the dropdowns show a placeholder, because the value isn't one of their options. Same shape as the `gender` fix (`b0cdc98`) and #171.
>
> **Acceptance:**
> - An unknown `roomType` reads as the default (shared) and an unknown `propertyType` as absent. The request doesn't send them, the badge doesn't count them, and the dropdowns show their neutral state.
> - Valid values (`OCCUPANCY_TYPES`, `PROPERTY_TYPES` slugs) are unchanged.
> - The check lives in `mergeSearchParams` (one reader), using `isOccupancyType` and a `PROPERTY_TYPES` check. Decide in planning whether to also strip them from the URL, as #171 does for `sort`.

### What the code shows

- **Readers of `roomType`/`propertyType` in search, all through `params()`:**
  - `SearchMap.query()` (`search-map.ts:432-434`; `roomType` defaults to `shared`);
  - SEO `hasFilters` (`:292`; a present key means `noindex`);
  - `SearchFilters.roomType`/`propertyType` (`search-filters.ts:128-144`), which feed `hasActiveFilters`, `activeFilterCount`, the room-type dropdown value and the modal seed.
  - **The header bar never reads them** (unlike `sort`).
- **`ListingsApi.list`:** sends `propertyType` raw as `f[property_type]` (`:348`) and `roomType` raw as `f[room_types.occupancy_type]` (`:359`). The price-band field already validates with `isOccupancyType`, falling back to shared (`:375`).
- **Vocabulary:**
  - `OCCUPANCY_TYPES = ['private','shared']` with `isOccupancyType` (`util/occupancy-type.ts`). The same file notes the backend publishes `private_room`, and that `isPrivateOccupancy` accepts both spellings.
  - `PROPERTY_TYPES` (`util/models/listing.ts:137`): apartment, room, building, house. It has no guard function.

### Understanding

Mirror #171: `mergeSearchParams` reads an unknown `roomType` as absent (so it reads as shared, the default) and an unknown `propertyType` as absent. The request, the badge, the room-type pill and the modal then agree. Valid values are unchanged.

**Open for planning:**
- whether to strip them from the URL too (the header bar can't revive them, unlike `sort`);
- what to do with `private_room`;
- the SEO effect: a URL whose only "filter" was a bogus `roomType` stops being `noindex`.

### What we already decided in this area

- **`mergeSearchParams` is the one place filter values are corrected on the way in** (gender `b0cdc98`, sort #171 D5).
- **The URL is the state; #171 strips a discarded `sort`** because the header bar would revive it (#171 D1). The same reasoning may not apply here.
- **Room type has no "Any":** an absent `roomType` means `shared` (`room-type-replaces-capacity.md`).
- **The seed must stay synchronous** (KB trap); seeds never carry `roomType`/`propertyType` today (`place-landing.ts:130-147`). To be verified.

## Plan

### Merged plan

**One engineer, a strict chain** (~30 lines):
1. **`apps/web/src/app/util/property-type.ts` (new):** `isPropertyType(value)` over the `PROPERTY_TYPES` slugs (array `includes`, case-sensitive). It follows `util/occupancy-type.ts`/`accommodation-type.ts`.
2. **`search-params.ts` · `mergeSearchParams`:** a small table `CHECKED_ALONE` (`roomType` → `isOccupancyType`, `propertyType` → `isPropertyType`) for keys whose values are judged on their own.
   - A query or seed value that fails the check is read as absent in `get`/`has`/`getAll`/`keys`.
   - Every value of a repeated key is checked.
   - The identity return is kept when nothing needs correcting.
   - The reader returns *absent*, not `'shared'`. Each consumer already defaults absent to shared, and returning `'shared'` would set `hasFilters` (`noindex`).
   - Doc comment updated.
3. **No change** to `search-map.ts`, `search-filters.ts`, the modal, `search-bar.ts` or `listings-api.ts`. They read `params()`, and after the fix the modal seeds shared/empty, so Apply writes `null` for both.
4. **SEO falls out of the fix.** `/en/search/lahore?roomType=bogus` reads as the unfiltered page, so it is indexable with canonical `/hostels/lahore` (correct: the content is exactly the landing list). `/en/search?roomType=bogus` (no place) stays `noindex`.
5. **KB (ships in this PR):**
   - area `:10`, `:26`, `:42` (replace "not yet (#176)"), `:54` (reuse `isPropertyType`), `:72` (widen the seed trap to `roomType`/`propertyType`);
