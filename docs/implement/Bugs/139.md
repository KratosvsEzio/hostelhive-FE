### The ticket

Privacy policy, terms of service and service policy (`features/public/legal/`) are written only in English but served at all 18 language URLs (`/ur/privacy-policy`, …). The sitemap lists every language version, and since #129 each one canonicalises to itself with a full hreflang set — telling search engines a translated version exists in every language, which `core/i18n/locales.ts` itself calls misleading.

**User decision (2026-10-18):** canonicalise every language version of the legal pages to `/en/…`, emit no hreflang for them, and list only the English URL in the sitemap. Do not translate.

**Acceptance:** the head, the sitemap and the page language agree for every legal URL.

## Root cause

**Status:** code-proven (the e2e `head-route-defaults.spec.ts:103-121` actively asserts the current behaviour); confirmed in Phase 5 when specs fail before and pass after.

| | |
|---|---|
| **Symptom** | `/ur/privacy-policy` (and the other 17 languages × 3 pages) each canonicalise to themselves with 19 hreflang links, and the sitemap lists all 18 — claiming a translation that does not exist. |
| **Cause** | `core/seo.ts:146` builds the canonical from the active language unconditionally; `:166` emits `localeAlternates` for every indexable page; `features/public/landing/sitemap-urls.ts:69-71,:89` repeat it; `core/route-head.ts:170-171` sends the legal pages down that path. "Translated" is modelled per language (`core/i18n/locales.ts:46-57`, `INDEXED_LOCALE_CODES`), never per page. |
| **Why it escaped** | Every test asserted what the code did: `app.routes.spec.ts:277-287` and the e2e above both expect `/ur/<legal>`. A route-walk spec would catch it only once a route can say which language its content is in. |
| **Same shape elsewhere?** | `/credits` (English throughout, `credits.html:5-8`, 18 sitemap entries); blog articles (16 × 18, self-canonical + hreflang, body `lang="en"`); and a separate defect: article JSON-LD `url`/`mainEntityOfPage` and the breadcrumb are unprefixed (`blog-article.ts:218`). |

## Plan

**Merged plan:**
1. New `core/i18n/content-locale.ts`: `SINGLE_LANGUAGE_PAGES` (`/privacy-policy`, `/terms-of-service`, `/service-policy` → `en`), `pageLocales(basePath)`, `pageAlternates(basePath)`.
2. `SeoConfig.contentLocale`: canonical and `og:url` use `withLocale(contentLocale, path)`; no hreflang (`setAlternates(null)`); `og:locale` from the content locale (`en_PK`); `noindex` still wins; an invalid code falls back to the active language.
3. `route-head.ts` reads `contentLocale` from route data (deepest wins) and passes it to `Seo`; `app.routes.ts` sets `contentLocale: 'en'` on the three legal routes; `app.routes.spec.ts` checks the flagged routes equal `SINGLE_LANGUAGE_PAGES`.
4. Sitemap lists only `/en/<legal>`, with no `xhtml:link` for those entries; every other page unchanged.
5. Legal templates: the content (h1, effective date, prose) wrapped in `lang="en" dir="ltr"` (blog precedent `blog-article.html:182`); `<html lang/dir>` keeps following the URL (the chrome is translated); the hard-coded "Back to home" becomes `common.backToHome` (exists in all 18 locales), outside the wrapper.
6. Links keep the visitor's prefix (`LocaleLink`); no `noindex`, no robots change; URLs keep answering 200 at their own address.
7. e2e `head-route-defaults.spec.ts`: legal pages leave the self-canonical loop for their own loop (en, ur, ar) plus a language-switch case.
8. KB in the same PR: new decision `decisions/ssr-seo-and-prerender/single-language-pages-canonicalise-to-their-language.md`; edits to `area/i18n.md` and `area/ssr-seo-and-prerender.md` away from #160's hunks.
