### The ticket

The become-a-host wizard keeps its progress in localStorage under `hh:onboarding:draft`: the server `draftId`, the hostel's details and the host's email, phone and secondary phone. The draft records no owner and nothing removes it. On a shared browser the next person to open the wizard resumes the previous host's draft.

**Reproduced (2026-10-11, unit test on the card):** A fills the wizard and saves (server draft 42), signs out; B signs in and opens the wizard → B sees A's name, email, phone and `draftId` 42; B's save sends `update(42, …)`.

**Fix (card):** store the draft with its owner and only resume it for the same owner; delete it on sign-out and once the hostel is submitted.

**Acceptance (card):**
- The reproduction test passes: B opens the wizard empty, with no `draftId`, and B's save does not target A's draft.
- A signing back in on that browser before anyone else still resumes their own draft (if kept), or the decision to drop it is recorded.
- After a successful submission the draft key is gone.

### What the code shows

- **Writers/readers of the key:** `onboarding-wizard.ts` — `persistDraft()` (effect on every change + direct calls), `restoreDraft()` in the constructor (line ~967), `deviceDraftPresent`; `onboarding-payment.ts` — `readDraft()` (name, city, gender, rooms count, `draftId`, `selectedProductIds`) and `persistSelectedProducts()` (read-modify-write of the same object). Nothing calls `removeItem`.
- **Route:** `host/listings/new` and `host/listings/new/payment` are `authGuard`ed ("any signed-in user may start it"). The wizard injects `AuthService` but not `SessionStore`.
- **"Submitted"** is unclear in the code: "Save and continue" creates/updates the hostel and goes to the payment page, which still needs the draft; `OnboardingPayment.pay()` is a fake `setTimeout` (KB trap).
- **Precedent (#105):** owner-scoped cache `{ owner, items }` read synchronously, ignored for any other user, removed on sign-out via an effect on `SessionStore.user()?.id`.

### What we already decided in this area

- Favourites: key per-user caches on the session **user id**, not the user object or the authenticated flag; read the cache synchronously; the store owns the session hook rather than `AuthService` / `SessionStore.clear()` (decision record above).
- Onboarding: the wizard is open to any signed-in user (route comment, `app.routes.ts`).

## Plan

### Merged plan

1. **New root service `OnboardingDraftStore`** (`apps/web/src/app/services/onboarding-draft-store.ts`) — the only owner of `hh:onboarding:draft`. Flat shape `{ owner, ...fields }`. `read()` returns the draft only when `owner` equals `SessionStore.user()?.id`, and deletes a foreign / ownerless / unreadable one on read. `write(fields)` stamps the owner and does nothing when signed out. `patch(fields)` edits only a draft the current user owns and never creates one. `clear()`. An effect on `computed(() => session.user()?.id ?? null)` deletes the key when the id is null (D1). Field-by-field validation stays in the components.
2. **Eager creation** — a browser-only `provideAppInitializer` in `app.config.ts` that injects the store, so deletion on sign-out works from pages where neither onboarding component exists (the gap `FavoritesStore` / `HostPropertyStore` have as lazy stores).
3. **Wizard** (`onboarding-wizard.ts`) — drop its `DRAFT_KEY`; `restoreDraft` / `persistDraft` go through the store (restore keeps its existing field checks).
4. **Payment page** (`onboarding-payment.ts`) — drop its `DRAFT_KEY`; `readDraft` → `store.read()`; `persistSelectedProducts` → `store.patch`; `pay()` success → `store.clear()` (in-memory signals keep the confirmation rendering).
5. **Specs** — store spec (new); wizard spec: `render()` seats a session user, owner on the seeded draft, plus the two-user reproduction and legacy-draft tests; payment spec (new).

Untouched: `core/auth/*` (no hooks in `AuthService` / `SessionStore.clear()`, as #105 decided), `HostPropertyStore` (#115), `docs/RISKS.md` (#117 covers RISKS edits).

### Principal Engineer report

Agrees with the #105 shape and adds eager creation — "that is what makes deletion on sign-out work". Flat `{ owner, ...fields }` so the payment page's patch keeps the owner and existing `saved.name` assertions survive. Both read-check (hard guarantee) and the effect (privacy: contact details off disk at sign-out). Delete at `pay()` success — not at "Save and continue", which would break the payment page and "Back to form". The wizard must skip `persistDraft` when signed out, or a mounted wizard would write the key straight back after a 401. Existing specs that break once an owner is required: `onboarding-wizard.spec.ts` `:143` "keeps the local draft restorable after an incomplete exit", `:397` "does not resurrect a persisted capacity…", `:501` "keeps the choice in the local draft" — fix by seating a user in `render()` and adding `owner` to the seed. `HostListingsData.draft` is always `null` (`host-shell-api.ts:164`) — no server-side draft listing. **Serious unknown:** whether the backend rejects `PUT /hostels/:id` from a non-owner (API down) — recommends a backend ticket. Recommends one engineer, sequential (~250 lines).

### Staff Engineer report (frontend)

- **New `services/onboarding-draft-store.ts`** — sole owner of `hh:onboarding:draft`, flat `{ owner, ...fields }`. `read()` returns the current user's fields (without `owner`); a foreign / ownerless / non-object / unparseable draft returns null and is removed; signed out returns null and removes nothing. `write()` stamps the owner, no-op without a user. `patch()` merges into an owned draft only, never creates. `clear()`. Not added to the `@services` barrel (not owned) — imported as `@services/onboarding-draft-store`.
- **`app.config.ts`** — browser-only `provideAppInitializer` creating the store, placed right after the restore-session initializer.
- **`onboarding-wizard.ts`** — `DRAFT_KEY` removed; `restoreDraft()` reads via the store, existing field checks kept; `persistDraft()` builds the draft with `satisfies OnboardingDraft` and calls `store.write`. `deviceDraftPresent` reads only signals — unaffected.
- **`onboarding-payment.ts`** — `DRAFT_KEY` removed; `readDraft()` via `store.read()`; `persistSelectedProducts()` → `store.patch(...)` (the old code created a draft from `{}`); `pay()` calls `store.clear()` right after `paid.set(true)`.
- **`onboarding-wizard.spec.ts`** — `render()` seats a real `SessionStore` user `u1` (role `seeker`; `student` is not a valid `Role`); the one seeded draft gets `owner: 'u1'`. The other two tests the PE named pass unchanged (they save through the wizard). No assertion changed, no test added.

**Deviation (accepted):** the effect keys on a `holder` computed — the user id when signed in; `undefined` when a token exists but no user yet (restore or sign-in in progress) → draft left alone; `null` only when both user and token are gone (`SessionStore.clear()`: sign-out, 401) → draft removed. A user change removes a draft the new user doesn't own. Reason: `restoreSession()`'s token-only path holds startup up to 8 s with the user null; keying on the id alone would wipe a host's own unsaved draft on reload, and unlike favourites there is no server copy to reload.
