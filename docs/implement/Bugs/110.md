### The cards (summarised; full text on Trello)

- **#110** — On `/hostels/lahore/girls`, picking another place in the mobile place field (`onPlaceSelected()`, `search-map.ts:1459`) merges `place/lat/lng/zoom` into the query. The page's `gender=girls` and its heading "Girls hostels in Lahore" stay, so Karachi girls' hostels appear under a Lahore heading. Since #106, the Karachi coordinates also follow the visitor to sibling pages. **AC:** picking Karachi on `/en/hostels/lahore/girls` leaves the Lahore page and the heading matches the results; `/search` is unchanged.
- **#109** — On a landing page, "Search everywhere" (`searchEverywhere()`, `search-map.ts:1513`) writes `place/lat/lng` as `null`, but the page's preset refills them (`mergeSearchParams`). `center()` therefore still feeds `near` (`search-map.ts:397`), and the search stays local. **AC:** on `/en/hostels/lahore/punjab-university`, "Search everywhere" gives results not limited to the campus or city; `/search` is unchanged.
- **#111** — The header bar reads the raw `?gender=` (`search-bar.ts:198`) and writes it back (`:286`), so `/search?gender=bogus` re-submits `bogus`. **AC:** the header shows no accommodation, and searching writes no `gender`. Fix: `isAccommodationType`.

### What we already decided in this area

- A page's preset can be overridden by the query but never removed by it. Where that matters, change **page** rather than writing the query (#106, D2/D9; KB area "Traps").
- The header bar's `search()` always leaves for `/search/<slug>` via `searchRouteFor` (`search-bar.ts:277`). The hero does the same (`hero-clouds.ts:147`). This is the precedent for "a new place = a search page".
- One reader of filter state, with a bad `gender` ignored (#106, D11, `search-params.ts`).
- Landing pages own the head; any filtered or uncurated search is `noindex` (decision `curated-landing-pages-own-place-intent.md`).
- The mobile place field only renders below 950 px (`search-map.html:3`); the desktop header bar is hidden on `/hostels/*` (`site-header.ts`). So on desktop landing pages there is no place field at all.

### Understanding

Both landing-page bugs are #106's root cause in two more functions: a query merge cannot remove what the page's path supplies. The fix direction follows #106 and the header-bar precedent: from a landing page, a new place, or "everywhere", leaves for `/search`, carrying the visitor's filters. #111 is a one-line validation with the guard #106 added.

## Plan

### Merged plan

1. **The rule:** on a landing page (`seed()` set), any action that changes **geography** leaves for `/search`, in one localised (`localiseCommands`) **push** navigation. It never merges into the landing URL. `/search` keeps today's behaviour.
2. **Place pick:** → `searchRouteFor(label)`. Query: the new `place/lat/lng/zoom`; the visitor's filters (merge); the page's own gender as an explicit `gender=`; **viewport keys nulled** (otherwise the new SearchMap restores the Lahore box); `city` null.
3. **Near me:** same, to `/search` with `place='My location'`.
4. **Search everywhere:** → `/search` with place keys and viewport nulled, carried filters, and a marker the new SearchMap reads at construction to start unbounded (PE: `everywhere=1`; D-pending).
5. **#111:** `search-bar.ts:198` validates with `isAccommodationType`; `search()` then writes `gender: null`, scrubbing the bad value.
6. **D1:** fix #106's e2e stub (CORS).
7. **Tests:**
   - unit for a small shared helper (`search-scope.ts`: `VIEWPORT_KEYS_NULLED`, `seededFilters`);
   - component specs for `SearchMap` (seed + navigate spy) and `SearchBar`;
   - an e2e for #110 / #109 / Near me.

### Principal Engineer report (key content)

- **Current behaviour:**
  - `mergeSearchParams` refills seeded keys;
  - the landing H1 comes from the path;
  - `query()` sends `near` when there is no box;
  - **bare `/search` frames the visitor's country (`setup()` `:1047-1056`)**;
  - viewport keys are read once at construction and beat `center`;
  - landing → `/search` re-creates `SearchMap`, so the `unbounded` signal is lost.
- **Approach:** `leaveLanding(commands, geo)` in SearchMap, with `onPlaceSelected` / `locateMe` / `searchEverywhere` branching on `seed()`. For "everywhere": a new query key `everywhere=1`. It is read at construction (`unbounded` initial value, unless coordinates are present); `setup()` skips country framing; `syncBoundsToUrl` mirrors it (one write site, so no racing navigations); `recenterTo` resets `unbounded`; `searchEverywhere` on `/search` also writes it; `SearchBar.search()` clears it.
- **Rejected:** navigation `state` (not shareable or SSR-visible); a world `ne/sw` box (Leaflet clamps, wrong heading); staying on the landing page with the geography dropped (worldwide results under "Hostels in Lahore"); bare `/search` (country framing).
- **Curated routing (`/hostels/karachi`):** feasible but not recommended. `PlaceResult` has no type, and label matching is a heuristic.
- **Test levels:**
  - component with `seed` + navigate spy (#110, Near me);
  - component construction from `?everywhere=1` (#109 request);
  - `search-bar.spec` (#111);
  - e2e for the H1 and requests.
- **Decomposition:** T0 shared helper → T1 SearchMap → T2 SearchBar → T3 e2e. Small enough for one engineer.

### Product Manager report (key content)

- **Impact:** wider than the cards. A place pick on a **city** or **campus** page also shows Karachi under a Lahore heading; only the gender page also forces the type.
- **Carry-over table:**
  - kept: effective gender (the page's own or a valid override), price, a non-default `roomType`, `propertyType`, amenities, sort (minus `price-*` when the type is "Any");
  - replaced or removed: place/lat/lng/zoom; removed: `city`, viewport keys, invalid gender, retired params.
- **ACs 1–25:**

- **Open questions:** curated routing (→ D2, decided: `/search`); carry gender (yes); "everywhere" across refresh (not required); push (yes); own-city pick (leave anyway); legacy `?place=` links (out of scope).

**What changed:**
- **One rule:** on a landing page, any action that changes geography leaves for `/search` in one localised push navigation (`SearchMap.leaveLanding`), never merging into the landing URL.
  - Place pick → `/search/<slug>`.
  - Near me → `/search?place=My location`.
  - Search everywhere → `/search?everywhere=1`.
  - Each carries the visitor's filters and the page's own gender (D3), drops the old viewport and place keys, and drops retired params. `/search` keeps its existing behaviour.
- **"Everywhere" is now a URL state, `?everywhere=1` (D4):**
  - it is read once when the page loads, and a bare `/search` would otherwise frame the visitor's own country;
  - country framing is skipped, and a slug-only centre is ignored for the request;
  - it is mirrored on map settle and cleared by a pan, a new place or a header-bar search.
- **#111:** the header bar ignores an invalid `?gender=` (`isAccommodationType`) and so scrubs it on the next search.
- **The #106 e2e stub (D1)** now gets a real empty list.

### #106's e2e stub returns a CORS error, not an empty list
The app sends `withCredentials: true` (`core/interceptors/auth-interceptor.ts:20-22`), and a credentialed request cannot use `access-control-allow-origin: *`. The stub in `apps/web-e2e/src/landing-gender-filter.spec.ts` therefore puts the page in its error state ("We couldn't load listings"). Its tests still assert the right requests and URLs, so they are valid, but the page under test is not the one a visitor sees. Echoing the origin with `access-control-allow-credentials: true` gives a real empty list (verified in this run's reproduction). Fix it alongside this run's e2e spec.

### Code-reading confirmation (Phase 1)
`searchEverywhere()` sets `unbounded` and nulls `lat/lng/place/city` with `replaceUrl: true`. `query()` (`search-map.ts:380-411`) then has `mb = null`, but `center()` still reads the seeded `lat/lng`, so `near` is set and the request stays local. Not yet reproduced in a browser.
