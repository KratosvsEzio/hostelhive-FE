### The ticket

Every other stay move opts out of the global error toast and shows a translated key where the host pressed. Confirm doesn't:
- `HostBookingsApi.confirm` takes no options;
- `onAct` uses `send`'s default `onError` (`viewError`).

So a refused Confirm:
- **from the panel:** shows **twice** (the global toast with the server's 4xx wording, plus the footer key);
- **from the row menu or a calendar card:** shows **only** the global toast with the server's untranslated English;
- `bookings.spec.ts:1011` asserts this on purpose.

**Fix direction:**
- give `confirm` `opts` with `requestContextArgs`, and pass `{ suppressErrorToast: true }`;
- show the key in the panel footer when the panel shows this booking, else a page error toast (translated);
- keep #173's moved-on handling working for confirm;
- rewrite the spec.

**Acceptance:**
- **From the panel:** one message (footer), no global toast.
- **From the row menu or calendar:** one translated error toast; never server text.
- **Network failure:** still "can't reach the server".
- **Success:** unchanged.
- **Specs:** panel, row menu and network.

### What we already decided in this area

- **Global toast with a per-request opt-out** (`SUPPRESS_ERROR_TOAST` via `ApiRequestOptions` and `requestContextArgs`): every call whose error shows inline opts out.
- **Refusal copy:** comes from `bookingMoveFailureKey`, never server text (#151/#159).
- **#173:** `send` hands "done / moved on" refusals to `onMovedOn`, whose `closeMovedOn` already shows the panel footer or an error toast with no panel. Confirm can't realistically get those kinds today.

### Synthesized understanding

This is a two-part change:
1. **The API option:** add `opts` to `confirm`, matching `checkOut`'s shape.
2. **Where confirm's failure is shown:**
   - in the footer when the panel shows this booking;
   - as a translated error toast otherwise.

Watch the case of a row-menu confirm while the panel shows a **different** booking. Today, `send`'s default `onError` would put the key in that other booking's footer.

   - `onAct` confirm passes `{ suppressErrorToast: true }`.

   - **`onMovedOn`:**
     - host moved → toast for `'toast'`;

### Principal Engineer report (condensed)

**Current wiring:**
- Only confirm uses `send`'s default `onError`.
- All three entry points (panel `(act)`, row menu, calendar card `confirmRequested`) go through `onAct`.
- The panel is a modal (`fixed inset-0`), so "another booking's panel" arises only while a confirm is **in flight**: View details, calendar Details and URL changes aren't busy-guarded. Today the key then lands in the wrong footer (code-proven).

**The naive fix is unsafe.** Making confirm quiet with a footer-or-toast `onError`, and nothing else, would double-toast with #173's `closeMovedOn`. It would also let `keepMoveOpen` write a footer nobody sees, and let `dropMissing` close a panel the host opened mid-flight. Approach D removes all of these and leaves #173's specs untouched.

**Other points:**
- **Network:** `common.cannotReachTheServer`. 404 → `bookingNotFound`. 5xx or unrecognised → `moveNotAccepted`.
- **401** still signs out.
- **Plan refusals** are still recorded by `hostAccessInterceptor`.
- **The guard spec is safe.**
- **Limitation:** "no global toast" can only be asserted through the opts (page spec plus the API `HttpContext` spec).

### Product Manager report (condensed)

**What the server can realistically refuse.** Read from the backend at `origin/main` 38ff508; code-proven, not live:
- network status 0 (most likely);
- 5xx after commit;
- 403 (CanCan, a manager role without `mark_as_confirmed`), realistic in multi-staff hostels;
- 400 subscribe or 403 `crm_required`;
- 422 legacy validation;
- 404 (near zero).

`mark_as_confirmed` has **no stage guard**, so no moved-on kinds today.

**AC1–AC12:**
- **Panel:** footer only, no toast, no re-read.
- **Row menu or calendar:** one error toast, title the key, no body.
- **Another booking opened mid-flight:** its footer stays untouched, plus one toast. If **A's own** panel was opened, A's footer and no toast.
- **Network:** `cannotReachTheServer` both ways.
- **404:** the footer or a toast; the panel stays open.
- **Success** unchanged.
- **No server text**, for 422, 403, 400, 404, 5xx and URL errors.
- **#173 on confirm with no panel:** exactly one toast (moved-on, or `moveNotAccepted` for D5).
- **Busy** holds.
- **401 and plan-refusal plumbing** unchanged.
- **The `:1011` rewrite.**

**Risks:**
- a 403 or 400 becomes the generic "server did not accept that" (less informative; matches the other moves);
- a pinned toast becomes a 6 s one;
- a 5xx may have landed (a retry is harmless).
