### The ticket

`POST /api/user/confirm_invitation` (BE PR #39) now answers:
- **404** "This confirmation link is invalid or has already been used";
- **403** "This confirmation link has expired".

The BE asks the FE to show both. The page currently maps every non-zero failure to one key, `authConfirmInvitation.linkIsInvalidOrExpired`, and that must not show raw server text.

**Fix (card):**
- 403 → new `linkHasExpired`;
- 404 → new `linkIsInvalidOrUsed`;
- any other non-zero status → the existing generic key;
- 0 → `cannotReachTheServer`;
- the new keys go into all 18 locales.

The card also suggests, optionally, pointing an expired link to sign-in or support, since no resend-confirmation endpoint exists.

**Acceptance:**
- 404 and 403 each show their own translated message;
- other failures are unchanged;
- no raw server text;
- spec rows for 403 and 404.

### What we already decided in this area

- **#124 (PR #100):** the page never shows raw server text; failures map to translated `messageKey`s.
- **#125 (PR #106):**
  - the page asks before replacing a signed-in session;
  - `AccountConfirmedNotSignedIn` separates "link failed" from "confirmed, but signing in did not finish";
  - focus moves to the heading.
- **#148 (PR #114):**
  - a pure classifier (`reset-failure.ts`) is the pattern;
  - an unrecognised failure fails closed to the generic message;
  - a bare Rails `"Not Found"` 404 is `unknown`, not a used link.

### Backend facts (BE `main` @ 75ac7ca, read only)

- `sessions_controller.rb:30-39` `confirm_invitation`:
  - 404 when no `email_confirmation` invite matches the token, or it has no user;
  - 403 when `expired_at < now`;
  - otherwise it activates the user, issues the JWT and destroys the invite.

  The 403 is the only 403 this action sends **itself**. `issue_token` (`:100-110`) can also send a 403, "User have no roles and not allowed to sign in", but only *after* the account is activated and the invite destroyed.
- `user_invite.rb:106`: invites expire after **1 year** by default, so an expired confirmation link is rare.
- `config/routes.rb:54-63`: there is **no resend-confirmation endpoint**.
- `sign_in` (`:7-12`) does not check `is_active`. `google_login` (`:41-66`) sets `is_active = true` on an existing account with the same email, so Google sign-in recovers an unconfirmed Gmail account. Whether an unconfirmed account can use the app after a password sign-in is **unverified** (`user.rb:29-31` destroys the user's `jwt_auths` on commit while it is inactive).

### Understanding

Classify the confirmation failure the same way #148 does. A 404 with a backend message means "invalid or already used". A 403 whose text says "expired" means "expired". Everything else non-zero keeps the existing generic key, and 0 keeps "can't reach the server". Translate into 18 locales, add specs, never echo server text. The open product question is what an expired link should offer, given there is no resend endpoint.

**Assumption (stated, not blocking):** a 403 from `issue_token`'s "no roles" path is classed as generic, not expired. It would arrive after the account was confirmed, but the FE cannot tell that from the HTTP reply, so the generic message ("invalid, has expired or has already been used") is the safe fallback.

## Root cause

**Status: hypothesised.** It is confirmed by reading the code; the new 404 and 403-expired page rows must fail on HEAD in 5a to confirm it by test.

| **Same shape elsewhere?** | `forgot-password.ts:58-64` and `lead-wall.ts:300-308` also split only "0 vs the rest", and they echo `err.message`; already filed as #150 and #151. `reset-failure.ts` (#148) is the fixed twin. ## Plan

The PE and PM agree on the classification, the copy direction and the expired-link options. They differ only on per-case headings (see 2d).

1. **Shared helpers.** New `core/errors/api-error-text.ts` holds `errorStatus`, `serverText` (joined and normalised) and `isBareNotFound`, with its own spec. `reset-failure.ts` moves onto it with no behaviour change; its spec (C1–C15) must stay green with no edits.
2. **Classifier.** New pure `features/auth/confirm-invitation/confirm-failure.ts`: `classifyConfirmFailure(err)` → `linkInvalidOrUsed` | `linkExpired` | `network` | `unknown`. The rules:
   - no numeric status → `unknown`;
   - `0` → `network`;
   - `404` with text that is neither empty nor a bare "Not Found" → `linkInvalidOrUsed`;
   - `403`, exact expired text or the keyword "expired" → `linkExpired`;
   - everything else → `unknown`, which maps to the existing generic key `linkIsInvalidOrExpired`;
   - `err.message` is never read.
3. **Page.**
   - `handleError` checks `instanceof AccountConfirmedNotSignedIn` **first**, then maps the kind to a key through an exhaustive `Record`.
   - After a server or network failure, focus moves to the error heading (`tabindex="-1"`, `aria-describedby` → the message), but not for a missing token; this mirrors #148.
   - Today the `role="status"` region empties on error, so a screen-reader user hears nothing.
4. **Copy.** New keys in all 18 locales, plus a parity spec like #148's. No link lifetime appears in any copy.
5. **Out of scope:**
   - any change to `AuthService`, the interceptor or `extractServerMessages`;
   - #150 and #151;
   - focus in the confirmed phase (follow-up note);
   - anything in the backend.

### Principal Engineer report (condensed)

- Traced every path that sends the token: first load, Log out and continue (`signOutThenConfirmInvitation`), and the session-ended effect. All three end in `handleError`.
- `AuthApi.confirmInvitation` already passes `inlineErrors()`.
- `AccountConfirmedNotSignedIn` can wrap a 403 or 404 from `/users/current`, so it must stay the first branch; a spec row pins this.
- The "no roles" 403 reaches the FE with no `serverMessages` (a nested array), so it is classed `unknown`.
- **Expired-link actions:**
  - there is no resend endpoint;
  - Google sign-in activates an existing account (code-proven, but too much of a quirk to advertise);
  - password sign-in appears to work for an unconfirmed account, but `user.rb:29-31` wipes its `jwt_auths` on any user commit.
  
  So support is the honest way out. It recommends Contact us for expired only, and keeping `confirmationFailed` as the heading.
- Proposed T0 (helpers + `reset-failure` refactor) → T1 (classifier) → T2 (page + en.json), with T3 (17 locales + parity spec) parallel; it advised giving the code track to one engineer.

### Product Manager report (condensed)

- **Most 404s come from people who already confirmed.** The invite is deleted on success, so a re-click or a second device hits a dead link. The copy should say "If you've already confirmed your account, just log in", with Go to log in as the main action.
- **"Sign up again" is a dead end:** email uniqueness rejects it with "is already registered".
- **Acceptance criteria** AC1–AC15 cover the 404 (exact, reworded and bare), the expired 403, other 403s, other statuses, network, missing token, the three asking-phase paths, `AccountConfirmedNotSignedIn`, the 18 locales, and no lifetime in copy.
- **Recommendations:**
  - per-case headings: "This link no longer works" and "This link has expired", the same wording as #148;
  - a neutral `ti-link-off` badge on the 404 card;
  - expired → Go to log in + Contact us + Back to home;
  - no Contact us on the 404 card.
- **Risk:** "Log out and continue" can sign out a user who has already confirmed. The FE cannot detect that ahead of time, so the 404 copy is what softens it.

## Summary

The confirmation link page (`/confirm_invitation`, `features/auth/confirm-invitation`) now tells the backend's two link failures apart:

| Server answer | The page shows |
|---|---|
| 404 with the backend's message | **"This link no longer works"**, neutral link badge, "If you've already confirmed your account, just log in", Go to log in + Back to home |
| 403 that says expired | **"This link has expired"**, Go to log in + **Contact us** (`/contact`) + Back to home |
| bare "Not Found" 404, the "no roles" 403, 500, anything else | the existing "Confirmation failed" with the generic message (fails closed) |
| no connection | the existing "Can't reach the server" |

Also:
- **Focus:** after a server or network failure, focus moves to the error heading, which is described by the message. Before, screen readers heard nothing.
- **Shared helpers:** a new `core/errors/api-error-text.ts` (`errorStatus`, `serverText`, `isBareNotFound`). `reset-failure.ts` (#148) moved onto it with no behaviour change.
- **Classifier:** a new pure `classifyConfirmFailure` (`confirm-failure.ts`).
