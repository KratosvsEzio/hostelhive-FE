### The cards

- **#120:** on `/search/lahore`, picking Karachi in the mobile place field (`onPlaceSelected`, non-seeded branch, `search-map.ts`) merges `place/lat/lng` but keeps the path `/search/lahore`. `canonicalPlace` prefers the path slug (`search-map.ts:263`), so an unfiltered Karachi search can carry canonical `/hostels/lahore` and a "Lahore" title. **AC:** the pick lands on `/en/search/karachi…`, and the title and canonical name Karachi.
- **#119:** after panning `/search`, the URL holds `ne_*/sw_*`. `SearchBar.search()` navigates to `/search/<slug>` with a merge and doesn't null them, so a newly constructed SearchMap restores the old box over the new place. **AC:** on `/en/search/lahore`, pan, then search Karachi from the header → map and request on Karachi. Fix: `...VIEWPORT_KEYS_NULLED` (`search-scope.ts`).
- **#121:** `PlaceLanding` sets the `place-breadcrumb` and `place-faq` JSON-LD and clears them only on a not-found page (`place-landing.ts:200-201`), never on destroy. **AC:** a client navigation from `/en/hostels/lahore` to `/en/search/karachi` leaves no such JSON-LD.

### What we already decided in this area

- A new place means `searchRouteFor(place)`: the header bar, the hero and, since #73, landing exits (`leaveLanding`).
- `VIEWPORT_KEYS_NULLED` and the other key sets live in `search/search-scope.ts`; any navigation that changes place nulls the viewport (#110 D8).
- `everywhere=1` is read at construction; a new place clears it (#110 D4).
- Unfiltered curated searches canonicalise to `/hostels/<slug>`; filtered ones are noindex (decision `curated-landing-pages-own-place-intent.md`).

## Root cause

**Status: confirmed** (2026-10-11): the new e2e fails on `origin/main`'s sources with each reported symptom (#120 URL keeps `/search/lahore`; #119 north edge 31.31 = Lahore; #121 one `place-*` survives) and passes on the branch. See QA results, round 4.

| | |
|---|---|
| **Symptom** | #120: a Karachi pick on `/en/search/lahore` → canonical `/en/hostels/lahore`, title "Search hostels — HostelHive". #119: a header search for Karachi after the map settles on `/en/search` → request on Lahore's box. #121: `place-breadcrumb` / `place-faq` survive a client navigation away. |
| **Cause** | **#120:** `onPlaceSelected` (`search-map.ts:1509-1519`) merges into the current path, so the `lahore` slug stays, and `canonicalPlace` (`:263-268`) reads the slug before `place`. The slug is the one reader that beats `place`, against the "slug is cosmetic" decision. The **title** half is separate and pre-existing: the route `title` in `search.routes.ts:6,14` is re-applied on every NavigationEnd (Angular's `DefaultTitleStrategy`), including `replaceUrl` viewport writes, and the SEO effect only re-runs when its inputs change. **#119:** `SearchBar.search()` (`search-bar.ts:282-309`) merges without nulling `ne_*/sw_*`. It shows across configs: bare `/search` ↔ `/search/x`. **#121:** `place-landing.ts:185-291` sets the JSON-LD with no teardown; `Seo` assumes the next page overwrites, but ids are per page type. |
| **Why it escaped** | #110 made "/search unchanged" an AC, and its TC-15 (`search-map.spec.ts:504-525`) asserts today's merge on an **unrouted** mount, so the slug was invisible. No test checks the canonical or title after a pick, and none checks the viewport keys in `SearchBar.search()`. No `PlaceLanding` or `Seo` spec; JSON-LD has only been checked on server renders. |
| **Same shape elsewhere?** | **"Near me" on `/search/<slug>`** (`search-map.ts:1680-1684`) keeps the slug, so its canonical is `/hostels/lahore` under "My location". **JSON-LD never cleared on destroy:** home (`organization`, `website`), blog (`blog`), blog-article (`article`, `breadcrumb`), listing (`listing` + preload image). **SSR safety for #121 (verified in source by the PE):** `@angular/ssr` `renderAngular` serialises the document (`platformState.renderToString()`) **before** `asyncDestroyPlatform` runs on a `setTimeout(0)` (`node_modules/@angular/ssr/fesm2022/ssr.mjs:181-207`), so a component's `onDestroy` can't remove anything from the server HTML. Each request has its own document. An e2e raw-HTML check still guards it.

## Plan

### Merged plan
1. **One "new search" helper in `SearchMap`:** generalise `leaveLanding` into `startSearch(commands, geo)`: a localised **push**, merge, viewport/place/retired/`everywhere` keys nulled, effective filters carried (`seededFilters(null)` is `{}` on `/search`). The **place pick always** uses it → `searchRouteFor(label)`. Near me uses it → `/search`. Landing "everywhere" keeps its branch.
2. **`canonicalPlace` prefers `toLocationSlug(place || city)`** and falls back to the path slug: defence in depth for links already shared with the wrong slug, consistent with the cosmetic-slug decision.
3. **Route titles:** remove `title` from `search.routes.ts` so the SEO effect owns the `/search` tab title (D-pending).
4. **#119:** `...VIEWPORT_KEYS_NULLED` in `SearchBar.search()`.
5. **#121:** `DestroyRef.onDestroy` clears `place-breadcrumb` and `place-faq` (with a comment on why SSR is safe). Optional: a `Seo` helper and the same sweep for home, blog, blog-article and listing (D-pending).
6. **Tests:**
   - rewrite TC-15 (it asserts the defect) and route TC-16;
   - routed pick, bare-`/search` pick, non-Latin label;
   - canonical precedence (`Seo.apply` spy);
   - Near me on `/search/lahore`;
   - `SearchBar` viewport nulls;
   - a `PlaceLanding` destroy spec;
   - e2e: red on `main`, plus a raw-HTML SSR guard.

### Principal Engineer report (key content)
- **Route reuse:** `/search` (`''`) and `/search/:location` are separate configs. Same config → same SearchMap (`paramMap` emits; `recenterTo` runs if the map is ready and `center()` changed). Different configs → a new SearchMap (viewport read once at construction).
- **Title:** `DefaultTitleStrategy.updateTitle` on every NavigationEnd (`@angular/router` `_router-chunk.mjs:3894`) overwrites the SEO title after viewport writes. Landing routes have no `title`.
- **Rejected for #121:** clearing on NavigationStart (PlaceLanding is reused across query-only navigations, so the JSON-LD would be lost while still on the page); clearing during the next page's setup (every page would need every other page's ids). No `isPlatformBrowser` guard needed.
- **Edge cases:**
  - the same city picked again → `/search/lahore-punjab-pakistan` (noindex), no special case;
  - a non-Latin label → `/search`;
  - `?gender=bogus` scrubbed;
  - a header search for the same place on a reused instance keeps the panned box until the next settle (low; accept);
  - landing → landing across configs: the router deactivates before it activates, so the order is right.
- **Decomposition:** T1 SearchMap (+ routes), T2 SearchBar, T3 PlaceLanding (+ optional Seo sweep), T4 e2e. File sets are disjoint.
- **Open questions:**
  - Q1 remove route titles (yes);
  - Q2 Near me (yes);

  - Q4 JSON-LD sweep via a Seo helper (yes; PlaceLanding-only is the fallback);

## Notes

### Header bar undoes an unsubmitted pick while the map settles (pre-existing)
Found by batch C in round 3. `SearchBar` subscribes to `queryParamMap` and re-syncs `place` on every emission (`search-bar.ts` constructor). The map's settle writes the viewport into the URL with `replaceUrl`, so a place the visitor has picked in the header but not yet submitted gets reset to the URL's place (Lahore) shortly after load. This is user-visible and outside this change. **Filed as [#130](https://trello.com/c/PHUAOxLb)** (user, 2026-10-11).

### `noindex` pages canonicalise to the home page (pre-existing, out of scope)
`Seo.apply` always calls `setCanonical`, with `path ?? '/'` (`core/seo.ts`), so a `noindex` search (any filtered or uncurated search) gets `<link rel="canonical" href="https://hostelhive.com/en">`. The decision `curated-landing-pages-own-place-intent.md` says such pages are "`noindex` with **no** canonical". The code and the decision disagree, and that predates this run. Seen in the #120 verification: the uncurated Karachi search has canonical `/en`. **Filed as [#131](https://trello.com/c/nKbhi1d4)** (user, 2026-10-11).
