## Ticket understanding

**Source manifest:** Trello card — ready (read in full). No linked docs, designs or comments.

**Card text (summary):** Esc does not close any `hh-confirm-modal`. `DialogFocus.onKeydown` only handles Tab. The backdrop and Cancel already emit `cancel`.

Fix as specified:
- Esc emits `cancel`, the same as the backdrop. Only the top-most dialog handles it. Focus returns to the control that opened the dialog.
- Esc is ignored while `confirmDisabled` is set.

Acceptance:
1. Esc closes any open `hh-confirm-modal`, and no confirm action fires.
2. Unit tests in `confirm-modal.spec` / `dialog-focus.spec`.
3. Billing downgrade and cancel confirms dismiss on Esc and send no request (a `billing-page.spec` case).

**Prior context:** `docs/knowledge-base/area/ui-library.md` lists `[hhDialogFocus]` as "focus trap + return" and `hh-confirm-modal` + `hhDialogFocus` as the modal pair. Focus return already lives in `DialogFocus.ngOnDestroy`, so the parent closing the modal on `cancel` restores focus with no new code.

## Root cause

| | |
|---|---|
| **Symptom** | Esc does nothing on any confirm dialog |
| **Cause** | `lib/src/ui/lib/dialog-focus/dialog-focus.ts` `onKeydown` returned on every key except Tab, and `confirm-modal.ts` had no other key handling. Nothing on the dialog listened for Escape |
| **Why it escaped** | the directive was built and tested as a focus trap only (its spec had "leaves keys other than Tab alone"); no confirm-modal spec asserted keyboard dismissal |
| **Same shape elsewhere?** | No. The other dialogs already close on Escape by their own means: `hh-drawer`, the hand-rolled host modals with `(keydown.escape)`, and the listing page's document listener chain |

**Confirmed:** the new Escape tests fail with the binding removed and pass with it (Phase 5, mutation M4).

## Plan

1. `DialogFocus` keeps a module-level stack of open dialogs (pushed in `ngAfterViewInit`, removed in `ngOnDestroy`). On Escape it emits a new `escape` output carrying the `KeyboardEvent`, but only when it is the top of the stack. It closes nothing itself, because it does not own the `@if` that shows the dialog.
2. `ConfirmModal` binds `(escape)` and always calls `stopPropagation()`. It emits `cancel` unless `confirmDisabled()`.
3. Specs: the directive (offered, top-most only, not to a covered dialog, returns to the lower one, passes the event), the modal (cancels never confirms, doesn't reach behind, ignored while disabled, focus returns), and billing (downgrade and cancel confirms dismiss on Esc with no request).

PE/PM agents were not spawned; see Notes.

## Decisions

| Question | Decision | Who |
|---|---|---|
| Where does "top-most" live? | In `DialogFocus`, as an open-order stack. DOM nesting can't answer it: a confirm opened from a drawer renders inside the drawer, and a dialog opened over a sibling isn't inside it | settled from the codebase |
| Should the directive close the dialog itself? | No. It emits `escape` and the host decides. The six listing-page dialogs and the room picker already close on Escape through their own document listeners, and an unbound output leaves them as they are | settled from the codebase |
| Stop propagation? | Yes, always, in `ConfirmModal`. Confirms render inside `hh-drawer` panels, whose `(keydown.escape)` would otherwise close the form behind the dialog on the same key press | settled from the codebase (`lib/src/ui/lib/drawer/drawer.ts:51`) |
| Stop it even while `confirmDisabled`? | Yes. A disabled confirm is usually mid-request, and that is the worst moment to lose the drawer underneath | my call, matches the card's "ignored" |
| Add the `billing-page.spec` case? | Yes: it is a pure spec addition, and billing renders the real `ConfirmModal` | the brief allowed it on that condition |
