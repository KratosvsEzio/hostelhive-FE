### The ticket

`NotificationBell` (`apps/web/src/app/layout/components/notification-bell/notification-bell.ts:79`) refetches invites on a `fetchKey` holding `session.isAuthenticated()` — a yes/no flag, not who is signed in. When one account replaces another without a sign-out (the account-confirmation link `/confirm_invitation` → `AuthService.establishSession` → `setSession(B)`), the flag stays `true`, so the bell does not refetch: B sees A's invites, unread count and locally-marked ids until a push or a manual refresh. The header (and the bell) stays mounted across `/confirm_invitation` and the navigation to `/`.

**Fix:** key the fetch on the session user id and reset locally-held per-user state (locally-marked ids) when it changes.

**Acceptance:**
- After `setSession(B)` over A with the bell mounted, the bell shows B's invites and unread count, none of A's.
- Sign-out still empties it; a same-user session refresh does not refetch.

### What we already decided in this area

- Per-user client state follows `SessionStore.user()?.id` (#105 favourites, #114 onboarding draft, #115 host property). Those stores persist, so they need the three-way `holder` (id / `undefined` while only a token / `null` signed out). The bell persists nothing — its state is a fetch result — so the plain user id is enough here (see Plan).
- `AuthService.establishSession` (`core/auth/auth.service.ts:230`) sets the new token first and the new user only after `currentUser()` answers; `refreshSession()` calls `setSession` with the same user's id.

### Assumptions stated

- Notification ids are unique across accounts, so A's locally-marked ids cannot match B's items: they never change B's unread count. Resetting them is hygiene the card asks for, not an observable fix on its own.
- #124 (`establishSession` clears on any error) and #125 (confirm before replacing an account) are separate cards and stay out of scope.

## Plan

One task, one file plus its specs.

1. **`notification-bell.ts`**
   - `private readonly userId = computed(() => this.session.user()?.id ?? null)`, declared above the fields that read it. It must be its own `computed`: `setSession` writes a new user object every time, so reading `user()?.id` straight inside `fetchKey` would emit a new key on a same-user refresh and refetch.
   - `fetchKey` holds `user: this.userId()` instead of `auth`; the `switchMap` empties on `!user`.
   - `locallyMarkedIds` and `actionLoading` become `linkedSignal`s on `userId`, so they reset on the same read that sees the new user (no tick where B's list is checked against A's marks) and stay writable (the badge spec keeps `.set(...)`). `linkedSignal` is already used in this repo (`features/auth/lead-wall/lead-wall.ts:101`, `features/host/bookings/booking-calendar.ts:161`).
   - Unchanged: `dismissing` clears itself on B's first finished fetch (`:97`); the open panel shows the existing skeleton because B's fetch starts with `loading: true, items: []`, and the navigation to `/` closes it.
2. **`notification-bell.badge.spec.ts`** — the session stub gains `user: () => ({ id: 'u1' })` (without it `session.user()` throws).
3. **New `notification-bell.session.spec.ts`** with a real `SessionStore`: A → B refetches and shows only B's items and unread count; A's in-flight response is dropped; same-user `setSession` does not refetch; marks and the action spinner reset on a switch; `clear()` empties. Run it against the pre-fix file first — that is what confirms the root cause.

**Not doing:** remounting the bell per user in the template (hides the state problem); a three-way `holder` like the stores (the bell persists nothing); owner checks in each action callback (a window of one request).

### Principal Engineer report

> I've finished the read-only analysis and changed no files. The cause is clear from the code, but it is **hypothesised, not confirmed**: no test fails on it yet. The fix is one task, and the existing badge spec has to change with it because its session stub breaks.
>
> **Root cause.** `fetchKey` reads `session.isAuthenticated()` (`notification-bell.ts:79-85`), and that value is `this._user() !== null` (`session-store.ts:43`). A to B goes from `true` to `true`, so the computed value does not change and `toObservable` never emits; the `switchMap` at `:89` never runs again. The header is shown on every route except `/host/listings/new` (`app.ts:78-81`); the bell sits inside `@if (isAuthenticated())` (`site-header.html:50-52`), which stays true, so it is never rebuilt. `confirmInvitation` is `establishSession` (`auth.service.ts:79-83`, `:230-241`): `setAccessToken(B)`, then `/users/current`, then `setSession(B)`. The redirect to `/` (`confirm-invitation.ts:56`) only replaces the routed page. Asking why further: the bell was written when sign-in was the only way into a session and the `@if` remounted it; underneath, there is no shared per-user signal in `SessionStore` — each consumer derives its own `userId` (`favorites-store.ts:46`, `onboarding-draft-store.ts:35`, `host-property-store.ts:71`). A shared `SessionStore.userId` would be a reasonable follow-up, not needed here.
>
> **Why it escaped.** A component test driving a real `SessionStore` from A to B would have caught it. `notification-bell.badge.spec.ts:41` stubs the session as a constant; no spec covers when the bell refetches; no e2e runs `/confirm_invitation` with an existing session.
>
> **Same shape elsewhere.**

> | Location | Real leak? |

> | `site-header.ts:139-141` | No — a mount gate |
> | `listing-detail.ts:214,340,378,435,623,634,646`, `listing-card.ts:224`, `search-map.ts:790`, `lead-wall.ts:79`, `guards.ts:18,31,47` | No — click and route gates; route components are rebuilt by the navigation to `/` |

>
> **Recommended change.** `userId` computed declared above `actionLoading` / `locallyMarkedIds` (field initializers run in order); `actionLoading` and `locallyMarkedIds` as `linkedSignal` on `userId`; `fetchKey` `{ user: this.userId(), r, push }`, `switchMap` empties on `!user`. The id must go through its own `computed`: reading `user()?.id` directly in `fetchKey` re-runs on every `setSession` (new user object), returns a new object literal, and a same-user `refreshSession` would refetch.
>
> **Edge cases.** Same-user `refreshSession` / `restoreSession` confirming its cached user: same id, no refetch, no reset. Sign-out: `clear()` makes the `@if` destroy the bell; the `!user` branch stays as a fallback. Token-only window (token B, user A): the interceptor reads the token when the request is sent (`provide-auth.ts:20`); nothing new fires unless a refresh or push tick lands in it, and if one does it fetches B's list under key A, then `setSession(B)` cancels and refetches — harmless; the reverse cannot happen. A's `listInvites` in flight: `switchMap` cancels it; B's fetch emits `items: []` on the same tick. A's markAsRead/accept/reject/dismiss finishing late: `actionLoading` — A's id never matches B's rows; after the reset a late `set(null)` could clear a spinner B just started (accept); `dismissing` clears itself on B's first fetch; a late `refresh++` costs one extra fetch; toasts about A's action may show to B (accept). A markAsRead fired in the token-only window goes out with B's token and A's id; `.subscribe()` has no error handler (`:274`). Open dropdown: NavigationStart closes it (`:60-65`); a `linkedSignal` for `open` is optional. IntersectionObserver: disconnected while closed (`:67-71`), re-observes current rows after each render (`:281-293`). `push.received` is per device.
>
> **Is the `locallyMarkedIds` reset visible?** No — hygiene only. `unreadCount` counts only marked ids in the current list (`:123`); the observer checks only rows on screen (`:271`, `:290`). `id` is the `/api/notifications` record id (`student-api.ts:170`), assumed a primary key. `linkedSignal` is cleaner than an `effect`: it resets on the same read, stays writable, and is already used in the repo.
>
> **Risks.** The badge spec stub breaks (`:41`) — give it `user`. KB text goes stale: `favourites-follow-the-session-user.md:28` says "The notification bell is still keyed on the signed-in flag (Trello #123)". Push registration across a switch — separate card. Tests must flush the `toObservable` effect between session writes or the A → B test passes without testing anything.
>
> **Task breakdown.** One task, T1: `notification-bell.ts`, `notification-bell.badge.spec.ts`, new `notification-bell.session.spec.ts`, the KB line. **Avoid:** remounting per user in the template; a three-way `holder`; owner checks in each action callback.

### Product Manager report

> **Intent:** the bell must always show the account that is signed in now. Nothing of A's (content, count or actions) may stay visible or clickable once B is seated. Every other per-user part already follows the session user's id; the bell is the last one, and the knowledge base says so (`favourites-follow-the-session-user.md:28`).
>
> **Who hits this:** anyone signed in as A who opens a "Confirm My Account" link for B on the same browser — a shared or family computer, a host or staff member opening an invite for someone else, a tester with several accounts. Rare, but every time until a reload.
>
> **Harm:** (1) Privacy — B sees A's notifications (invite and meal-confirmation messages, rent and receipt notices, hostel names, A's unread count). (2) Wrong count. (3) Acting on A's notification as B, checked against `be-hostelhive@main` (`be58f6b`): accept/reject and mark-as-read are refused with **422 "Invalid token"** by `authenticate_invite` (`user_invites_controller.rb:6,93-96`); review only navigates and a later `add_review` is refused too. **Dismiss (`DELETE /api/notifications/:id`) is not covered by `authenticate_invite` and has no owner check (`:79-85`)**; the only gate is CanCan, and `UserInvite` defines no `permitted_conditions` (`ability.rb`). If B's role holds the `UserInvite` destroy permission (data, not code — `lib/tasks/permission.rake`), B deletes A's notification on the server.
>
> **Acceptance criteria** (Given the bell is mounted with A signed in and A's list loaded, with a pending interactive invite and an unread item):
> 1. When `setSession(B)` runs, the bell sends exactly one new request for B's list and shows only B's items and B's `unread`.
> 2. Before B's list returns the badge is hidden; it never shows A's number.
> 3. An open dropdown shows the loading skeleton in place of A's items, then B's items or the empty state (closing is also acceptable).
> 4. A's Accept/Decline/Dismiss/Review buttons go away with the items; no click after the switch can send A's id.
> 5. An in-flight Accept/Decline on A's invite leaves no button stuck disabled and no "dismissing" state; reset `actionLoading` and `dismissing` on a user change; a late toast may appear.
> 6. A late response for A's list never shows.
> 7. Locally marked ids are cleared on a user change.
> 8. `mark_as_read` is sent only for B's ids after the switch.
> 9. Sign-out (or a 401) unmounts the bell; a later sign-in as B shows only B's data.
> 10. A same-user `setSession` (refresh, restore) makes no new request and no skeleton flash.
> 11. A restore that resolves to a different user than the cached one is treated as a switch.
> 12. A push still refetches.
>
> **Product rules.** Per-user client state follows `SessionStore.user()?.id`; the same id again must not wipe or refetch. Every way in goes through `setSession` or `clear`, so listening to the session covers all of them. The badge is the server's account-wide `unread` minus marks the server hasn't caught up with — keep that rule; only the set of marks resets. The backend scopes the list to `current_user`, so the fix is only about when the bell refetches.
>
> **Out of scope:** #124, #125, the `/notifications` page (a route component, not mounted during the confirm flow), the backend `destroy` gap, push registration moving from A to B, any visual change. **Must not regress:** the badge correction, push refetch, refetch after accept/reject/dismiss, closing on navigation/Escape/outside click, no second fetch when the restored user matches, no bell for signed-out visitors.
>
> **Open questions (with recommendations).** (1) Token-only window: ship keyed on the user id, name the gap in the PR, give it to #125. (2) Backend `destroy` has no owner check: raise a backend card. (3) Open dropdown: keep it open with the skeleton. (4) Toast from A's in-flight action: accept it; clear the disabled/loading flags only. (5) Notification ids assumed unique. (6) Manual QA needs two accounts and a fresh confirmation link; the unit spec is the main proof.
