### #201 (as written)

> **Found while fixing #160 (PR #184).** Same shape as #160, on the landing page instead of `/search`.
>
> **Verified (2026-10-18, dev server on the #160 branch, live LAN API):** the raw server HTML of `/en/hostels/lahore?ne_lat=20&ne_lng=100&sw_lat=10&sw_lng=90` has `index, follow`, canonical `https://hostelhive.com/en/hostels/lahore`, title "Hostels in Lahore — verified hostels, PGs and co-living", and h1 "Hostels in Lahore".

>

>
> **Decide:** make a landing link carrying a viewport `noindex`, as `/search` does now; or don't let a landing page restore or write a viewport at all; or both.
>
> **Acceptance:** a product decision is recorded; a landing page link carrying a far viewport no longer shows Lahore's indexable copy over another area's hostels.

### Understanding

A landing page is the place's indexable page, and it should always show and claim the place. Today a landing URL carrying viewport keys restores that box for the camera and the list, both on the server and in the browser, while the head still claims the place, indexable. Panning the landing also writes keys into its URL, so most copied landing links carry a viewport.

After the change:
1. **Restoring:** a seeded `SearchMap` ignores the URL viewport. The camera opens on the place and the list searches near the place, including in the server HTML.
2. **Writing:** it never writes `ne_*`/`sw_*` into the URL. A pan still re-searches the visible box in memory.
3. **The head:** `PlaceLanding` emits `noindex` with no canonical, `og:url` or hreflang when the link it was opened with carries a valid viewport (the same four-keys-with-area test as `/search`, decision D8 of #160). It keeps the place title, description and photo, because the page now really does show the place.

A pristine `/hostels/lahore` is unchanged: indexable, with a self-canonical.

## Root cause

**Status:**
- **Head:** confirmed live by the reporter (this session, 2026-10-18).
- **List, camera and write:** hypothesised, from deterministic code paths. They become confirmed once L1, L2 and L4-L6 fail on HEAD and pass after the fix.

**Symptom.** The raw HTML of `/en/hostels/lahore?ne_lat=20&ne_lng=100&sw_lat=10&sw_lng=90` reads `index, follow` with the canonical `/en/hostels/lahore` and a Lahore title and h1. The list under it searches the far box. Panning a landing writes the keys into its URL.

**Causes:**
- **List and camera.** `mapBounds = signal(this.urlBounds())` (`SM:403`) is a field initialiser that reads before `seed` (an input) is set. Separately, `urlBounds` (`SM:391-400`) has no notion of a seed: the viewport keys pass through `mergeSearchParams` untouched. `query()` (`SM:524-526`) then prefers the box, and `setup()` (`SM:1295-1312`) calls `fitBounds` to it and marks `userInteracted`.
- **Write.** `syncBoundsToUrl` (`SM:1978`) has no seed guard.
- **Head.** `PL:226-255` claims the place, indexable, without looking at what the request uses.

**Why, pushed further.** There are two models of a landing page's geography:
- `PlaceLanding` says the path is the place;
- the embedded `SearchMap` says URL state wins.

That is #160's head-versus-request shape, one level up. Under it is a second cause: construction-time reads of seed-dependent state. The KB trap at `area/search-and-discovery.md:84` says the seed must be known on the first pass; `unbounded` honours it, but `mapBounds`, `areaChosen` and `arrivedWithViewport` don't.

**Why it escaped.**
- #160 scoped landings out (D5). The landing describe only tests the exits.
- The e2e harness hides the write: `stubListings` returns no hostels, so `fitTo` never runs, the camera never moves, and no e2e landing ever wrote keys.
- The right level is a component test with a seed plus a viewport URL (the harness already reproduces input-after-construction), plus a raw-HTML e2e of a keyed landing.

**Same shape elsewhere.**
- **The query's place keys (`place`/`lat`/`lng`/`zoom`) override the seed on a landing** (query wins, `search-params.ts:188-191`). No app writer produces them on a landing; only a hand-made link does. Code-proven; a follow-up card.
- **`areaChosen` and `arrivedWithViewport` have the same initialiser flaw.** Neither is read on a landing, so it isn't visible.
- **An unknown slug** (`/hostels/nowhere`) has seed `null`. Its embedded map behaves as a bare `/search`. It is noindex either way, and out of scope.

## Plan

### Merged plan

**Part 2: no restore, no write (`SearchMap`).**
- **`seeded`.** A new `seeded = computed(() => this.seed() !== null)`.
- **No restore.** `urlBounds` returns `null` when seeded, via a new shared `viewportIn(params)` in `search-scope.ts`. That is the D8 rule moved without changes; `hasArea` is exported from `search-framing.ts`.
- **No initialiser reads.** `mapBounds`, `areaChosen` and `arrivedWithViewport` become `linkedSignal`s:
  - sourced on `seeded`, not `seed`, so a gender-to-gender page reuse keeps the visitor's in-memory view;
  - computed with `untracked(urlBounds)`, so the map's own rounded write on `/search` doesn't reset the box and fire another search.
- **No write.** `syncBoundsToUrl` returns early when seeded.
- **Unchanged:**
  - `captureMapBounds`, so a pan still re-searches the box in memory;
  - `startSearch`, `searchEverywhere` and `recenterTo`, which only null keys.

**Part 1: noindex (`PlaceLanding`).**

### Principal Engineer report

**Corrections to the brief.**
- `acquire` already gets the seed centre on HEAD (`setup()` runs after the inputs are set). The bug is the `fitBounds(restored)` that follows, so the camera test must assert that **`fitBounds` is not called**.
- A `linkedSignal` on `seed` would regress gender-page reuse, which changes `seed` but keeps the centre. Source it on `seeded` instead.

**Timing (verified for Angular 21.2.9).**
- Signal inputs are set during the parent's first update pass, after `SearchMap`'s constructor and field initialisers, and before its effects and first template pass. The spec copies this order (`spec:223-224`).
- `producerRecomputeValue` runs the `linkedSignal` computation with the node as the active consumer (`_untracked-chunk.mjs:56-73`), so `untracked` is required.
- SSR: `query()` first reads `mapBounds` after the seed is set, giving `null` and therefore `near` the seed. `setup()` never runs on the server. Whether the server request lands before the page stabilises (the `timer(600)` isn't a `PendingTask`) doesn't affect correctness.

**`setup()`:** `restored` and `home` are both null, so there is no `fitBounds` and `userInteracted` stays false. The first results then `fitTo`, which does `setView(seed centre, seed zoom)`: exactly a pristine landing.

**The writer guard:**
- It sits in `syncBoundsToUrl`, not `captureMapBounds`. Guarding earlier would also stop the in-memory re-search (mutant M4).
- Side effect: `everywhere: null` is no longer written on a landing. That's harmless, because `unbounded` is always false when seeded and every exit nulls it.

**Part 1, live read vs arrival machinery.** The live read is recommended:
- After Part 2 the live URL equals the arrival, so one URL gets one verdict everywhere.
- Copying #160's `NavigationEnd` and refinement machinery would duplicate code merged hours ago.
- The risk is stated plainly: a regressed write guard would de-index every landing in crawlers that run JS. It is double-pinned in CI (`ci.yml:33` runs `test` and `e2e`), and the comments in `syncBoundsToUrl` and `carriesViewport` name each other.

**Head and JSON-LD:**
- The head is `noindex: true` with no `path`, in both branches.
- Title, description and `placeSocialImage` are kept, and the unknown-place branch is unchanged.
- The breadcrumb and FAQ are kept, because the content is identical and the FAQ is visible (Google's policy).

**Don't strip the keys:**
- The keys are inert on a landing, and nothing can bring them back to life: exits null them, and merges and language switches stay on a landing.
- Stripping would be the same-path write Part 2 removes, and it would flip the rendered head away from the raw one.

**Edge cases:**
- A keyed landing on the server lists near the place and gets the noindex head.
- Hydrated, the camera opens on the place, pans stay in memory, and the URL keeps its arrival keys.
- A pristine landing that pans, zooms, resizes, or is rendered by a crawler that runs JS stays clean and indexable.
- Partial or garbage keys read as none, so the page is indexable.
- Filter Apply or gender Apply on a keyed landing carries the keys, so it stays noindex.
- Gender-to-gender reuse after a pan keeps the box (L7).
- A language switch or Back onto a keyed entry is noindex.
- **Back from a listing, or a refresh after a pan, reopens on the place: the pan is lost.**
- Exits null the keys.
- `?everywhere=1` stays in the URL, inert.
- In GA, `page_title` is unchanged and landing pans are no longer navigations at all.

**Technical requirements:**
1. The first request for a keyed landing is `near` the seed, with no `bounds`, on the server and in the browser, for city, gender and campus.
2. No `fitBounds` to a URL viewport, and no `forVisitor`.
3. A settle sets `mapBounds`, resets the page, and the next request carries the box. `navigate` is never called with `ne_*`/`sw_*`. Arrival keys are neither overwritten nor stripped.
4. Unseeded behaviour is byte-for-byte identical, and the map's own write doesn't trigger another request.
5. In `PlaceLanding`, a valid viewport gives `noindex: true` with no `path` and everything else unchanged. Without one, the head is today's, with no `noindex` key.
6. There is exactly one parser of the four keys.
7. Raw HTML for a keyed city or campus landing: noindex, `[]` canonicals and `og:url`, 0 hreflang, the place title and h1, JSON-LD present. Pristine: index, canonical and `og:url` at `/en/hostels/lahore`, hreflang count > 0.
8. A pristine landing after a pan: no `ne_lat`, head unchanged, a request carried the box.
9. No new i18n keys and no backend change.

### Open questions (consolidated)
