### #128 (card text)

> On `/search/lahore`, "Search everywhere" nulls `place`/`lat`/`lng` but keeps the `lahore` path, and the page is correctly worldwide (#110). A pan then ends the worldwide search. With no `place` in the query, the path slug becomes the heading and the canonical again. The page then names Lahore over whatever area the visitor has panned to. See `locationName` and `canonicalPlace` in `search-map.ts`.
>
> **Fix direction:** "Search everywhere" on `/search/<slug>` could navigate to bare `/search?everywhere=1` instead of keeping the slug. Or the heading and canonical could ignore the slug once a pan has replaced it.
>
> **Acceptance:** On `/en/search/lahore`: Search everywhere, then drag the map. The heading and canonical don't claim Lahore unless the map is on Lahore.

### #130 (card text)

> On `/search`, shortly after the page loads or after a map drag, the map writes its viewport into the URL as it settles (`syncBoundsToUrl`, `replaceUrl`). `SearchBar` subscribes to `queryParamMap` and to `NavigationEnd`, and re-syncs `place` from the URL on every emission (`search-bar.ts`, constructor / `syncPlace`). So a visitor who picks a new place in the header's Where field but hasn't pressed Search yet sees it reset to the URL's place (e.g. Lahore). Pressing Search then searches the old place.
>
> **Fix direction:** don't overwrite the bar's place while it has an unsubmitted edit, for example while the Where field is focused or dirty. Alternatively, re-sync only when the URL's `place`/`lat`/`lng` actually change, not on viewport-only writes.
>
> **Acceptance:**
> - On `/en/search?place=Lahore…`, drag the map and immediately pick Karachi in the header. The field still reads Karachi as the map settles, and Search goes to `/en/search/karachi-…`.
> - A real navigation to a new place still updates the bar.

### What I found in the code

- **#128.** `SearchMap.searchEverywhere()` (`search-map.ts` ~1554) does a `[]`-relative merge with `replaceUrl`, so `/search/lahore` stays `/search/lahore?everywhere=1`. The first real pan sets `unbounded` to false, and `syncBoundsToUrl` clears `everywhere`. With no `place`/`lat`/`lng`:
  - `slugPlace()` resolves Lahore again;
  - `locationName()` answers "Lahore";
  - `canonicalPlace()` answers Lahore, so the head is **indexable** with canonical `/hostels/lahore`.
  The request itself is right: once `mapBounds` is set, `near` is dropped and the panned box is sent.
- **#130.** `SearchBar` sets `place`, `lat`, `lng`, `zoom` (and budget and type) from the URL on every `queryParamMap` emission and again on every `NavigationEnd`. The map's viewport writes are both. A header pick that has not been submitted is overwritten, and `lat`/`lng` are reset with it.
- The e2e spec `search-new-place-and-landing-head.spec.ts` ("searching a new place from the header after the map has moved") **works around #130**: it waits for the URL to go quiet, then retries the pick until it sticks.

### What earlier runs decided in this area

- **#120 / PR #86:**
  - every place change goes through `startSearch` (a push to a `/search` path, nulling viewport and place keys);
  - landing-page "Search everywhere" goes to `/search?everywhere=1`;
  - `everywhere=1` is read once at construction, and `syncBoundsToUrl` is its only writer afterwards.
- **#110:** "Search everywhere" drops the slug-implied place from the request while worldwide; the pan that ends it must not fly the camera back to the slug.
- **#144 / PR #126:** GA skips an imperative `replaceUrl` with the same page path; a push to a new path is a new page view.

### Understanding

Two independent defects in the search area, one branch:
1. A worldwide search started from `/search/<slug>` keeps a path that still names the old place. That path names it again, in the heading and the canonical, as soon as a pan ends the worldwide search.
2. The header bar treats every URL change as the truth for its own edit state, including the map's viewport-only refinements.

No blocking questions.

### #128

|---|---|
| **Symptom** | "On `/search/lahore`, 'Search everywhere' … A pan then ends the worldwide search … the path slug becomes the heading and the canonical again." |
| **Cause** | `search-map.ts:1567-1579`: on any non-landing page, `searchEverywhere()` merges into the current path (`navigate([], {relativeTo, merge, replaceUrl})`). So `/search/<slug>` keeps naming the place the visitor just discarded. Once a pan clears `everywhere`, the slug's readers (`slugPlace` → `locationName`/`placeText`, `canonicalPlace`, and `SearchBar.syncPlace`) name it again. `zoom` is not nulled either. Root: the path is state, and a query merge cannot remove what the path supplies (the same shape as #106/#109/#110/#120). The #110 fix patched one reader (`query()`, `:407-412`) instead of the URL. |
| **Why it escaped** | TC-36 (`search-map.spec.ts:937-949`) asserts only the request after "everywhere" on a slug. The head specs mount static URLs. Nothing chains everywhere → pan → head on a slug path. The missing level is **e2e** (or a component test of the navigation target). |
| **Same shape elsewhere?** | `searchEverywhere` is the only in-place navigation that removes a place; every other place change already goes through `startSearch`. Three more symptoms of the same defect: during the worldwide search, the mobile field (`placeText`) and the header's Where field read "Lahore", and an uncurated slug's heading comes back after a pan. |
| **Status** | **confirmed** (QA round 1 unit Q1–Q5, round 2 e2e Q8: red on `origin/main`, green with the fix). |

### #130

| | |
|---|---|
| **Symptom** | "a visitor who picks a new place in the header's Where field but hasn't pressed Search yet sees it reset to the URL's place." |
| **Cause** | `search-bar.ts:192-209` and `:215-220`: every `queryParamMap` emission and every `NavigationEnd` overwrite `place/lat/lng/zoom`, the budget and the type, whichever keys changed. ## Plan

### Merged plan

**#128: "Search everywhere" on `/search/<slug>` leaves for bare `/search?everywhere=1`** (PE option a, PM OQ-1):
- In `searchEverywhere()`, branch on `seed() || locationSlug()` → `startSearch(['/search'], {everywhere: 1})`, a push.
- The in-place `replaceUrl` merge stays for bare `/search` only.
- The cross-config navigation builds a new `SearchMap`, which reads `everywhere=1` at construction, the same path the landing pages use (proven by e2e TC-30).
- This fixes every reader of the slug at once, including refresh and shared links.
- GA: one page view of `/search` per such click (as from a landing page); bare `/search` is unchanged at zero.

**#130: the header bar re-syncs per group, only when that group's URL inputs change** (PE option a, PM OQ-6):
- **Place group:** `place, city, lat, lng, zoom` plus the routed slug.
- **Budget group:** `minPrice, maxPrice`.
- **Type group:** `gender`.
- `activeSort` keeps syncing every time.
- The map's viewport writes change none of the groups, so unsubmitted Where/Budget/Accommodation edits survive.
- A pasted `/search/lahore` still fills from `NavigationEnd`, because the slug is part of the place key.
- Implementation: `linkedSignal`s over `computed` sources with structural equality, or an equivalent keyed diff.

**Tests:**
- Unit:
  - `search-map.spec.ts`: rewrite TC-36 and remount the "widens in place" test on bare `/search`;
  - `search-bar.spec.ts`: new describe.
- E2E:
  - a new everywhere-from-slug spec;
  - remove the #130 workaround in `search-new-place-and-landing-head.spec.ts`;
  - add the #130 acceptance test.

**Out of scope (both agents):**
- a plain pan on `/search/<slug>` or `?place=` (the heading names the search, by design);
- the "Pakistan" heading after a pan on bare `/search`;
- normalising legacy `/search/<slug>?everywhere=1` links.

<details><summary>PE report (verbatim)</summary>

**Current behaviour, #128.**
- `searchEverywhere()` (`search-map.ts:1554-1580`) has two branches:
  - Landing page (`seed()` set): it leaves through `startSearch(['/search'], {everywhere:1})`.
  - Anything else: it sets `unbounded`, then merges in place with `navigate([], {relativeTo, merge, replaceUrl})`. That nulls the viewport keys plus `lat/lng/place/city` and writes `everywhere=1`. It does not null `zoom`, and the path `/search/lahore` stays.
- While `unbounded()` is true, the head effect short-circuits to the worldwide title and `noindex` (`:844-855`), and `query()` drops the slug-implied centre (`:412`).
- A real drag calls `leftHomeCountry()`, which sets `unbounded` to false. `syncBoundsToUrl` then writes the box with `everywhere: null`.
- From there, `slugPlace()` resolves `lahore` again, `locationName()` returns "Lahore", and `canonicalPlace()` returns Lahore (indexable `/hostels/lahore`). The request is still correct, because `mapBounds` is set.
- The mobile `placeText` and the header `syncPlace` read "Lahore" even while worldwide. An uncurated slug's heading comes back after the pan.
- `''` and `':location'` are separate route configs, and `AppRouteReuseStrategy.shouldReuseRoute` compares `routeConfig` (`route-reuse-strategy.ts:32`), so `/search/lahore` → `/search` builds a new component. It reads `everywhere` at construction (`everywhereInUrl`, `:349-351`), as landing-page "everywhere" already relies on (e2e TC-30).

**Current behaviour, #130.**
- The `queryParamMap` subscription (`search-bar.ts:192-209`) unconditionally sets `place`, `lat`, `lng`, `zoom`, `budgetLow/High`, `accommodation` and `activeSort`. The `NavigationEnd` subscription (`:215-220`) calls `syncPlace` on every navigation.
- `syncBoundsToUrl` (`:1744-1757`) and `recenterTo`'s viewport clear (`:1647-1653`) emit both.
- The mobile field is safe: `placeText` is a `computed` with string equality, and `hh-place-search`'s `value` effect (`lib/src/maps/lib/place-search.ts:169-173`) does not re-run.

**Root causes:** as recorded in Root cause above (taken from this report).

**Options for #128 (recommend a).**
- **(a) Leave for bare `/search?everywhere=1` through `startSearch`.**
  - Works as a cross-config rebuild, and also nulls the stale `zoom`.
  - Fixes every reader, including refresh and shared links.
  - Push, because Back returns to `/search/lahore?…ne_*` and Forward rebuilds and re-reads `everywhere=1` (better than D10).
  - GA counts one view of `/en/search`, revising #152 D8 for the slug case only.
  - A path change resets scroll (`scroll-reset.ts:38-45`), which is fine.
  - No SSR concern: the action runs in the browser only.
  - The mobile sheet starts at `peek`.
  - `startSearch` also clears retired keys, normalises `gender`, and drops a price sort with no type.
- **(b) Ignore the slug after a pan.** Rejected: a component-held flag is lost on refresh or share, it needs threading through 4-5 readers including `SearchBar`, and it leaves "Lahore" in both fields while worldwide.

**Options for #130 (recommend a).**
- **(a) Re-sync each group only when its URL inputs change.** The place group includes the slug read at that moment (which keeps the pasted-slug `NavigationEnd` fill and handles slug → bare `/search`), plus a budget group and a type group.
  - Preferred implementation: `linkedSignal`s over `computed` sources with structural `equal`, the idiom `SearchMap` already uses. An imperative `lastKey` per group is an acceptable alternative.
  - Behaviour:
    - a new place updates the bar;
    - Back to an entry with the same place keys keeps the edit;
    - a language switch keeps the edit;
    - in-place "everywhere" on bare `/search` clears the edit.
- **(b) Focus/dirty flag.** Rejected: focus has already left the field when a pick is made (the budget popover opens), and the dirty flag's clear rule *is* option (a).
