### The ticket

`HostPropertyStore` clears the host's hostels and selected property only on the signed-in → signed-out transition (`wasAuthenticated && !isAuthenticated()`). When one account replaces another without passing through "signed out", `isAuthenticated()` stays `true`, nothing clears, and the new account starts with the previous host's hostel list and selection (incl. the persisted `hh_property`).

**How it happens:** `/confirm_invitation` → `AuthService.confirmInvitation` → `establishSession` → `session.setSession(B)` with no `clear()` and no check that someone is already signed in; or a session restore that resolves to a different user. Not the Log in screen — `LeadWall` redirects a signed-in user away.

**Reproduced (2026-10-11, unit test on the card):** A signed in with `a-1`, `a-2` loaded and `a-2` selected; `session.setSession(B)` leaves `hostels()` `['a-1','a-2']` and the selection and `hh_property` on `a-2`. Control: A signing out first clears.

**Fix (card):** key the clear on `session.user()?.id` changing (A→null and A→B); keep bootstrap's initial `null` from wiping a persisted selection that belongs to the same user. Separately, consider whether `/confirm_invitation` should sign the current user out (or ask) first.

**Acceptance (card):** the reproduction test passes; reloading as A still restores A's persisted selection; signing out still clears everything.

### What the code shows (`origin/main` @ `7eefc2e`)

- Only the selected id is persisted (`hh_property`), with no owner; the list is never written to disk. The store is created lazily (first host-area visit).
- The host shell calls `load()` on every dashboard entry (`host-shell.ts:72-75`), which eventually replaces A's list and resets a selection B doesn't own.
- **But the guards run first and trust a loaded list:** `hostRootRedirect` and `knownHostelGate` (`host.routes.ts`) short-circuit on `store.loaded() && store.properties().length`. After A→B, `loaded()` is still `true` with **A's** hostels, so `/host` redirects B to `/host/a-2`, and `knownHostelGate` admits `a-2` because it is in the stale list. The shell's `_syncStore` effect then copies `a-2` from the URL into the selection (and `hh_property`); when B's list lands, the store resets the selection to B's first hostel while the URL still names A's. `bookingsGate` / `monthlyOnlyGate` decide on A's billing cycle too.
- The server should refuse B's requests for A's hostel; until then the console shows A's hostel names in the switcher and A's hostel id in the URL.
- `hh_property` left by a session that ended without a sign-out (tab closed) is restored for whoever opens the console next; it heals on load because it is not in their list.

### What we already decided in this area

- #105 / #114: per-user client state keys on `SessionStore.user()?.id`, not the user object or the authenticated flag; the store owns the session hook (no calls added to `AuthService` / `SessionStore.clear()`); #114 added a `holder` computed so a token-only restore is not a sign-out, and eager creation where deletion must happen without the feature open.
- `HostPropertyStore`'s own comment: the initial `null` at bootstrap must not wipe the persisted selection before `restoreSession()` re-establishes the session.

## Plan

### Merged plan

1. **`services/host-property-store.ts`** — copy the #105/#114 shape:
   - one private `state` signal `{ owner, properties, hostels, loaded }`; the public `properties`, `hostels` and `loaded` become **computeds that read empty/false when `state().owner !== userId()`** — the guards are then correct in the same tick as `setSession(B)`, before any effect runs, and with `loaded()` false they call `load()` themselves (no guard change);
   - `userId` / `holder` computeds as in #114 (`undefined` while a token exists without a user → leave alone; `null` → `clear()`; a different id → reset: cancel the request, selection `''`, remove a stored entry B doesn't own, and `load()` again if the store was in use so a guard waiting on `loaded` does not hang);
   - `load()` syncs the owner, stamps the owner it started for, and drops a result for anyone else;
   - selection stored owner-scoped under a new key (`{ owner, id }`), migrated from the legacy plain `hh_property` (rule: D3); `setProperty` writes to disk only with a user; `selected` stays a writable signal (`host-property-store.spec.ts:72` writes it).
2. **Specs** — store cases (A→B same tick and after effects, sign-out, same-user re-set, token-only, restore by owner, legacy migration, in-flight A load landing after B, guard-waiting reload); guard regression tests in `host.routes.spec.ts` (`/host` after A→B fetches B's list → `/host/b-1`; `knownHostelGate('a-2')` → `/host`).
3. Untouched: `host.routes.ts` (comments only, optional), `host-shell.ts`, `core/auth/*` (#105 decision). No eager creation — unlike #114's draft, `hh_property` is an opaque id that an owner-checked restore never hands to anyone else.

### Principal Engineer report

Confirms the store defect and hypothesises the guard consequence. An effect alone is not enough: root effects are scheduled and the guards read `loaded()` synchronously, so gate the public signals on the owner. Clearing alone has two holes — the same-tick window (fixed by the gated computeds) and cancelling a load a guard is waiting on (fixed by reloading after the switch). Owner-scoped storage (~20 lines, new key) closes a selection left by a session that ended outside the store's lifetime, the failed-load path and cross-tab writes; a new key also stops an old bundle reading `{"owner":…}` as an id during the deploy window. No eager creation needed. Existing specs: none break if `selected` stays writable (specs run with no session; owner `null` equals user `null`). Avoid hooks in `AuthService`, keying on the user object, clearing on a first-run `null` holder without stamping the owner, and per-guard owner checks. Gaps: bookmark `/host/<A's id>` + B's list failing to load → the gate fails open by design and B's pages request A's hostel — the server must refuse. Recommends one engineer, sequential (T1 store + spec → T2 guard specs; KB after merge).

### Staff Engineer report (frontend)

`services/host-property-store.ts` only.
- **Gated state:** one private `state` signal `{ owner, properties, hostels, loaded }`; public `properties`, `hostels`, `loaded` are read-only computeds returning `[]` / `[]` / `false` when the state's owner is not the signed-in user — so right after `setSession(B)`, before any effect runs, the guards see `loaded() === false`, call `load()` and wait for B's list. `activeProperty`, `activeHostel`, `isMonthlyBilled`, `isNightlyBilled` read through them. `selected` stays writable. No consumer wrote these signals (only this file).
- **`holder` effect** (body `untracked`) replaces `wasAuthenticated`: token-only → nothing; signed out → `clear()`; same user → nothing; different user → cancel, reset for the new user.
- **`load()`** syncs the owner, stamps who it fetched for, ignores a result/error for anyone else; body `untracked`.
- **Selection** under `hh:host-property` as `{ owner, id }`: `setProperty` writes only with a user; restore with no user returns nothing and leaves both keys; with a user returns their own entry, removes another's, adopts a lone legacy `hh_property` (D2); the legacy key is removed once someone is signed in; `clear()` removes both.

**Deviations (accepted):**
1. Sign-out clears only a store that belonged to someone — a plain `clear()` on the effect's first run at a signed-out start wiped a list a guard had just loaded (broke `knownHostelGate › lets a hostel through when the list is empty or failed to load`; the old code's "initial null must not wipe" case).
2. A switch picks up the new user's own saved selection (or `''`) rather than always `''` — needed so a token-only reload restores A's selection when A arrives.
3. A legacy key is not adopted when a new-format entry already exists; it is just removed.

### Round 2 — reload only when a request was in flight

The first version reloaded after any switch if a load had been asked for since the last switch, so host A → seeker B in one tab would call `GET /api/host/hostels` as B (possible 403 toast) for a page that never asked. Narrowed: `private inFlight` (set by `load()`, cleared by an owned response, reset by `syncOwner()` / `clear()`); after a switch the effect calls `load()` again only if a request was in flight (the only case a guard can be waiting on). A response for A landing after the user changed but before the effect ran is dropped and leaves `inFlight` set, so B still reloads. A finished list is not refetched — the gated `loaded()` already reads false for B.
