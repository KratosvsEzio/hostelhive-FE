### The ticket

`PATCH /api/user/reset_password` (BE PR #39) now answers:
- **200** — password changed, link used up
- **404** "This reset link is invalid or has already been used" — unknown, already-used or wrong-type token
- **403** "This reset link has expired"
- **403** "This account's password can't be reset with a link" — admin and moderator accounts
- **422** "New password can't be blank"

Before PR #39 every valid request crashed with a 500 (a typo) and expired links were accepted. The BE asks the FE to show these, and to offer "Send a new reset link" for an expired or invalid link.

**What the FE does today** (`features/auth/reset-password/reset-password.ts:57-72`): shows `err.message` verbatim (English, whatever the server sends); `AuthApi.resetPassword` has no `inlineErrors()`, so the global toast also fires; the two 403s are not told apart; no new-link action after a failed submit. The page's validation strings (`:39`, `:42-43`, `:68-69`) are hard-coded English. The page already has an "invalid link" state for a missing token, with **Request a new link** → `/auth/forgot-password` (`reset-password.html`, `@if (!token())`).

**Acceptance:** each of the five responses shows its own translated message, with no toast over the page; an expired or invalid link offers a working "Send a new reset link"; spec coverage per status.

### What we already decided in this area

- **Never show raw server text; use translated keys** — #124's confirmation page (`messageKey()`, D5), following `util/models/api-error.ts` ("never surface `message` to a user").
- **A page that explains its own failure suppresses the global toast** — `inlineErrors()` on `signIn`, `signUp`, `googleLogin`, `confirmInvitation`, `currentUser({ inlineErrors })` (#124 D8), `signOut({ inlineErrors })` (#125 D8).
- New strings in all 18 locales, register per file, CRLF round trip.

### Backend facts found in Phase 2 (BE `origin/main`, read only)

- The response body is the Rails envelope `{"errors":[…],"success":false}` with **no machine code** (`app/controllers/concerns/render_message_template.rb:11-17`); the FE's `ApiError` carries `status` + `serverMessages`. The two 403s can only be told apart by their text.
- Check order: 404 → 403 expired → 403 admin/moderator → 422 blank → 422 model errors (e.g. `has_secure_password`'s 72-byte limit) → 200 (the invite is destroyed, so a second submit is a 404) (`sessions_controller.rb:14-28`).
- Reset links last **10 minutes** (`forgot_password` sets `expired_at: 10.minutes.from_now`, `:91`; the email says so) — the expired case will be common.
- The reset token is `SecureRandom.hex(3)` — 6 hex characters (`user_invite.rb` `ensure_token`) — with no rate limit on `reset_password`. A brute-force risk for the BE developer.
- `forgot_password` crashes (500) on an unknown email (`user.id` on nil, `:87`) before its own 404, emails admins/moderators a link they can never use, and answers a repeat within 10 minutes with 422 "Otp already has been shared…".

## Plan (merged; open branches in 2d)

- **`AuthApi.resetPassword`** passes `inlineErrors()`.
- **A pure classifier** `features/auth/reset-password/reset-failure.ts`: `classifyResetFailure(err)` → `linkInvalid` (404 with an envelope) / `linkExpired` (403, text "expired") / `accountNotResettable` (403, text "can't be reset with a link") / `passwordRejected` (any 422) / `network` (0) / `unknown` (anything else, incl. a 404 without an envelope and a 403 whose text matches neither). Normalise the joined `serverMessages` (lowercase, `’`→`'`, collapse spaces); exact match first, keywords second; **fail closed** to `unknown`.
- **Placement:** `linkInvalid` / `linkExpired` → replace the form with the link panel (per-case title and body, **Request new link** → `/auth/forgot-password`); `accountNotResettable` → a panel without the new-link button; `passwordRejected` / `network` / `unknown` → inline above the submit button, form kept, retry allowed.
- **State:** `rejected = signal<{ token, kind } | null>`; the dead-link panel shows only while `rejected().token === token()`, so a new `?token=` clears it. Inline error as a key signal rendered with `| transloco`.
- **Copy** (translated, all 18 locales): validation keys replace `reset-password.ts:39, 42, 43, 68, 69`; no "10 minutes" in any copy.
- **A11y:** the panel heading keeps `id="hh-reset-title"` (the dialog's `aria-labelledby`) and gets focus when it replaces the form (`afterRenderEffect`, as on the confirmation page).
- **Tests:** the classifier (every row), the component (each status → key + panel or inline), `auth-api.spec.ts` (toast flag).

### Staff Engineer report (condensed)

- `core/api-resource.ts`: `patch<T>(path, body, context?)`. With no context it makes the same call as before.
- `services/auth-api.ts`: `resetPassword` passes `inlineErrors()`, so the global toast no longer fires (D6).
- `reset-password/reset-failure.ts` (new) — `classifyResetFailure(err)`:
  - **`linkInvalid`** = status 404 *and* a non-empty `serverMessages`. A routing 404 has no envelope, so it falls to `unknown`.
  - **The two 403s:** the server messages are joined and normalised (lowercase, curly apostrophes to `'`, spaces collapsed, trailing period removed). An exact match wins first, then keywords. If both keyword sets match, or neither, the result is `unknown` (D2).
  - **Other statuses:** 422 is `passwordRejected`; 0 is `network`; anything else, or no numeric status, is `unknown`.
  - `err.message` is never read.
- `reset-password.ts/.html`:
  - **`rejected`** holds only the three dead-link kinds, keyed to the token that was *submitted* (D8). A token change mid-request can't kill the new link.
  - **`panel()`** chooses between missing token, link invalid, link expired and account not resettable.
  - **The account panel** has a `ti-shield-lock` badge, **Contact us** → `/contact`, and **Back to login** → `/auth?mode=login` (the same route forgot-password uses). It has no new-link button.
  - **Headings:** every panel heading keeps `id="hh-reset-title"`.
  - **Focus:** `afterRenderEffect` focuses the heading (`tabindex="-1"`) when a rejection panel appears. It does not do this for the missing-token panel on load.
  - **Errors:** inline errors and field errors are translation keys.
- i18n: 11 new `authResetPassword.*` keys in all 18 locales, each file +11/−0. `min8Characters1Uppercase` is reused for the password-rule error. Each locale keeps its own formal or informal register and its existing word for "moderator".
- Gates:
  - changed specs: 68 passed (re-run by the orchestrator: 4 files / 68 passed);
  - full web suite: 175 files / 3002 passed;
  - `web:lint`: 0 errors (109 warnings, all in untouched files);
  - `web:typecheck`: OK;
  - `web:i18n-check`: no missing keys.
- **Pre-fix proof:** against the original component and template, the page spec fails 25 of 29. The other 4 are guards that pass both ways: missing token, success, status 0 leaking nothing, and no focus taken on load.
- Prettier was not applied: the touched files were already non-conforming at HEAD, so the edits match the surrounding style.

## Summary

The reset-password page now classifies the backend's answer and shows translated copy:

| Server answer | What the page shows |
|---|---|
| 404 | "This link no longer works", with Request new link |
| 403, expired | "This link has expired", with Request new link |
| 403, admin or moderator | "Reset isn't available for this account", with Contact us and Back to login |
| 422, network error, anything else | inline message; the form stays |

Also:
- **No raw server text:** neither the server's wording nor the API URL reaches the DOM.
- **No toast:** `inlineErrors()` on `resetPassword`, through a new optional `context` on `ApiClient.patch`.
- **Validation and network strings are translated.**
- **A new link starts the attempt over.**
- **11 keys × 18 locales,** guarded by a parity spec.

### Knowledge-base entries drafted (to apply after merge)

- **area (auth):**
  - The reset-password page classifies through `classifyResetFailure` (`features/auth/reset-password/reset-failure.ts`). The two 403s are told apart only by their English text, so a reword on the backend falls back to the generic message until the backend sends codes.
  - A bare Rails "Not Found" 404 is `unknown`, not a used link.
- **decision:** an unrecognised 403 shows the generic inline message, never the expired panel (fail closed). Admins and moderators get Contact us, not a new link.
- **convention:** per-attempt page state keyed to a route token uses `linkedSignal({ source: token })`, and a reply for a token that is no longer current is ignored.
- **convention:** `ApiClient.patch`/`delete` take an optional `HttpContext` (for `inlineErrors()`).
