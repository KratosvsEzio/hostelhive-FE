### The ticket

`AuthService.establishSession` (`core/auth/auth.service.ts:230-241`) has two problems:

1. **Any error clears the session.** Its `catchError` calls `session.clear()` whatever the failure, contradicting "Only a 401 ends a session". A network failure while confirming an invitation signs out the user who was already signed in on that browser.
2. **An account switch skips sign-out's clean-up.** When a confirmation link is opened while account A is signed in, B's token replaces A's in place. `signOut()` (`:101-115`) revokes the JWT server-side (`DELETE /api/user/sign_out`) and calls `push.rotate()`; this path does neither, so A's token stays valid server-side (up to 30 days) and this device's push registration carries over to B (`core/interceptors/push-token-interceptor.ts`).

**Card's fix:** clear only on a 401; otherwise restore whatever session was there before (or leave the tokenless state) and surface the error. When a session is already present for a different account, revoke it and rotate push before seating the new one — or let #125's ask-first step run `signOut()` first.

**Acceptance:**
- A network failure during `confirmInvitation` does not sign out the user who was already signed in.
- After a confirmation link switches from A to B, A's token is revoked and push has been rotated.

### Correction to the card

The card says `establishSession` is "used by sign-in and by the account-confirmation link". It is not used by sign-in: `signIn` and `googleLogin` go through `hydrateInBackground` (`:209-223`), which already clears only on a 401 and has spec coverage (`auth.service.spec.ts:110-130`). `establishSession`'s only caller is `confirmInvitation` (`:79-83`), whose only caller is `ConfirmInvitation` (`features/auth/confirm-invitation/confirm-invitation.ts:55`).

### What we already decided in this area

- **Only a 401 ends a session** (`decisions/auth-and-session/only-a-401-ends-a-session.md`): status 0 / 5xx keep the token; "code that adds a new validation path must apply the same rule". `isUnauthorized()` lives in `core/errors/is-unauthorized.ts` (#116).
- **Push rotates on sign-out** (`decisions/mobile-app/push-permission-after-sign-in-rotate-on-sign-out.md`).
- **Per-user client state follows `SessionStore.user()?.id`** (#105, #114, #115, #123), so an A → B switch already clears favourites, the onboarding draft, the host property and the bell. This ticket is about the session itself and the server/push side.

### Corrections found in Phase 2 (verified)

- **A's JWT lives 8 hours server-side, not 30 days** — `be-hostelhive` `main` @ `be58f6b`, `app/controllers/concerns/jwt_authentication/expiry.rb:4` (`8.hours`); 30 days is only the `hh_auth_token` cookie's lifetime.
- **Push does not "carry over" to B in the harmful direction.** `/api/user/confirm_invitation` is a session path, so the exchange carries this device's FCM token (`core/interceptors/push-token-interceptor.ts:20-25,51`), and the backend's `issue_token` calls `Device.link(token, user)`, which re-points the device row at B (`app/models/device.rb:4-11`). After a successful switch A's pushes stop reaching the device. Web builds have no push token.
- **A 401 on `GET /api/users/current` clears the session before `establishSession` sees it**: that path is not in `CREDENTIAL_PATHS` (`core/interceptors/error-interceptor.ts:21-26, 44-48`), so `UNAUTHORIZED_HANDLER` → `session.clear()` (`core/auth/provide-auth.ts:24-28`) runs first.

## Root cause

**Status: hypothesised** — confirmed once a test fails before the fix and passes after it (Phase 5).

| | |
|---|---|
| **Symptom** | A network failure on a confirmation link signs out whoever was already signed in; an A → B switch neither revokes A's token nor rotates push. |
| **Cause** | `core/auth/auth.service.ts:236-239` — `establishSession`'s `catchError` calls `session.clear()` whatever the error. `setAccessToken(B)` (`:231`) only replaced the in-memory token (`session-store.ts:61-65`); `clear()` (`:67-72`) then deletes A's `hh_auth_token` cookie and `hh.auth.user` cache too. The `catchError` dates from the initial commit `24ceaad`; `c079248` introduced "only a 401 ends a session" for `restoreSession` and `hydrateInBackground` and missed this private third path, whose docstring (`:226-228`, "never sit in a half-authed state") reads like a deliberate rule. |
| **Why it escaped** | A service unit test would have caught it. `auth.service.spec.ts` pins the rule at `restoreSession` (`:76-108`) and `signIn` (`:110-133`) only; its `AuthApi` mock has no `confirmInvitation`, and `ConfirmInvitation` has no spec. The KB's evidence line ("pins the rule at both call sites") never counted the third. |
| **Same shape elsewhere?** | `hydrateInBackground` applies the rule correctly. Two adjacent findings, not this ticket: a re-sign-in over A that fails non-401 would leave A's user with B's in-memory token (sign-in is not offered to signed-in users, so probably unreachable); `restoreSession`'s background `.then(setSession(cachedUser, token))` (`:164`) can put A back over B if it resolves after a confirmation succeeds. |

## Plan

**Part 1 — fixed here** (`establishSession`):
- Remember the previous in-memory token before seating B's (`const previousToken = this.session.accessToken()`).
- On a 401: `session.clear()` (the interceptor has already done so; repeating it is harmless and is what a spec mocking `AuthApi` can observe).
- On any other error: if the session still holds B's token, put the previous token back (`setAccessToken(previousToken)`). A's user, cookie and cache were never touched, so A is fully restored; with nobody signed in this returns to token `null`. The `=== token` guard leaves the session alone if something else changed it meanwhile.
- Re-throw so the page shows its error; fix the stale docstring.

**Part 2 — see the 2d decisions** (both specialists recommend #125).

**Tests** in `core/auth/auth.service.spec.ts` (add `confirmInvitation` to the `AuthApi` mock): S0 / SA × status 0, 500, 401; the exchange failing (nothing touched); success (B seated and persisted). SA × status 0 should fail on today's code.

### Principal Engineer report (condensed)

> Recommend fixing part 1 here with a one-line restore using an existing API, and moving part 2 to #125: doing it here would mean changing three interceptors and the API client for a hygiene revoke.
>
> **Part 1 table.** Exchange POST fails: nothing touched in either starting state (but the POST already carried the device's FCM headers). `currentUser` 401: tokenless in both; the interceptor already wiped A; do not try to bring A back (undoing an interceptor's clear for a freshly minted token that comes back 401, which points to a server fault). `currentUser` 0/5xx: S0 → token `null`, B's invitation spent and B's JWT dropped; SA → A fully back (user never changed, token restored, cookie and cache never touched). Error re-thrown in every case.
>
> **Part 2 options.** (a) Revoke A and rotate before the exchange = `signOut()` then confirm = #125's Continue: the only push-correct ordering (rotate nulls token and registration synchronously, so the confirm POST goes out without push headers), but A is lost if B then fails, acceptable only by user choice. (b) Revoke A after B validates: needs A's token on the DELETE while B is seated. `ApiClient.delete` takes no context (`core/api-resource.ts:48-49`), `authInterceptor` always sets B's bearer (`auth-interceptor.ts:15-19`), and a 401 on that DELETE would clear B's new session. Making it work needs a bearer-override `HttpContextToken`, an interceptor exemption, a context param on `ApiClient.delete` and `AuthApi.signOut(token?)`; and rotating afterwards kills the registration the backend just tied to B. (c) Rotate only, after the switch: loses the race. If #125 lands this path never sees A, except a token-only restore still unresolved after the 8 s race (`user()` null, `accessToken` set), so #125's check should test `session.accessToken()`. After a switch A's JWT exists nowhere on the client, so not revoking it is hygiene, not exposure.
>
> **Risks.** `ConfirmInvitation` starts the exchange from `afterNextRender` (`confirm-invitation.ts:44`), which project memory says can be dropped in this zoneless app; verify before trusting manual QA. The `restoreSession` race (above) is out of scope. Error copy after a spent link ("try again" when a retry will fail) is a follow-up.

### Product Manager report (condensed)

> **Corrections:** 8 h not 30 days; push is re-linked to B at `issue_token`; the interceptor clears on a 401 before `establishSession` (all verified above).
>
> **Harm.** S0 (a new user on a weak connection): clearing is harmless, the message is the harm. SA (a host opening a staff member's confirmation link on their own device: `Staff` creates a `User` and that emails the link, `staff.rb:37`, `user.rb:36,53`; shared front-desk PCs): A is signed out by a blip; `clear()` drops A's cookie without revoking; the device row already points at B. A's JWT after a successful switch is stored nowhere on the device; exposure is a copy taken earlier (cookie not httpOnly). **The real push risk is restoring A after B's exchange succeeded: the device row belongs to B, so B's pushes would show on a phone signed in as A.** Rotate push on that path. **Rotating after seating B is harmful** (deletes B's linked token).
>
> **The page today.** The link is single-use (the invite is destroyed, `sessions_controller.rb:32`); reopening a used link → 500. An expired invite for an active user returns no token, so the page shows the developer string "Auth response did not include a token.". A 403 body has no message, so the page likely shows Angular's "Http failure response for http://…/api/user/confirm_invitation: 403", exposing the API URL (`confirm-invitation.ts:61` shows `err.message`, against `util/models/api-error.ts:12-16`). After a successful exchange with a failed `currentUser`, the page says "Confirmation failed" though the account **is** confirmed; it should say "Your account is confirmed. We couldn't finish signing you in. Please log in."
>
> **Acceptance (abridged).** S0/SA success → B seated, `/`. Exchange fails → S0 stays signed out, SA keeps A, unrevoked; copy never shows an API URL or developer string. Exchange OK + `currentUser` 0/5xx → S0 nothing persisted; SA A restored (memory token back, cookie/cache untouched), A not revoked, push rotated on native; page says confirmed + Log in. Exchange OK + 401 → S0 empty; SA ideally A kept (needs `UNAUTHORIZED_HANDLER` skipped for that one request, R1; accept clearing if too invasive, since a freshly minted token getting 401 is near impossible).
>
> **Scope.** Fix part 1 here; part 2 via #125's Continue (`signOut()` then confirm: revoke with A's token, rotate before the exchange so the new FCM token is linked to B). Optional safety net here: revoke A after B is confirmed, carrying A's token explicitly, no rotate. Out of scope: ask-first UI, translating the page's hard-coded English (unless the copy is touched anyway), the backend 500 on a used link.

**State at hand-off:** branch `fix/124-establish-session` on `origin/main` @ `da7197f` (main has since moved to `f7cd2c7`, docs only, no overlap), uncommitted; full web suite 2286/2286 green; lint 0 errors at the 107-warning baseline; i18n-check clean; M1 and part of M3 browser-verified; the confirmed state and native push not browser-verified; awaiting the delivery gate.

**Area:** auth and session — **account confirmation link** (`/confirm_invitation`, `features/auth/confirm-invitation/`), `AuthService.confirmInvitation` / `establishSession` (`core/auth/auth.service.ts`), `AuthApi.currentUser` (`services/auth-api.ts`, **extended** with an opt-in to suppress the global error toast), endpoints `POST /api/user/confirm_invitation` and `GET /api/users/current`; i18n `authConfirmInvitation.*` in 18 locales.

**What changed:**
- **Only a 401 ends the session on the confirmation path.** Any other failure after B's token is issued puts back whatever session was there (A fully restored; nobody signed in → tokenless), guarded so a session changed meanwhile is left alone; on native, push is rotated when A is restored, because the backend already re-linked the device to B.
- **The page tells the two failures apart.** A failure after a successful exchange arrives as `AccountConfirmedNotSignedIn`; the page says "Your account is confirmed" with **Go to log in**, or "You're still signed in as {name}" with **Back to home**. Link failures show translated copy only — never `err.message` (which could carry the API URL or a developer string). No global toast over that page (D8).
- **Part 2 of the card (revoke A's token, rotate push on an A → B switch) moved to #125** (D2), with comments on both cards.

**Who ran:** `principal-engineer` + `product-manager`; one `frontend-staff-engineer` (strong model; sent back twice — German register, then D8); `senior-qa` (matrix on the strong model; two parallel test batches on the cheaper one, one per file); `qa-reviewer`.

**Root cause — confirmed:** S1, S2, S6, S10 fail on the pre-fix `auth.service.ts` (8 cases) and pass with the fix.

**Tests:** S1–S12 in `auth.service.spec.ts`, C1–C8 in the new `confirm-invitation.spec.ts`, A1 in the new `auth-api.spec.ts`; every automated row claimed by exactly one batch.

**Change surface:** rows 1–8 `done`. Drift: rows 7–8 (`auth-api.ts` and its spec) were **undeclared** at 2e — added by the 5d toast decision (D8).

**Follow-ups:** the `restoreSession` background write can put A back over B if it resolves after a confirmation (D7, not filed); the backend answers 500 for an unknown or already-used confirmation token (`sessions_controller.rb:32`, `nil.expired_at`) — worth a BE card; ur.json mixes two spellings of sign in / log in (16 vs 9 on `origin/main`).
