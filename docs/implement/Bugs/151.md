### The ticket

`util/models/api-error.ts` says `ApiError.message` can be Angular's synthetic text with the API origin and path, and must never reach a user. But `error-interceptor.ts` fills `message` with the server's text "because several screens render `err.message` inline", and these screens do. The result is untranslated English, or Angular's "Http failure response for http://…" with the API URL.

**Fix (card):**
- per screen, show translated copy by status, or `toToastCopy` / `serverMessages` where the server's wording really is the best text;
- never show `err.message`;
- then decide whether the interceptor should stop putting server text into `message` at all.

**Acceptance:**
- none of the listed screens renders `err.message`;
- no API URL can reach the DOM, with a spec per screen.

## Root cause

**Status: hypothesised.** The code paths are confirmed by reading; the URL leaks are code-proven but not reproduced live.

| | |
|---|---|
| **Symptom** | Seven screens show untranslated backend English ("User not found", "Bookings cannot be cancelled within 3 days of check-in"), developer strings ("Cannot reach the server — is the API running?", "booking X not in response", "Upload failed: 403"), and in places Angular's "Http failure response for http://(api)/api/...: 403 Forbidden". |
| **Cause** | Each site renders `.message` of whatever was thrown: `lead-wall.ts:305`, `booking-form-drawer.ts:148` and `:354`, `staff-form-drawer.ts:167`, `listing-detail.ts:429`, `booking-detail.ts:273`, `booking-edit.ts:253`. The interceptor deliberately fills `ApiError.message` with server text (`error-interceptor.ts:273-279`), so it looks like display copy; and every plain `Error` thrown by a mapper or service also has a `.message`. The type cannot say which values are safe to show. |
| **Why it escaped** | No component spec threw an error with an Angular-style URL `message` and no `serverMessages` (the C3 no-leak pattern in `confirm-invitation.spec.ts`). Worse, `booking-detail.spec.ts:334-346` and `booking-edit.spec.ts:167-178` assert that the raw message is shown. `lead-wall` has no error specs, and the two drawers have no spec at all. |
| **Same shape elsewhere?** | Rows 2 and 3 belong to #83, whose uncommitted work adds two more: `host/bookings/bookings.ts:621` (`hostBookings.invoiceNotPaid` with a message parameter) and `host/invoices/invoices.ts:1169`. Code-proven URL leaks: the sign-in "no roles" 403 (nested array, so no `serverMessages`) and the drawer's `hostel_detail` 404 (Rails HTML). |

## Plan

**The rule, the same at every site:**
- never render `message`, from any error type;
- a recognised backend refusal gets translated per-case copy;
- status 0 gets `common.cannotReachTheServer`;
- anything else gets the site's translated generic message;
- `serverMessages` is shown verbatim nowhere here (that remains billing's rule only).

**One shared helper:** `util/booking-refusal.ts`, which recognises the `Booking` model's 422 texts. It is used at 4 sites (host save, guest create, update, cancel), and checks in a fixed priority: closed, no longer changeable, within cutoff, check-in in the past, dates out of order, room not bookable.

**Per-feature classifiers:**
- `lead-wall/auth-failure.ts`;
- host `booking-save-failure.ts`;
- public `booking-failure.ts`;
- user `booking-change-failure.ts`;
- the staff upload handled inline.

Signals hold keys; templates translate them through the pipe.

**Toasts:** suppressed on guest create, update and cancel, with `SUPPRESS_ERROR_TOAST` written inline as the call's context. The host create call stays as it is, because `host-bookings-api.ts` is #83's file.

**Specs:** each site gets one that throws a URL-bearing `ApiError` and a plain `Error`, and asserts neither reaches the DOM. The two existing specs that assert the leak are rewritten.

**Translations:** about 25 keys in 18 locales, with a parity spec. Keys go into the middle of `hostBookings`, not at its end, where #83 is appending.

**Not touched:**
- the interceptor and `ApiError`, `api-resource.ts`;
- `host-bookings-api.ts`, `booking-details-panel.ts` and `bookings.ts`;
- `services/hostels-api.ts` and `image-upload.service.ts`;
- the lead wall's English validation strings and tab labels (follow-up).

### Principal Engineer report (condensed)

- **Backend answers, per call:**
  - **Sign-in:** 404 "User not found" (unknown email), 401 "Invalid email or password", 403 nested "no roles" (which shows the URL), 429.
  - **Sign-up:** 422 messages, mostly "Email is already registered", and 429.
  - **Google login:** 404 "User does not exist" (Google rejected the token), 422, 429, or a plain error with no status from the popup.
  - **`hostel_detail` for an unknown id:** an unrescued not-found error, so an HTML or bare 404 (URL leak).
  - **Host create:** 400 subscribe (already handled), 403 `crm_required`, 422 "does not accept bookings", and the `Booking` model 422s, including "Checkin date cannot be in the past" for a host recording yesterday's walk-in.
  - **Guest create:** 404, 422 closed, the same model 422s, 401 handled by the session.
  - **Guest update and cancel:** 404, 422 "can no longer be updated/cancelled", "within 3 days of check-in".
  - **Presigned upload:** 422 "Content Type not supported", and the S3 upload's plain errors.
  - **No capacity check exists**, so the "only 2 left" comment at `listing-detail.ts:425` is wrong.
- **Recommends:**
  - one neutral sign-in message for the 401 and a non-bare 404;
  - an interceptor change as a follow-up card gated on #83 merging;
  - an optional source-scan guard spec with a two-line allowlist;
  - a seven-task decomposition, with T0 (shared helper and locales) first.

### Product Manager report (condensed)

- **Impact per site:** sign-in reveals accounts ("User not found"); guest booking shows a pinned English toast on top of the inline error, which defeats the fix unless the toast is suppressed.
- **Kinds and English copy per site:** sign-in `invalidCredentials`, the same for 401 and 404; `emailTaken` for sign-up; a Google message; host save `crmRequired`, `notAccepting`, `pastCheckIn`, `roomUnavailable`; guest `notAccepting`, `pastCheckIn`, `roomUnavailable`; cancel and edit reuse `userBookings.withinCutoff` and `noLongerEditable`.
- **Acceptance criteria:** G1–G5, L1–L8, R1, H1–H4, S1–S2, B1–B6, C1–C3, E1–E3.
- **Risks:** toast duplication, losing specific reasons (degrades to generic), the room name being dropped, hosts unable to backdate (a backend product question), enumeration remaining at API level.
