### #171 (as written)

> Price sorts are withdrawn under "Any type" because `starting_price` mixes nightly (backpacker) and monthly prices. Every control now respects that: the inline Sort dropdown, the Filters modal (#112), Apply, the header bar, and a new search from a landing page.
>
> But a URL that already carries one is not checked. `SearchMap.query()` (`search-map.ts` ~427-433) passes `?sort=price-asc` with no `gender` straight to `ListingsApi.list`, which sends `sort[starting_price]` (`listings-api.ts` ~387). So a shared link, a bookmark or a hand-typed URL like `/en/search/lahore?sort=price-asc` is ranked over mixed cycles. On that page the inline Sort dropdown shows its placeholder, because the value isn't one of its options, and the Filters badge still counts the sort.
>
> **Acceptance:**
> - A search URL with a price sort and no accommodation type sends no price sort to the API (treated as Recommended).
> - The Filters badge does not count it.
> - A URL with a type and a price sort is unchanged (still price-sorted).
> - Use the shared `isPriceSort` from `search-sort.ts` (added by #112).

### What the code shows

- **Exactly three readers of `sort`:**
  - `SearchMap.sort` (`search-map.ts:285`), which feeds `query()` (`:428`) and so the API;
  - `SearchFilters.sort` (`search-filters.ts:147`), which feeds `hasActiveFilters` (`:164`), `activeFilterCount` (`:175`), the inline dropdown's value (`search-filters.html:54`) and the modal's seed (`:214`);
  - `SearchBar.activeSort` (`search-bar.ts:229`), which reads the URL directly and already strips a price sort when submitting with no accommodation (`:390`).
- **Both search readers go through `mergeSearchParams`** (`search-params.ts:29`), "the one reader" both the request and the filter row use. It already treats an unknown `gender` as absent so the two can't disagree.
- **The type in force** is the query's `gender` when valid, else the seed's (a gender landing page). So `/hostels/lahore/girls?sort=price-asc` has a type and is legitimate. `/en/search/lahore?sort=price-asc` and `/en/hostels/lahore?sort=price-asc` do not.

### Understanding

**What has to happen:** a price sort that no type in force can justify must be read as absent everywhere the search reads filters:
- the request sends no `sort`, which means Recommended;
- the badge and the "Clear" state don't count it;
- the inline dropdown shows Recommended rather than a placeholder;
- the modal opens on Recommended.

A URL whose type is in force, whether from the query or a gender landing page's seed, keeps its price sort.

### What we already decided in this area

- **The price-sort rule has one home:** `search-sort.ts` (`isPriceSort`, `sortsFor`). No new `startsWith('price-')` (#112, D3).
- **`mergeSearchParams` is the one place filter values are corrected on the way in** (the `gender` precedent). Controls never read the route themselves.
- **The modal's `effectiveSort`** shows and applies Recommended while the type is "Any". `onApply` keeps a backstop (#112, D2/D8/D9).
- **GA** skips same-page `replaceUrl` navigations (rule A, `area/ssr-seo-and-prerender.md`). Any URL rewrite added here must be one of those or it counts a page view.

**Assumptions:** none blocking. The open question for 2d is whether the stale `sort` should also be removed from the URL, or only read as absent.

**Corrections from Phase 2:**
- **There is a fourth reader:** `SearchMap.startSearch` reads `params().get('sort')` (`search-map.ts:1626, 1637`).
- **The inline Sort pill never reads "Recommended".** Untouched, it reads "Sort", untinted, with Recommended highlighted inside. On a stale URL it is *tinted* and reads "Sort", with nothing highlighted (`dropdown.ts:628, 636-641, 701-704`).
- **Today, picking a type in the modal brings the stale price sort back** (the seed carries `price-asc` and `draftSort` keeps it, #112 D2).

## Plan

### Merged plan

**One engineer, one strict chain** (~40 lines): the predicate, then the reader, then the map.

1. **`search-sort.ts`:** add `isSortOffered(sort, type)` built on `sortsFor`/`isPriceSort`, so the rule keeps one home and no new `startsWith('price-')` is written. Broad or narrow is D2.
2. **`search-params.ts` · `mergeSearchParams`:**
   - work out the type in force: a valid query `gender`, else a valid seed gender, else `'all'`;
   - discard a `sort` the type doesn't offer, in the query and, for completeness, in the seed;
   - keep the identity return when nothing is corrected;
   - exclude the discarded sort from `get`, `has`, `getAll` and `keys`;
   - update the doc comment ("`gender` is the one key checked" is no longer true).
3. **`search-map.ts`:**
   - add a `discardedSort` computed (`raw query has sort && raw ≠ params().get('sort')`);
   - `startSearch` writes `sort: null` exactly when `discardedSort()`. Otherwise the merge carries the raw stale sort into the new URL, and `search-map.spec` `:424`, `:661` and `:996` go red;
   - drop the now-unused `isPriceSort` import;
   - **(D1)** add a browser-only effect on `discardedSort()` that navigates `[]` with `{sort: null}`, `merge`, `replaceUrl: true`, wrapped in `untracked`. It can't loop, because after the write `discardedSort()` is false. It also cleans a Back/Forward into an old stale entry.
4. **No change** to `search-filters.ts`, `search-bar.ts` or the modal. They read `params()`, or are correct once the URL is clean.

**Settled from the code (PE and PM agree):**
- **Rejected alternatives:**
  - a per-consumer `effectiveSort` helper (that is #112's root cause again);
  - normalising in SearchMap only (the badge still counts the sort);
  - a guard in `ListingsApi` (request only; a fifth copy of the rule);
  - a route-guard redirect (it would teach search the landing URL scheme).
- **No hint text** (#112 D5).
- **No SEO effect:** `hasFilters` ignores sort (`search-map.ts:276-281`).
- **A bad `gender` stays dormant** in the URL: it can never come back to life.
