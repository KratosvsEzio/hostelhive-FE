### The ticket

Today `/confirm_invitation` spends the emailed one-time token straight away and signs the invited account in, silently replacing whoever is already signed in on that browser — common on shared front-desk PCs.

**Wanted.** When someone is already signed in, ask before using the token: **"You're signed in as <A's name or email>. Continue and sign out of that account to activate the new one?"**
- **Continue** → run the real `AuthService.signOut()` (revoke + push rotation), then confirm the token, then land on `/` as the new account.
- **Stay signed in** → go to `/` as A; the token is **not** spent, so the link still works later.
- Nobody signed in → today's behaviour, unchanged.

The page can only name A (the token is opaque until exchanged). New strings through Transloco in all locales.

**Acceptance:**
- Signed in as A, opening a confirmation link sends nothing until A chooses.
- Continue: A's token revoked, push rotated, B signed in, host console shows only B's data.
- Stay: A still signed in; the same link still confirms B later.

**Card comment (2026-10-11, from #124):** this card owns "after a confirmation link switches from A to B, A's token is revoked and push has been rotated". `signOut()` must run **before** the `confirm_invitation` POST, so the fresh FCM token travels with the exchange. "Someone is signed in" should test `session.accessToken()`, not only `isAuthenticated()` (a token-only restore still pending after the 8 s cap has a token but no user). `afterNextRender` on this page needed checking.

### What we already decided in this area

- **#124 (merged):** the page has `verifying` / `confirmed` / `error` phases; post-exchange failures arrive as `AccountConfirmedNotSignedIn`; only a 401 ends a session on this path, otherwise the previous token is put back; copy is translated, never `err.message`; the follow-up lookup suppresses the global toast.
- **#124's browser check:** `afterNextRender` **does** fire on a fresh load of this routed page (one `POST /api/user/confirm_invitation` seen in Resource Timing). The card's "use `ngAfterViewInit`, not `afterNextRender`" predates that check; `afterNextRender` also keeps the token from being spent during SSR.
- **Backend facts (verified in #124):** a JWT lives 8 h server-side; `issue_token` re-links the device's push token to the new user (`Device.link`); an unknown or used confirmation token answers 500.
- **Per-user client state follows `SessionStore.user()?.id`** (#105, #114, #115, #123), so an A → B switch already clears per-user stores.

### Findings from Phase 2 (verified by the orchestrator on `be-hostelhive` `main` @ `7b8ff7f` and the FE)

- **The backend links a device's push token in one place only:** `sessions_controller.rb:113`, inside `issue_token` (`Device.link(request.headers["X-FCM-Token"], user)`). Nothing links on authenticated traffic. So `push-token-interceptor.ts`'s promise that "the first token rides authenticated traffic", and #124's QA line "A's next request re-links the rotated registration", are both false. After `signOut()` (which nulls the FCM token synchronously, `push-notifications.ts:192-196`) the confirm POST carries no push headers, and B is not linked on that device until B's next sign-in. This page is effectively web-only anyway — `AndroidManifest.xml` declares no app links, so the email link opens the browser.
- **The JWT carries its expiry as `expiry`, not `exp`:** `app/controllers/concerns/jwt_authentication/issuer.rb:6` (`payload = { id, email, phone, name, jti, expiry }`). The FE's `jwtExpiresAt` reads only `exp` (`core/auth/jwt.ts:44-47`), so `isJwtExpired` can never retire a token locally — every stale session goes to the server and comes back 401. The payload also carries `name` and `email`.
- **A stale session is the common case here** (PM): a front-desk PC left signed in overnight still shows A by name (30-day cookie, cached user), but the server stopped accepting the token after 8 h. On load, `restoreSession`'s background validation gets a 401 and runs `session.clear()` + `navigateByUrl('/')` (`auth.service.ts:190-194`), destroying this page — B lands on home with no explanation.
- **A and B can be the same person** (PM): sign-in does not check the account is active (`sessions_controller.rb:7-12`), so the copy must not say "the new account".

## Plan (merged; open branches in 2d)

- **Page state machine** (`confirm-invitation.ts/.html`), decided once in `afterNextRender` (kept — it fired in #124's browser check, and `ngAfterViewInit` would run during SSR on this server-rendered route and spend the token there): no token in the query → error (before anything else); `session.accessToken() === null` → today's flow; otherwise → a new **`asking`** phase.
- **Continue** → latch (`phase` to `verifying` synchronously; one DELETE and one POST even on a double click) → a new `AuthService` method that runs `signOut()` then `confirmInvitation(token)` in order (pinned in the service spec) → success: `navigateByUrl('/', { replaceUrl: true })` so Back does not bring the spent link back; failure: #124's existing handling (A is already signed out, so "confirmed → please log in" or the error copy).
- **Stay** → a button with the same latch → `navigateByUrl('/')`; nothing sent.
- **`restoreSession` guard:** both late branches (`.then` write, 401 clear-and-navigate) act only if `session.accessToken() === token` — the same guard as `establishSession`. Closes #124's D7 and the Continue race.
- **`AuthApi.signOut({ inlineErrors })`** opt-in (mirrors #124's D8), used by this flow only, so a failed revoke does not toast over the page.
- **Copy:** new `authConfirmInvitation.*` keys in all 18 locales, register matched per file.
- **Tests:** service (order, failures, the guard), `auth-api.spec.ts` (the flag), page (decision table, buttons, latch, rewritten C5).

### Principal Engineer report (condensed)

> **State machine.** Phases `verifying | asking | confirmed | error`; SSR renders `verifying`. Decide once in `afterNextRender`: missing token → error first ("don't ask someone to give up their session for a link that cannot work"); no access token → today's flow; otherwise `asking`, latched. Test `accessToken()`, not `isAuthenticated()`: with a cached user, token and user are set synchronously in the initializer and validation runs in the background **under the startup veil** (`app.html:63-76`); token-only validated within 8 s → user set; token-only past the cap → token, no user; expired by `isJwtExpired` → already cleared. Name = computed `user()?.name || user()?.email || null`, so it fills in when a token-only restore resolves.
>
> **A cleared while asking → keep asking, never proceed on its own.** In practice the restore 401 and the header sign-out both navigate to `/` and destroy the page (link unspent); only the global `UNAUTHORIZED_HANDLER` clears in place. Proceeding automatically "would activate B on A's PC after A was shown a question"; a latched prompt is deterministic.
>
> **Guard `restoreSession` first.** The veil lifts after 6 s (`startup-gate.ts:10`) even with validation pending. If A clicks Continue then: signOut clears A, B is seated, then A's earlier validation returns — a 200 writes A's revoked token and user over B and persists them (`:186`); a 401 clears B and navigates home (`:193-194`). Guard both with `accessToken() === token`.
>
> **Continue** in `AuthService` (`signOut().pipe(switchMap(() => confirmInvitation(token)))`), because "revoke and rotate strictly before the POST" is a service rule. `replaceUrl` on success. DELETE 0/5xx: swallowed, but the global toast still shows — add `signOut({ inlineErrors })`. DELETE 401: the handler clears first, harmless. DELETE with no bearer: backend 500 (`sessions_controller.rb:68`, `Authorization.split` on nil) — the opt-in covers it.
>
> **Push.** The confirm POST carries no FCM token (rotate nulls it synchronously); the backend links only in `issue_token`; B is unlinked until the next sign-in. Don't build a wait-for-token step. Escalate separately: a first-time user who grants permission *after* signing in is never linked until their next sign-in.
>
> **Stay** as a latched button, not a bare `routerLink`. Leaving mid-Continue: no `takeUntilDestroyed` (finish seating B). **Token-only copy:** generic "Someone is already signed in on this device. Continue and sign out of that account to activate the new one?". Suggested keys: `alreadySignedIn`, `signedInAsAskToSwitch`, `someoneSignedInAskToSwitch`, `continue`, `staySignedIn`.
>
> **Memory correction:** the note that `ngAfterViewInit` "does not run on the server" is wrong — lifecycle hooks run during SSR.

### Product Manager report (condensed)

> **Who:** a confirmation email is sent only when a user is created inactive (`user.rb:36,53-55`). Main case: a host adds a manager by email (`staff.rb:29-50`) and the manager opens it on the hostel's front-desk PC where the host is signed in — A is the host, with billing and every property. Also self sign-ups on a shared browser, and the same person (sign-in before confirming). Not Google sign-ups (created active), not renter invites (link to `/auth`), not password resets. The link lasts **1 year** (`user_invite.rb:93`) though the email says 24 h; a used link → 500.
>
> **Copy:**
>
> | Key | English |
> |---|---|
> | `alreadySignedInTitle` | You're already signed in |
> | `signedInAsAccount` | You're signed in as {{account}}. To activate the account from this link, you'll be logged out first. |
> | `signedInToAnotherAccount` | You're signed in to another account. To activate the account from this link, you'll be logged out first. |
> | `linkStillWorksLater` | If you stay signed in, this link will still work later. |
> | `logOutAndContinue` (primary) | Log out and continue |
> | `staySignedIn` (secondary) | Stay signed in |
>
> "Log out" matches the account menu (`account.logOut`); "the account from this link", never "new account" (A may be B). `{{account}}` = "Name (email)" when both are known — two front-desk staff can share a first name; wrap it in Unicode isolates for RTL. Naming a token-only session: `user()` → `readPersistedUser()` → the JWT payload (`name`, `email`, `issuer.rb:6`; `jwt.ts` already decodes payloads, display only) → the no-name sentence.
>
> **Acceptance (abridged).** (1) Nobody signed in → unchanged. (2) A signed in → the ask, **no** POST and **no** DELETE until a button is pressed (check Resource Timing). (3) **The startup check settles before the ask is decided** — if A's cached session is still validating, keep "Confirming…" under the veil; on 401 carry on as signed-out, **not** redirected home; on 0/5xx A stands and the ask shows. (4) Log out and continue → button disables at once; DELETE with A's bearer; cookie and cache cleared; `rotate()`; only then one POST with no bearer; success → `/` as B; double-click → one DELETE, one POST. (5) Continue then the exchange fails → #124's error state with Go to log in (works now); A not restored — acceptable, the ask said A would be logged out. (6) Stay → `/` as A, nothing sent; the link works later. (7) A 401 while asking → the ask goes away and the page **carries on as signed-out**. (8) Reload during the ask → the ask again, nothing sent. (9) Mobile 320–360 px: stacked full-width buttons, Stay a real secondary button, long emails wrap, ≥ 44 px targets, RTL mirrors. (10) Keyboard: Tab order matches; **no autofocus** (a stray Enter must not log A out); focus moves to the `h1` (tabindex -1) when the ask appears; `aria-busy` while running; a page state, not a modal.
>
> **Rules:** only a 401 ends a session; push rotates on sign-out (Continue must use the real `signOut()`); translated copy, never `err.message`; no toast over this page (`AuthApi.signOut` has no suppression — add an opt-in). **Out of scope:** naming B before the exchange (needs a backend "peek invite"), the backend 500 on a used link, the 24 h vs 1 year email text, the missing `exp` claim (backend), native deep links, account-menu sign-out. **Follow-up:** a BE card for `exp`, the 500, and the email text.
