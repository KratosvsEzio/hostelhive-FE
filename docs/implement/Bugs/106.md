### The card

> On a gender landing page such as `/en/hostels/lahore/girls`, the results come from the landing route: `PlaceLanding` passes `gender` into the search. The filter bar, however, reads the accommodation type only from the URL's query string.
>
> **Result** — The bar shows "Any type" while the list is girls-only. Choosing "Any type" in the filter modal cannot remove the girls filter, because it was never in the query.
>
> **Fix** — Give the filter bar the landing page's preset as well. Then changing the accommodation from a landing page either moves to the matching sibling page (`/hostels/lahore`, `/hostels/lahore/boys`) or to `/search` with the new filter.
>
> **Acceptance**
> - On `/en/hostels/lahore/girls` the filter bar shows "Girls".
> - Choosing "Any type" or "Boys" changes the results to match.
> - The plain `/en/hostels/lahore` page is unchanged.

### Reproduction (2026-10-10, Chrome, `:4301`, branch at `origin/main`)

1. `/en/hostels/lahore/girls`: the request is `GET /public/hostels?…&f[gender_type]=girls&f[room_types.occupancy_type]=shared…`. The Filters button has **no count badge**. In the Filters modal, "Type of stay" has **"Any type"** selected (`bg-ink-900`); Girls is not.
2. In the modal, "Any type" → Show results: URL becomes `/en/hostels/lahore/girls?roomType=shared`. The search is unchanged (still `f[gender_type]=girls`). **Both symptoms confirmed.**

Where the accommodation type appears: it is **not** an inline control in the filter row (`search-filters.html` comment: it moved to the header bar). It appears in the **Filters modal** ("Type of stay"), in the **Filters badge count** (`activeFilterCount`), and through **Sort options** (price sorts are hidden while the type is "all"). The header search bar is not shown on landing pages.

### What we already decided in this area

- `seed` sits **under** query params (`SearchMap.params()`): "a visitor's own filter wins" (KB area, `search-map.ts:168-201`).
- Curated landing pages own their place intent and the `<head>`. Filtered searches are `noindex` (decision `curated-landing-pages-own-place-intent.md`).
- `/hostels/:place/:gender` serves gender segments **and** campus slugs; gender wins. Backpacker has **no** segment (`places.ts` `GENDER_SEGMENTS`).
- Price sort is withdrawn while the type is "All" (`search-filters.ts` `sortOptions`).

### Understanding

`SearchMap` merges the landing page's `seed` under the query string, so the **search** sees `gender=girls`. Its child `SearchFilters` reads `route.queryParamMap` directly, so **its** view of `gender` is empty. The modal gets seeded with `all`, the badge count misses the filter, and price sorts are hidden. Applying "all" writes `gender: null`, which removes nothing, so the seeded `girls` still applies.

## Root cause

**Status: confirmed** (2026-10-10) — TC-19/20/21 fail on `origin/main`'s implementation with the reported symptom (`…/girls?roomType=shared`, `…/girls?gender=boys&roomType=shared`) and pass on the branch. See QA results.

| | |
|---|---|
| **Symptom** | "The bar shows 'Any type' while the list is girls-only. Choosing 'Any type' in the filter modal cannot remove the girls filter, because it was never in the query." |
| **Cause** | Filter state has two readers, and only one knows about the seed. `SearchMap.params` merges `seed` under the query (`search-map.ts:187-203`). `SearchFilters` injects its own `route.queryParamMap` (`search-filters.ts:33-35`) and reads `gender` from it (`:103-105`), so its display, badge, sort options and modal pre-selection all fall back to `'all'`. On the write side, `onApply` can only say "Any type" as `gender: null` (`:203`). Under the merge, a missing key means "use the seed", so a seeded key can be overridden but never removed. Only a path change removes it. |
| **Why it escaped** | No component test of `SearchFilters`, `SearchMap` or `PlaceLanding` exists. The landing specs test pure functions only, and the e2e lane has one home-page test. A component test given a seed, or an e2e test on a gender landing page, would have caught it. `seed` was added (commit a9871a7) assuming "the filters come as they are". |
| **Same shape elsewhere?** | Yes — the seed can't be unset by a query merge anywhere. `searchEverywhere()` nulls place/lat/lng, and the seed brings them back (`search-map.ts:1476-1491`). `onPlaceSelected()` on a gender page keeps the seeded gender and the H1 (`:1422-1434`). The header `SearchBar` reads the raw query (`search-bar.ts:186-200`), but it is hidden on `/hostels/*` (`site-header.ts:86-91`). Related: `onApply` writes the default `roomType=shared` on every apply and has no price-sort guard (`SearchBar.search()` has one). |

## Plan

### Merged plan

1. **One reader of the URL.** `SearchMap` passes its merged `params()` to `SearchFilters` as an input. `SearchFilters` stops reading `queryParamMap` itself. The display, badge, sort options and modal pre-selection then follow the effective value.
2. **The landing page owns the landing URLs.** `PlaceLanding` computes, for a **gender** page only, the path each accommodation type lives at, and hands it down as plain data (`SearchMap` input → `SearchFilters` input). City pages, campus pages and `/search` pass nothing and keep today's query merge.
3. **`onApply` routes gender changes.** On a gender page, choosing a type with its own page goes to that sibling (`/hostels/c`, `/hostels/c/boys`, `/hostels/c/co-living`). It is one absolute navigation, localised with `localiseCommands`, using `queryParamsHandling: 'merge'` (other filters and the viewport kept) and `gender: null`. Backpacker is decided in 2d. With no gender change, it stays on the current path.
4. **Two tidy-ups in `onApply`.** Strip a `price-*` sort when the result is "Any type" (matching `SearchBar.search()`). Write the default room type as `null`, not `shared`.
5. **Tests.** Component spec for `SearchFilters`, unit specs for the pure helpers, and a Playwright regression on `/en/hostels/lahore/girls` (stubbed API).

## Summary

**Area:** search-and-discovery: gender landing pages (`/hostels/:place/:gender`), the search filter row (`SearchFilters`), the Filters modal, `SearchMap`'s seed merge.

**State at hand-off:**
- branch `fix/106-landing-gender-filter`, uncommitted, all green (1631 unit, 5 e2e, lint 0 errors, build OK);
- root cause **confirmed** (red on main, green on the branch);
- left: delivery (commit, push, PR), follow-up cards, and the knowledge-base entry after the merge.

**What changed:**
- `SearchMap` is the only reader of filter state, and `SearchFilters` now gets its merged `params` as an input, so the modal pre-selection, the badge and the sort options follow the landing page's preset.
- On a **gender** landing page, changing the type in the Filters modal goes to the page for that type: Any type → `/hostels/<place>`; Boys/Girls/Co-living → the sibling page; Backpacker → `/hostels/<place>?gender=backpacker`. Other filters and the locale are kept.
- City pages, campus pages and `/search` keep the query filter as before.
- The merge moved into a pure `mergeSearchParams`. It ignores an unknown or empty `gender`, so a malformed link falls back to the page's type.
- `onApply` no longer writes `roomType=shared`, and drops a price sort on "Any type".

**Components touched:**
- **extended:**
  - `SearchFilters` (`params` and `genderRoutes` inputs, routed apply);
  - `SearchMap` (`genderRoutes` input, `params` exposed);
  - `PlaceLanding` (`genderRoutes`);
  - `SearchFilterModal` template (`aria-pressed`).
- **new:**
  - `landing/gender-routes.ts` (`genderRoutesFor`);
  - `search/search-params.ts` (`mergeSearchParams`, `isAccommodationType`).

No API or endpoint change; `GET /public/hostels` gets the same `f[gender_type]` contract.

**Routing:** a single `frontend-staff-engineer` (6 tightly coupled files), sent back twice for fix rounds (the 5d crash, then D11). `senior-qa` wrote the tests in 2 batches, plus 3 small additions. `qa-reviewer` did 3 independent rounds.

**Change surface:** rows 1–9 done. Undeclared, added during QA: `search/search-params.ts` (new, D11), `search/search-params.spec.ts` (TC-26). That drift came from a decision made in QA (D11), not from a gap in the plan. No rows dropped.

**Coverage:** TC-01–27; automated 01–21 and 24–27; TC-22/23 manual (M1–M4 above).

**Browser:** verified in Chrome on `:4301` for girls, boys, co-living, backpacker, Any type, city, campus, `/ur` and a bad `?gender=`. Result lists were not seen (API 503); request URLs are the evidence.

**Follow-ups (cards drafted, pending the user's approval):**
1. "Search everywhere" does not widen on `/hostels/*` pages: the seed restores `place/lat/lng` (`search-map.ts` `searchEverywhere`).
2. Picking another place in the mobile place field on `/hostels/lahore/girls` keeps the girls filter and the Lahore H1; the `place/lat/lng` override is then carried by sibling navigation (`onPlaceSelected`).
3. The header `SearchBar` reads and re-writes the raw `?gender=` (`search-bar.ts:198,286`), so a bad value is re-submitted from `/search`.
4. The Filters modal offers price sorts under "Any type", and Apply now drops them silently (already a KB trap).
5. The modal's type labels ("Any type", "Boys", …) are hard-coded English.
