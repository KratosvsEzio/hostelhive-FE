### The ticket

`FavoritesStore` keeps saved hostels in localStorage (`hh:favorites`). Hearts on listing cards, the search map and the listing page read it. Toggling calls `markFavourite` / `unmarkFavourite`, but:
- the store is never loaded from the server (only the Favourites page calls `GET /api/favourites`), so another device shows the wrong hearts;
- it is never cleared on sign-out (`clear()` has no callers), so the next user on the browser sees the previous user's hearts;
- write failures are not reconciled — the heart flips and stays flipped.

**Fix:** after sign-in and session restore, fill the store from `GET /api/favourites` (server is the source of truth); clear it on sign-out; roll back the local toggle when the mark or unmark call fails.

**Acceptance:**
- A hostel saved on device A shows a filled heart on device B after sign-in.
- Signing out empties the hearts; signing in as another user shows only their favourites.
- A failed save reverts the heart.

### What the code shows

- `FavouritesApi.markFavourite` / `unmarkFavourite` end in `catchError(() => of(null))` (`services/favourites-api.ts:33-43`), so a failure is indistinguishable from success — the store *cannot* roll back until that is removed.
- Session changes all go through `SessionStore` signals (`setSession`, `clear`): sign-in (`hydrateInBackground`), Google, invitation, `restoreSession` (optimistic cached user, then validated), `signOut`, and the 401 handler (`session.clear()`). Keying the store off `SessionStore.user()?.id` catches every one of them, including a 401-forced sign-out, without touching `AuthService`.
- Consumers: `listing-card.ts:216` (`toggleSaved`), `search-map.ts:738` (card heart) and `search-map.ts:1287-1291` (imperative popup heart that paints the return value of `toggle()` once — it would not repaint on rollback), `listing-detail.ts:431` (guests sent to `/auth?mode=login`), `features/user/favorites/favorites.ts:71` (confirm-then-unmark; does not restore the row on failure).
- The error interceptor toasts any failed request unless `SUPPRESS_ERROR_TOAST` is set — so a failed save will already announce itself once the `catchError` is gone.
- KB trap: signed-out hearts on search cards and map popups save locally and fire a write that fails; only the listing page sends guests to `/auth`.

### What we already decided in this area

- *Only a 401 ends a session* (KB decision, auth-and-session).
- Listing page: favouriting while signed out sends the guest to the Log in tab with `returnUrl` (comment "B3" in `listing-detail.ts`).

## Plan

### Merged plan

1. **`services/favourites-api.ts`** — delete both `catchError`s; `listFavourites({ quiet })` sends `SUPPRESS_ERROR_TOAST`.
2. **`util/favorites-store.ts`** (rewrite) — inject `SessionStore`; state `{ owner, items }` in one signal; owner-scoped cache read synchronously in the constructor (legacy bare-array cache discarded); effect on `computed(user()?.id)` — id change resets to empty + loads (browser only), same id does nothing; load merges in-flight toggles; optimistic `toggle` with a per-hostel in-flight lock and rollback on error (ignored if the owner changed meanwhile); `unsave(listing): Observable` for the Favourites page; signed-out toggle is a no-op; persist effect writes `{owner, items}` or removes the key when signed out.
3. **`search-map.ts`** — popup heart repaints from an effect on the store; signed-out handling on the map card and popup.
4. **`listing-card.ts`** — signed-out handling (also covers the home page cards, which use `hh-listing-card`).
5. **`features/user/favorites/favorites.ts`** — `confirmRemove` goes through `favorites.unsave` and restores the row on failure.
6. **Specs** — store spec (cause-confirming tests first), API spec.

Untouched: `core/auth/*`, `error-interceptor.ts`, `listing-detail.ts` (already redirects guests; reactive).

`POST /api/favourites/mark_as_favourite` → 401, `DELETE /api/favourites/mark_as_unfavourite` → 401, `POST /api/favourites/nope` → 404. Both write routes exist; the PE's possible blocker is cleared.

### Principal Engineer report

Agrees with the session-keyed effect, keyed on `user()?.id` not the object (restore confirmation and `refreshSession` re-set the same user). The owner-scoped cache is the essential part: the store is lazily instantiated, so an effect alone cannot clear a sign-out that happened before the store existed; the owner check must be synchronous in the constructor because a root effect's first run is scheduled. Replace an ordering guard with a per-hostel in-flight lock (backend behaviour for unmark-of-unsaved is unknown). Background load quiet and cache-preserving; a 401 still signs out. Popup heart must repaint from an effect (a server load can change it too); do not rebuild the card (restarts its entry animation). Also: merge load with in-flight toggles; unsubscribe a load on user change; discard legacy bare-array caches; dev `?role=` seed will now get a 401 from the load on public pages (dev-only, accept + comment). Recommends **one engineer, sequential** — T1 (API + store + specs) is ~80% of the work. Full report in the session transcript; edge-case list folded into the merged plan above.

### Staff Engineer report (frontend)

- **`services/favourites-api.ts`** — both `catchError(() => of(null))` removed; `listFavourites({ quiet })` sends `SUPPRESS_ERROR_TOAST` via `ApiClient.get`'s context arg. A quiet load still lets a 401 reach the session handler (the interceptor checks 401 before the toast flag).
- **`util/favorites-store.ts`** (rewrite) — one `{ owner, items }` signal; synchronous owner-matched cache read in the constructor (legacy array / bad JSON / other owner → empty; signed out → key removed); persist effect writes `{owner, items}` or removes the key; session effect on `user()?.id` → `syncOwner()` then `load(id)` (browser only, once per owner via `loadedFor`); `syncOwner()` bumps an `epoch`, clears pending, cancels the load, resets to empty; `load()` is quiet, ignores results for a changed owner, merges pending writes, keeps items on error; `write()` is optimistic + pending lock + `AsyncSubject` outcome (the request runs even if unsubscribed) + exact `restore()` on error within the same epoch. Public API: `items`, `count`, `isFavorite(id)`, `toggle(listing): boolean`, `unsave(listing): Observable<void>`. `add` / `remove` / `clear` deleted.
- **`listing-card.ts`** — guest → `/auth` `{ mode: 'login', returnUrl: router.url }` (covers home cards).
- **`search-map.ts`** — `redirectGuest()` for the map card heart and the popup heart; `popupHeart {id, paint}` set in `buildCard`, cleared in `renderSelection()` and `clearMarkers()`; a constructor effect on `favorites.items()` repaints in `untracked`.
- **`favorites.ts`** — `confirmRemove` → `favorites.unsave(item)`; on error the id leaves `_removed` so the row comes back in place.

Deviations: `toggle()` / `unsave()` call `syncOwner()` first so a click between a session change and the effect's run never lands on the previous user's list; `unsave` while locked or signed out returns `throwError` (no HTTP, no toast) so the page restores its row; Prettier applied only to the two rewritten files (the others were not Prettier-clean before; the repo has no format target).

### Staff Engineer report — TC-17 race fix (after the 4a gate)

The user approved fixing the matrix's TC-17 race in this ticket. One `frontend-staff-engineer` owning only `util/favorites-store.ts`, run alongside the 4e batches (no format/lint/test runs). It adds a `settled` map (hostel id → saved state) and a `loading` flag: a write that **succeeds** while a load is in flight is recorded in the map; failed writes never are. `load()` empties the map and sets `loading`; a new `endLoad()` clears both when the load finishes (success or error, including a response for a changed owner); `syncOwner()` clears both. `mergePending()` precedence: an in-flight write, then a write settled during the load, then the server list. The design differs from the brief in one way: the `Listing` for a save is not stored, because a hostel saved during a load is always still in the current list. Type-check `tsc --noEmit -p apps/web/tsconfig.app.json` exit 0. Edge cases handed to QA: save settles during the load → kept; unsave settles during the load → stays unsaved; settled save + in-flight unsave → absent; failed save during the load → absent; load fails → overlay cleared; write after the load → not recorded; owner switch → not carried over.

- Saves/unsaves are optimistic with an exact rollback on failure (one toast from the error interceptor), a per-hostel in-flight lock, a merge so a load never undoes an in-flight or just-settled write, and a quiet reload after any non-401 failure so the server settles the heart.
- `FavouritesApi` no longer swallows write errors.
- Guests clicking a heart on search cards, home cards, the map card or the map popup go to `/auth?mode=login&returnUrl=…` (as the listing page already did). The map popup heart repaints when the list changes.
