### The ticket

`isSubscriptionError` treats a 403 whose text says "not authorized" as a subscription problem. That text is CanCan's default for a **missing role permission** (`{ error: "You are not authorized to access this page." }`). The real plan refusal is `code: "crm_required"`, which the check doesn't match (its message "Your plan does not include CRM" matches none of the regexes). Its doc's "Pundit" note is stale.

**Effect:**
- a manager whose booking **create** is refused for permission gets the **plan-renewal prompt** in the booking drawer;
- the same misreading affects list loads in rooms, tenants, utilities, invoices and overview.

**Fix direction:**
- a plan refusal is `crm_required` (share `isCrmRequired`) or the 400 "need to subscribe";
- a 403 with no server code is a permission refusal (the #187 keys or a screen-appropriate equivalent), never the renewal prompt;
- fix the doc.

**Acceptance:**
- a permission 403 never opens the renewal prompt or reads as a plan problem;
- a real plan refusal still does;
- specs cover both on the drawer and one list load.

### What we already decided in this area

- **#187 D4:**
  - a 403 with `crm_required` (code or message) is a plan refusal;
  - a 403 with **no** server code (`'unknown_error'`) is a permission refusal;
  - any other coded 403 is generic;
  - `isCrmRequired` (`core/host-access/host-access.ts`) is the one plan check, shared with `classifyHostAccess`.
- **#187 D1:** the permission wording is split by role: `hostBookings.notAllowed` (staff, "ask the hostel owner") vs `notAllowedOwner` (owner, "contact HostelHive support").
- **#187 D2:** `hostBookings.planHasNoCrm`, "This hostel's plan doesn't include CRM."
- **Roles are global** and edited only by HostelHive admins.
- **The console's plan lock** (`<hh-access-lock>`) replaces the page on a recorded plan refusal.

## Root cause

**Status:** hypothesised; the unit spec asserts the defect (`subscription-error.spec.ts:27-29`), and it gets confirmed in Phase 5.

## Plan

1. **Shared rule** (`core/host-access/host-access.ts`): `isPermissionRefusal(err)` = 403, not `isCrmRequired`, and no server code (`code` missing, empty, non-string, or `'unknown_error'`). The `'unknown_error'` literal stays local with a comment, because importing it from the interceptor would create a cycle.
2. **`util/subscription-error.ts`:** **no 403 is a subscription error** (`if (status === 403) return false;` before the text match), covering both error shapes. 402 and the 400 "need to subscribe" text still count. The doc drops "Pundit".
3. **`booking-move-failure.ts`:** `forbiddenKey` uses `isPermissionRefusal`; delete its private `hasServerCode` / `NO_SERVER_CODE`. Behaviour is unchanged (the #187 specs guard it).
4. **Drawer:**
   - `bookingSaveFailureKey(err, opts)` uses `isCrmRequired` (→ `hostBookings.crmRequired`, now also on the message-only form), then `isPermissionRefusal` (→ `notAllowedOwner` / `notAllowed`);
   - `booking-form-drawer.ts` passes `{ owner: session.hasRole('host') }` at reply time;
   - the renewal branch then catches only the 400 / 402.
5. **Six list pages** (overview, rooms, tenants, utilities, add-bill, invoices):
   - an optional `permissionError` on each page's `ViewState`, set from `isPermissionRefusal` in `catchError` (`error` stays true);
   - a template branch showing a new shared `<hh-permission-refused>` (`layout/components/permission-refused/`): `<hh-error-state>` titled `coreForbidden.accessBlocked`, with a role-split body and **no Retry**.
6. **i18n:** per D2.
7. **KB:** `area/host-billing-and-subscription.md` (drop "a 403 on a plan-gated endpoint" and the "broad" trap; the lock owns plan refusals and the paywall is a backstop); `host-console.md` and `api-and-data.md` Reuse entries.

### Product Manager report (condensed)

- **Check order** means a CanCan 403 arrives only after the plan checks passed, so at that moment the plan is live and includes CRM. **The message isn't just aimed at the wrong person; it's false.**
- **Who:**
  - the **drawer Save is the main case**: Bookings has no `permissionGuard` and New booking has no flag, so any manager without create hits it on every save;
  - add-bill: the route checks only `UtilityBill:index`;

  - overview: a removed manager.
- **Impact:**
  - owners may buy or change a plan needlessly (money and trust);
  - managers can't renew, and the link leads to "Billing isn't available to you" (a dead end);
  - the drawer's Renew link closes the drawer, losing the walk-in's details;
  - the list toast contradicts the paywall.

    - header actions not disabled;
    - C → paywall backstop + lock;
    - 400 / 402 → paywall;
    - `forbidden` / 404 / 422 / 500 → generic with Retry; status 0 → network.

- **Rejected — "the drawer save still toasts the server's English text".** `HostBookingsApi.create` already sends `contextArgs({ suppressErrorToast: true })` (`host-bookings-api.ts:239`), so the interceptor never toasts a drawer save. That was already true before this change.

  - **Raw `HttpErrorResponse` with the CRM message and no code** reads as a permission refusal (`isCrmRequired` reads `serverMessages`, which only `ApiError` has). It's unreachable, because every request goes through the interceptor.

  - **Any codeless 403** (a proxy or WAF page) reads as a permission refusal, as #187 D4 already decided.
  - **An account holding `host` among several roles** gets the owner wording everywhere, as #187 D1 already decided.
  - **Overview's other panels** can each toast an English 403 GET when the role lacks them too. That is the out-of-scope GET toast (#194).
