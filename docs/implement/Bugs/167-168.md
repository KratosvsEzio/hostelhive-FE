### #167 — "Stayed in" on a cancelled booking labels every room "Checked out"

Seen live while verifying #83 (2026-10-11). A booking cancelled after check-in lists its rooms under "Stayed in", each labelled "Checked out" (`hostBookings.checkedOut`). The guest never checked out. Fix direction: label cancelled rows "Released" (or a neutral label); keep "Checked out" for checked-out bookings; add the key.

**Acceptance:** a cancelled booking's rows don't say "Checked out"; a checked-out booking's rows are unchanged; a spec covers both.

### #168 — "room already released" refusal doesn't mark the room released

Found in the #131 fix-forward. Release answering 422 "Occupancy is already inactive" shows `hostBookings.roomAlreadyReleased`, but the room stays drawn active with its Release button until the panel reopens. Fix direction: on `bookingRefusal(err) === 'roomAlreadyReleased'`, add the room to `releasedIds` and emit `released` so the page re-reads the booking. Keep the message.

**Acceptance:** after that refusal the row is struck through, says "Released", has no button; the list row's room line updates; a spec covers it.

### What we already decided in this area

- **Index lag:** list endpoints and `…/occupancies` read the search index; `GET bookings/:id` reads the database. Trust our own writes and the single read, never a re-fetched list. `releasedIds` exists for exactly this: released is final.
- **Refusals** show translated keys from `booking-move-failure.ts`; `message` is never read (#151/#159).
- **Release** opts out of the global toast and shows its error under the rooms.

### Synthesized understanding

Both bugs live in `features/host/bookings/booking-details-panel.*`.
- #167 is a template label: `stayHistory` covers lanes `checked-out` and `cancelled`, and the row label is hard-wired to `checkedOut`.
- #168 is the release `error` branch: it sets `releaseError` only. The server's "already inactive" is as final as a successful release, so the same bookkeeping as `next` applies.

**Cause of the implementation defect:** `linkedSignal` re-runs its computation whenever a signal its `source` function reads changes; it does not compare the source's old and new values. `source: () => this.booking()?.id ?? ''` reads `booking()`, so any booking swap resets `releaseError`, the same id included. `releasedIds` has the same latent flaw, masked because the re-read booking carries the room as inactive. The engineer's D4 comment claimed the opposite. **Fix:** a `computed` booking id as the source of both, since a computed only notifies when its value changes.
