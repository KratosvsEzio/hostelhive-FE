### The ticket

Some stay moves are refused because the booking already reached the requested state, or has moved on (another tab, or a stale index row). The panel shows a translated key telling the host to refresh and keeps the old state until they do. #168 fixed this for Release by counting the refusal as done and re-reading the booking.

- **Check in → `alreadyCheckedIn`** (`bookings.ts:747`, `assignError`; copy "…Refresh to see its rooms.").
- **Mark as paid → `alreadyPaid`** (`markPaid` `:645` via `send` `:539`; `bookingAlreadyPaid`).
- **Any move → `wrongStage` / `noLongerChangeable`** → `bookingHasMovedOn` ("…Refresh to see where it stands.").

**Fix direction:**
- keep the translated message;
- re-read the booking (`bookingsApi.get`) and swap it into the panel and the list (`replaceBooking`);
- if the re-read fails, refresh the list;
- reword the three keys in 18 locales;
- close a dialog whose move no longer applies.

**Acceptance:**
- check-in on an already-checked-in booking switches the panel to checked in with its rooms;
- mark-paid on an already-paid booking shows it paid;
- a wrong-stage refusal shows the real stage;
- other failures are unchanged and don't re-read;
- component and page specs cover each refusal.

### What we already decided in this area

- **#168 precedent:** an "already" refusal counts as done. The panel emits `released`, and `onReleased` re-reads via `GET bookings/:id` and swaps it into the list row (`replaceBooking`); a failed re-read refreshes the list. `onGenerateRefused` does the same for `invoiceExists` (closes the dialog, info toast, re-looks the invoice up).
- **Index lag:** trust `GET bookings/:id` and our own writes, never a re-fetched list.
- **Refusal copy:** comes from `booking-move-failure.ts` keys via `bookingRefusal`; never `message`.
- **`linkedSignal` trap:** per-booking panel state keys on the computed `bookingId`.

### Synthesized understanding

All stay moves go through `send` (`bookings.ts:534`), whose error branch only calls an `onError` that sets one of three messages:
- `viewError` (the panel footer, the default for confirm);
- `dialogError` (cancel, no-show, check-out, mark paid, invoice);
- `assignError` (the check-in panel).

Dialog moves hide the details panel behind the dialog (`panelBehindDialog`). So a re-read on refusal has to decide which surface shows the message, whether the dialog closes, and which booking the restored panel shows.

## Root cause

**Status:** hypothesised (read from the code; confirmed in Phase 5 when the specs fail before and pass after).

| | |
|---|---|
| **Symptom** | After a refusal saying the booking is already checked in or paid, or has moved on, the host sees "…Refresh to see…" and the screen keeps the old booking and buttons that can't work. |
| **Cause** | `send`'s error branch (`bookings.ts:562-566`) only calls `onError`, and every `onError` (`:539` `viewError`, `:600` `dialogError`, `:703` `onGenerateRefused`, `:747` `assignError`) only sets a message key. Only the success branch brings in a new copy. `bookingMoveFailureKey` keeps only the key, not the kind, so "the server's state differs" is never acted on. #168 and `invoiceExists` each re-classify on their own. |
| **Why it escaped** | The page-integration specs are at the right level, but four **assert the bug**: `bookings.spec.ts:420-436` (wrongStage invoice keeps the dialog), `:614-630` (mark-paid alreadyPaid keeps the modal, balance still due), `:854-873` (check-in alreadyCheckedIn/movedOn stay in the assign footer), `:1615-1629` (check-out wrongStage keeps the modal). They were written to prove no server text leaks, not the outcome. |
| **Same shape elsewhere?** | Confirm has no `suppressErrorToast` (`host-bookings-api.ts:248`), so a panel refusal shows twice and a row-menu one only as the raw-English global toast; but no confirm refusal matches these kinds today. The invoices page's cross-pay (`invoices.ts:1163-1173`) shows "booking already paid" as a sticky error. The calendar moves only on success. The success toasts are hard-coded English ("Checked in", "Room N × N"). |

## Plan

1. **`booking-move-failure.ts`:** add `isMovedOnRefusal(err)`, true for `alreadyCheckedIn`, `alreadyPaid`, `wrongStage` and `noLongerChangeable` only, next to `bookingMoveFailureKey`.
2. **`bookings.ts`:** in `send`'s error branch, on `isMovedOnRefusal`, call `onMovedOn(booking, err)` instead of `onError`.
   - The surface stays open with its key at first; `busy` holds and `epoch` bumps.
   - A quiet `bookingsApi.get` follows.
   - **On success:**
     - `replaceBooking` and `calendar.applyChange(shown, fresh)`;
     - close the assign panel or dialog (directly, since `closeDialog` returns early while busy);
     - open or restore the details panel on the fresh copy (`panelBehindDialog`, or `viewing`, or for check-in the panel, URL `bookings/:id`);
     - show the message per D2;
     - `ensureInvoice` and `refetchDelay.track('/rooms')` when the stage changed on a room move.
   - **Guards:**
     - if the host moved (epoch or URL changed), only swap the row;
     - a 404 closes everything, leaves the URL, shows `bookingNotFound` and refreshes the list;
     - any other failure keeps today's surface and message and refreshes the list;
     - if the re-read shows no change, keep today's surface with `moveNotAccepted` and still swap the copy in (D5).
3. **`markPaid` with the box ticked and an unpaid invoice:** `alreadyPaid` follows D1.
4. **i18n:** reword `alreadyCheckedIn`, `bookingAlreadyPaid` and `bookingHasMovedOn` in 18 locales, plus a new key if D1 says so. The invoices page also uses these keys, so the wording mustn't promise a re-read.
5. **Specs:** rewrite the four that assert the bug; add one per entry point × kind; a failed re-read; a 404; the host having moved; other refusals not re-reading; parity.
6. **KB, in the same PR:** the "already done counts as done" rule in `area/host-console.md`.

`booking-details-panel.ts`, `assign-rooms-panel.ts` and `booking-calendar.ts` need no changes (PE).

### Principal Engineer report (condensed)

- Root cause as above, with the four specs that assert it.
- **Which kinds each move can get back:**
  - confirm: none realistically (the server doesn't guard it; no confirm text in `WRONG_STAGE_TEXTS`);
  - check-in: `alreadyCheckedIn` or `wrongStage`;
  - cancel: `noLongerChangeable`;
  - no-show, check-out and invoice: `wrongStage`;
  - mark paid: `alreadyPaid` or `wrongStage`.
- **What each entry point should do:**
  - **Check-in:** close the assign panel and open the details panel on the fresh copy, navigating for the row-menu case.
  - **Dialog with a panel behind it:** close the dialog and restore the panel with the fresh copy and the footer key.
  - **Dialog from the row menu:** close, swap the row, toast.
  - **Invoice:** `invoiceExists` keeps its own path.
- **One shared branch in `send`;** the kind check lives in `booking-move-failure.ts`.
- **Don't re-read on:** `reasonRequired`, `notEnoughBeds`, `allocationInvalid`, `invoiceExists`, `bookingsClosed`, the create-only kinds, `roomAlreadyReleased`, status 0 or 404.
- **A semantic false-positive risk:** "only checked-in bookings can be invoiced" contradicts `INVOICEABLE_LANES` (checked-out is invoiceable). A re-read could return an unchanged booking, hence the unchanged-booking guard.
- **markPaid when already paid:** still pay the ticked invoice, through a `catchError` → `get` → invoice in the request pipe, with a new key `alreadyPaidInvoicePaid`. Never pay the invoice without a confirmed booking copy.
- **i18n:** all three keys are in `TRANSLATED_KEYS`. `invoices.ts:1168` embeds them in `hostInvoices.bookingNotPaid`, so the wording must stay true where there is no re-read.
- **Edge cases:**
  - a 404;
  - the host moving mid-read (epoch or URL);
  - busy released in both branches;
  - a quiet `get`;
  - `applyChange` from the shown copy;
  - occupancies carried on the fresh copy;
  - `ensureInvoice`;
  - `/rooms` tracking.
- **Follow-ups:**
  - confirm's double or raw toast;
  - the invoices-page "already paid" shown as an error;
  - the hard-coded success toasts.

**Keys:** `hostBookings.alreadyCheckedIn`, `bookingAlreadyPaid` and `bookingHasMovedOn` reworded; `alreadyPaidInvoicePaid` new; all 18 locales.

**What changed for the host.** A stay move refused because the booking already got there or moved on (another tab, another staff member, a stale index row) no longer says "Refresh…". The page re-reads the booking from the database and catches up:
- **Already done** (already checked in, already paid): an info toast, and the dialog or room allocation closes. The panel shows the fresh booking; check-in always opens it, so the host sees which rooms a colleague picked.
- **Moved on** (wrong stage, no longer changeable): the dialog closes and the panel shows the real stage with a red footer, or an error toast when no panel is open.
- **Safeguards:**
  - a re-read showing no change keeps the move open with "The server did not accept that";
  - a 404 closes everything ("booking not found");
  - a failed read refreshes the list;
  - if the host moved elsewhere meanwhile, only the row updates;
  - stages compare by lane, so legacy slugs aren't mistaken for moves.
- **Cross-pay:** "already paid" with the invoice box ticked pays the invoice only if the booking is settled and still payable **and** the invoice's own copy still owes. An invoice already paid is recorded, never paid twice; one that can't be read is never paid blind.
- **Every other refusal** is unchanged.
