Confirm on `/mess/confirm` only appends to `MessNotificationsService.confirmations` (in-memory, mock-seeded). Needed: a BE endpoint to record the confirmation against the token; FE `confirm()` calls it and shows "Confirmed" only on success; "Already confirmed" decided by the server; host mess page reads from the API.

### What the code says
- **No backend endpoint exists to confirm by token — on any branch.** Routes (`config/routes.rb`) expose only `GET /api/host/hostels/:id/meal_confirmations` (index) and the mess dashboard aggregates.
- **The read endpoint the FE already calls does not exist either.** `HostelsApi.getMealInfo` calls `GET /public/meal_confirmations/meal_info/:token` (`apps/web/src/app/services/hostels-api.ts:495`); `git grep meal_info` over every `origin/*` branch of the BE returns nothing. So today every real token renders "invalid" (the call 404s and `catchError` maps it to `null`).
- **The only existing confirm path is authenticated:** `POST /api/notifications/:id/mark_as_accepted` (`app/controllers/api/user_invites_controller.rb:52`) — needs a logged-in user who owns the `UserInvite`, keyed by invite id, not the `MealConfirmation.token`. Acceptance enqueues `PostRequisiteInviteActionJob` → `PostRequisiteInviteActionService` sets `MealConfirmation.is_confirmed/confirmed_at` (`app/services/post_requisite_invite_action_service.rb:12`). FE already wraps it (`student-api.ts:123`).
- **Link mismatch:** the BE emails `${HOSTELHIVE_BASE_URL}/meal_confirmation?token=<MealConfirmation.token>` (`app/services/pre_requisite_invite_action_service.rb:27`), but the FE route is `/mess/confirm` (`app.routes.ts:49`). There is no `/meal_confirmation` route, so the emailed link lands on the 404 page.
- **Host side is already on the API:** `mess-confirmations.ts:120` uses `HostelsApi.mealConfirmations`, `mess-list.ts` uses the overview endpoint. The seeded signal's only remaining consumers are `MessConfirm.confirm()` and the host "send test link" (`mess-notifications.ts:194`, `makeTestToken` → a base64 token the real API would never accept).

## Notes

### Draft backend ticket (for azeem-hamza/hostelhive)

**Title:** Public meal-confirmation endpoints keyed by the emailed token

**Why:** Students get a meal-confirmation link (`MealConfirmation.token`) by email/WhatsApp/SMS and must be able to confirm without logging in. The FE page `/mess/confirm` already calls `GET /public/meal_confirmations/meal_info/:token`, which does not exist (404), and there is no route to confirm by token. The only confirm path today is the authenticated `POST /api/notifications/:id/mark_as_accepted`.

**1. `GET /public/meal_confirmations/meal_info/:token`** — no auth
- Look up `MealConfirmation` by `token` across tenants (`ActsAsTenant.without_tenant`), then set the tenant to the record's.
- `200`:
  ```json
  { "success": true, "meal_info": {
      "meal_type": "lunch", "meal_date": "2026-10-10",
      "expired_time": "2026-10-10T13:00:00+05:00",
      "is_confirmed": false, "confirmed_at": null,
      "hostel_name": "…" } }
  ```
  `expired_time` must be ISO-8601 with an offset. Return `hostel_name` if it's cheap to include. No renter PII (phone/email).
- `404` `{ "success": false, "errors": ["Invalid token"] }` for an unknown token.
- An expired link still returns `200` with `expired_time` in the past. The FE shows the "expired" state itself.

**2. `POST /public/meal_confirmations/confirm`** — no auth, body `{ "token": "…" }`
- Unknown token → `404` `{ "success": false, "errors": ["Invalid token"] }`
- Already confirmed → `200`, **idempotent**, with `"already_confirmed": true` and no changes
- `Time.current > expired_time` and not yet confirmed → `410` `{ "success": false, "errors": ["Confirmation window has closed"] }`
- Otherwise, in one transaction:
  - set `is_confirmed: true, confirmed_at: now`
  - mark the matching pending `UserInvite` (`associated: meal_confirmation`, type `meal_confirmation`) `is_accepted: true, is_read: true, accepted_at: now`, so the student's notification stops showing as pending
  - respond `200` `{ "success": true, "already_confirmed": false, "meal_info": { …same shape as GET… } }`
- Concurrency: use `with_lock` on the record so a double-tap confirms once. The second call gets `already_confirmed: true`.
- **Both routes must be decided synchronously.** Today the accept path sets `is_confirmed` through `PostRequisiteInviteActionJob`, which is async. The response has to reflect the saved state, and that job re-applying the same values is harmless.

**3. Email link path**
`app/services/pre_requisite_invite_action_service.rb:27` builds `${HOSTELHIVE_BASE_URL}/meal_confirmation?token=…`, but the FE route is `/mess/confirm`. Change it to `/mess/confirm?token=…`. Apply the same path to any WhatsApp/SMS templates. (The FE will also add a `/meal_confirmation` redirect so links already sent keep working.)

**Acceptance**
- Request specs for: unknown token, valid token, expired token, already confirmed, and a confirm followed by a second confirm.
- After a confirm, `GET /api/host/hostels/:id/meal_confirmations?f[is_confirmed]=true` includes the renter, which means the search index is updated.
- The student's meal-confirmation notification is no longer pending.
- No auth header is required on either route, and neither route leaks renter contact details.

**FE counterpart:** Trello #104 (hostelhive-FE) — `/mess/confirm` will call both routes and show "Confirmed" or "Already confirmed" from the server's response.

## Root cause

**Confirmed** — the new `mess-confirm.spec.ts` case "records the confirmation on the server and only then shows confirmed" fails against the old `confirm()`, which set the state synchronously and sent no request.

| | |
|---|---|
| **Symptom** | Student taps Confirm and sees "Confirmed", but the host never sees it and a reload forgets it |
| **Cause** | `MessConfirm.confirm()` called `MessNotificationsService.confirm()`, which only prepended to a mock-seeded in-memory signal (old `mess-notifications.service.ts:333`). The FE had nothing better to call: the backend has no public endpoint to confirm by token, and not even the `meal_info` lookup the page already uses |
| **Why it escaped** | The page had no spec, and the backend contract was never checked against `config/routes.rb`. The 404 on `meal_info` is swallowed into the "invalid" state, so the page looked like it worked |
| **Same shape elsewhere?** | The emailed link path (`/meal_confirmation`) never matched the FE route (`/mess/confirm`): the same "contract assumed, never checked" failure. The FE redirect added here covers it, and #108 asks the BE to change the URL |

## Plan

1. `HostelsApi.confirmMeal(token)` → `POST /public/meal_confirmations/confirm` (the #108 contract). `MealInfoRaw` gains `is_confirmed`, `confirmed_at` and `hostel_name`.
2. `MessConfirm`:
   - A meal already confirmed on load shows "Already confirmed".
   - Confirm calls the API and shows "Confirmed" or "Already confirmed" from the server's flag.
   - 410 → expired, 404 → invalid.
   - 0/5xx → stay on the confirm step with a retryable error.
   - The button is disabled while the request is in flight.
   - An unknown `meal_type` → invalid. It previously crashed on `MEAL_META[undefined]`.
3. Add a `/meal_confirmation` → `mess/confirm` redirect that keeps `?token=`.
4. Delete dead mock code: the `confirmations` seed and its computeds, `totalSubscribers`, the token codec, `makeTestToken`, `resolve`, `confirm`, `TokenPayload`/`ResolveResult`/`MealConfirmation`, and the host `openTest()`, which no template referenced.
5. Hide the "On the menu" card and the "— {{menu}}" suffix when there is no menu. The API sends none, so the page rendered "reserved — .".
