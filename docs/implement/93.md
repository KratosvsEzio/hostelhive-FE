#### A. Backend contract

All paths are relative to the backend repo on `feature/billing-core`.

**Routes** (`config/routes.rb` lines 34–46):
- `GET /api/plans?country=XX` is public and skips auth. The country falls back to the `CF-IPCountry` header.
- `GET /api/hostels/:hostel_id/billing`
- `POST /api/hostels/:hostel_id/checkout` with `{plan_id}`
- `GET /api/hostels/:hostel_id/invoices`
- `POST` and `DELETE /api/hostels/:hostel_id/subscription/schedule_downgrade`. POST takes `{plan_id}`; DELETE is "undo".
- `POST /api/hostels/:hostel_id/subscription/cancel`. DELETE on the same path is "resume".
- `GET /api/invoices/:id`
- `POST /api/invoices/:id/payments`
- Admin routes exist but are out of scope.

**Success envelope:** every success response is the payload plus `success: true`. IDs are obfuscated strings (`obfuscated_id`). Amounts are decimal strings such as `"1500.00"` (`Billing.to_major`, `billing.rb:24-26`). The frontend never sees minor units.

**Error envelope** (`render_message_template.rb`):
- Errors are `{success:false, errors:[msg…]}`, with 422 as the default.
- 401 is `errors:["You need to sign in or sign up before continuing."]`.
- 403 from CanCan (`api_controller.rb:19-22`) is `{success:false, error:"<msg>"}`. The key is singular `error`, not `errors`.
- `billing_access.rb:6-8`: every `Billing::Error` becomes **422** `{success:false, errors:[message]}`. The concern has no 400 or 403 bodies at all.
- **The 400 "You need to subscribe to avail the services" is not on this branch.** A repo-wide search finds nothing; the FE's `isSubscriptionError` still matches on that wording. It is probably produced by another controller or by the host/bookings endpoints; this is inferred, not confirmed.

**`GET /api/plans`** (`plans_controller.rb:7-12`, `summary.rb:22-26`):
```
{currency, country:"PK"|null, plans:[{id, code, name, features:["boost"|"crm"…], interval, currency, price:"…"|null}], success}
```
- Plans are `Plan.active.ordered`. `features` lists only add-ons (`boost`, `crm`); listing is implicit in every plan (`plan.rb:1-2`).
- `interval` is a string, and `Plan::INTERVAL` is 1 month.
- `price` is `null` when the plan has no price in that currency.

**`GET …/billing`** (`summary.rb:10-19, 38-80`) returns `{billing:{…}}`:
- `currency` is the live subscription's currency, otherwise the hostel's `billing_currency`.
- `country_code` is the hostel's country code.
- `payment_methods` is `HOST_PAYMENT_METHODS[currency]`. It is `["safepay","bank_transfer"]` for both PKR and USD (`billing.rb:17`).
- `subscription` is null when there is none, otherwise:
  - `id`
  - `status` as `{id, name, slug, color}`
  - `currency`
  - `plan {id, code, name, features}`
  - `current_period_start` and `current_period_end`
  - `grace_until`, which is `current_period_end + 3 days` (`GRACE_PERIOD`)
  - `scheduled_plan {id, code, name}` or null
  - `cancel_at_period_end`
- `features` is a subset of `["listing","boost","crm"]`.
  - Boost applies only when the subscription is `active`.
  - Listing and CRM stay on while `past-due`.
- `open_invoice` is null if there is no open invoice or it has expired. Otherwise it is `{id, number, kind, total, currency, period_start, period_end, expires_at, awaiting_verification}`.
- `plans[]` is the plans-list shape plus an `action`:
  - `buy`: not live.
  - `upgrade`: `amount_due_now` is the prorated amount.
  - `renew`: the current plan when past-due, or a different plan that is not an upgrade.
  - `current`: `amount_due_now` is the renewal price.
  - `downgrade`: `amount_due_now: null` and `scheduled: bool`.
  - `unavailable`: `amount_due_now: null` and `reason`.
- **There is no hostel timezone in the billing payload.** The frontend must read `timezone` from `HostelSerializer` (`hostel_serializer.rb:6` includes `:timezone`).
- There is no `possible_statuses` in `/billing`.
- Subscription slugs are `incomplete|active|past-due|expired|canceled`.

**`POST …/checkout`** (`hostel_billing_controller.rb:19-22`, `checkout.rb`):
- It returns 201 with `{invoice:{…}}`.
- It reuses the existing open invoice if kind, plan, currency and total all match. Otherwise it voids the old one and issues a new one.
- It returns 422 `Set the hostel's country first` when the hostel has no `country_code` and no currency override (`checkout.rb:38`). The Ruby hash also carries `country_required: true`, but that flag is not sent in the response, so the frontend must match on the message text.
- Other 422 messages from `checkout.rb`:
  - `This plan is not available`
  - `This plan is not available in USD` (or PKR)
  - `Choose a cheaper plan by scheduling it for your renewal`
  - `A bank transfer for invoice HH-… is waiting for verification`
- An unknown `plan_id` returns 404 via `Plan.active.find`.
- A missing `plan_id` raises `ParameterMissing`. Its status is not handled in this controller, so it is presumably 400 (inferred).
- The invoice number format is `HH-YYYY-000123` (`invoice.rb:48`).
- Invoice lifetimes:
  - Online invoices are open for 24 h.
  - A renewal invoice is open until `grace_until`.
  - Bank-transfer submission extends the expiry to at least 72 h.

**`POST /api/invoices/:id/payments`** (`invoices_controller.rb:14-19`, `payments.rb`):
- Request body is `{payment_method, reference, proof_attachment_id}`. `payment_method` is required.
- Response is 201 `{payment:{…}, invoice:{…}}`.
- The proof field is `proof_attachment_id` and takes the **raw `Attachment.id`**. Attachments use `skip_obfuscates_id!` and are UUIDs (`set_uuid`), so it is the same `id` the presigned call returns.
- 422 messages from `payments.rb`:
  - `Enter the bank transfer reference` (reference is blank)
  - `A bank transfer for this invoice is already waiting for verification`
  - `Invoice HH-… is paid` (or void)
  - `This invoice has expired`, which also voids the invoice
  - `Bank transfer isn't available for PKR invoices` (the humanized method name is interpolated)
  - **`safepay` → 422 `Online payment isn't available yet`** (`payments.rb:22`)
- A bank-transfer payment is created with status `awaiting-verification`.
- Payment slugs are `pending|awaiting-verification|succeeded|failed`.

**Not in this PR, so the frontend needs a decision:**
- **No bank account details for the bank transfer.** There is no endpoint or field. Nothing in `summary.rb`, `payments.rb` or `billing.rb` carries bank details. They would have to come from frontend config or a new backend field.
- **No Safepay `checkout_url`.** It is rejected with 422 until Safepay's own PR. Its return-page contract is unknown, so the success and cancel pages can only poll `GET /api/invoices/:id` or `/billing` (inferred).
- **No invoice PDF route or serializer field.** Download PDF has nothing to call.
- **Rejection reason:** `PaymentSerializer` has `failure_reason`. `fail!` sets it. A rejected bank transfer presumably becomes status `failed` with `failure_reason`, but the admin `reject` controller was not read.

**Serializers:**
- `InvoiceSerializer` (`invoice_serializer.rb:4-6`): `id, number, kind(new|renewal|upgrade), currency, total, period_start, period_end, expires_at, paid_at, voided_at, created_at, plan{id,code,name,features}, lines[{description,amount}], status{id,name,slug,color}, payments[]`. Invoice slugs are `open|paid|void`.
- `PaymentSerializer`: `id, payment_method(safepay|bank_transfer|cash|admin_grant), amount, currency, reference, failure_reason, proof_url, verified_at, succeeded_at, created_at, invoice_id, status{…}`.
- `SubscriptionEventSerializer`: `id, kind, data, created_at, invoice_number`. It is only used in admin.
- Invoice `kind` can be `new`, `renewal` or `upgrade`.

**`GET …/invoices`** (`hostel_billing_controller.rb:25-32`):
- It is search-backed (Searchkick) and filters by `f[status.slug]=…`.
- It returns `{invoices:[…], possible_statuses:[{id,name,slug}], pagination:{current_page,next_page,prev_page,total_pages,total_count}}`.
- The default sort is `created_at desc`.
- The page size is `params[:limit]`, defaulting to 30.

**Plan changes** (`plan_changes.rb`): schedule, undo, cancel and resume each return the full `/billing` payload, `{billing:{…}}`. All four return 422 `There is no active subscription` unless the subscription is `active`. Schedule also returns:
- `Only a cheaper plan can be scheduled; upgrade through checkout`
- `This plan is not available`
- `This plan is not available in …`

**Permissions:** `authorize!` uses CanCan abilities `Subscription :show/:update` and `Invoice :index/:create/:show/:create_payment`. The FE nav uses `core:Hostel:subscription`, which maps to the old model. The new permission names are not verified.

**`hostels_controller.rb`:**
- **`country_code` is not in the strong-params permit list** (lines 66–95; `grep -c country_code` returns 0). The list has `:country` but not `:country_code`, so the frontend cannot write it.
- **`HostelSerializer` does not return `country_code` either.**
- The `Hostel` model requires `country_code` on create (`validates :country_code, presence: true, on: :create`, `hostel.rb:41`). It must match `/\A[A-Z]{2}\z/`, with the message "must be a two-letter ISO country code".
- Create therefore fails until the permit list is fixed. This is a likely backend gap in PR #26 and needs raising with the backend.
- `timezone` is permitted, required on create, and locked once the hostel has bookings.
- `PublicController` has no `crm` or booking flag. The PR only removes `products`.

**Old endpoints** (PR #26 file list): `orders_controller.rb`, `order.rb` and `product.rb` are removed. `current_subscription` is removed from `hostels_controller`. `public#products` is removed. The old order, contract and product migrations still exist.

**Presigned upload** (`attachments_controller.rb:8-11`, `routes.rb:18`):
- The route is `GET /api/:attachment_type/presigned_url?key=…&file_name=…&content_type=…&label_id=…`.
- It returns `{success, url, id, object_url, message}`, where `id` is the raw UUID.
- Valid `attachment_type` values are `documents generic avatars videos audios cnic_front cnic_back` (`attachment.rb:17`).
- `content_type` must be in `content_type_map` (pdf, jpg, png and others), otherwise 422 `Content Type not supported`.
- The S3 PUT URL expires after 24 h.
- The FE's `ImageUploadService` (`services/image-upload.service.ts`) calls `GET /api/documents/presigned_url?key=&content_type=`, then PUTs to S3 with XHR. That `key` becomes the backend `params[:key]`, and `documents` in the path is the `attachment_type`.
- The FE does not send `file_name`, and `Attachment.create!` takes `file_name` from `params[:file_name]`.
- `imageMimeType` (in `lib/src/ui/lib/photo-grid/photo-grid.ts`) is image-oriented. A PDF proof needs the real MIME type and a size check against `MAX_UPLOAD_BYTES` (10 MB, `documents-api.ts:14`).
