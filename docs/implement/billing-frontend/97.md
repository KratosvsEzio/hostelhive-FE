## Ticket understanding

### Ticket (Trello #97, as retrieved 2026-10-11)

Part of #93, section 5. Depends on 2/8. Backend merged in PR #26.

1. **Invoice history** — `GET /api/hostels/:id/invoices` (also `f[status.slug]=paid`, `page=2`) → `{invoices:[{id, number, kind, period_start, period_end, total, currency, status, invoice_pdf_url, created_at, …}], possible_statuses, pagination:{current_page, next_page, total_pages, total_count}}`. Table: number, date, kind (New plan / Renewal / Upgrade), period, total with currency, status badge, PDF. Status filter from `possible_statuses` (`open`, `paid`, `void`), plus pagination.
2. **Invoice detail** — `GET /api/invoices/:id` → `{invoice:{…, lines:[{description, amount}], payments:[{payment_method, amount, currency, status, reference, failure_reason, proof_url, succeeded_at}], invoice_pdf_url}}`. Show the lines and each payment attempt with method, status and failure reason (an invoice can have several attempts). An `open` invoice gets **Pay** (payment step, 3/8).
3. **Download PDF (the receipt)** — `invoice_pdf_url` is a plain string URL or `null`; show **Download PDF** only when set, as a plain link (no auth header). Open and void invoices never have a PDF. Built a few seconds after the invoice becomes paid: paid + `null` → "Preparing receipt…" and fetch the invoice again.
- **Acceptance:** list filters by status and paginates · detail shows lines and payment attempts with failure reasons · Download PDF only on paid invoices; "Preparing receipt…" covers the gap · amounts in their own currency, PKR and USD never mixed.

#### 2. Backend contract (`azeem-hamza/hostelhive@main`)

##### `GET /api/hostels/:hostel_id/invoices` (`app/controllers/api/hostel_billing_controller.rb`)

```ruby
before_action -> { authorize!(:index, @hostel.invoices.new) }, only: :invoices
params[:f] ||= {}
params[:f][:hostel_id] = @hostel.obfuscated_id
params[:sort] ||= { created_at: :desc }
invoices = Invoice.safe_search(load: false, body: search_kick_body, page: params[:page] || 1, per_page: params[:limit] ||= per_page_records)
render_success_response({ invoices: Invoice.serialize_json(invoices), possible_statuses: Invoice.all_statuses.as_json(only: [:id, :name, :slug]), pagination: get_pagination(invoices) }, :ok)
```

- **Params:**
- Status filter is `f[status.slug]=paid`.
- Page is `page`. The page size param is `limit` (not `per_page`) and defaults to 30 (`per_page_records`).
- `pageParams` in `util/pagination.ts` already does `page` + `limit`.
- The default sort is `created_at desc`. Other sorts use `sort[field]=asc|desc`.
- The hostel scope is forced from the URL. A client cannot override it.
- **Filter mechanics (`SearchHelper`):** `f[status.slug]` is a `term` filter. `parse_key` turns `status.slug` into `status.slug.keyword`. The admin payments and listings pages use the same key.
- **Response:** `{invoices:[…], possible_statuses:[{id,name,slug}], pagination:{current_page,next_page,prev_page,total_pages,total_count}, success:true}`.
- `prev_page` is extra.
- `ApiPagination` and `toPageInfo` in `util/pagination.ts` already match.
- **Authorisation:** CanCan `Invoice :index`.
- The host role gets `core:Invoice:index|show|create|create_payment`, from migration `20261004140000` (per 95.md).
- A 403 uses the singular `{error}` envelope.
- The hostel is loaded with `Hostel.find` (a 404 envelope if unknown).
- Nobody checked whether `authorize!(:index, instance)` enforces a host-ownership condition on the hostel.

**The list serializer is not the detail serializer.** `serialize_json` on a `Searchkick::Results` with `load: false` uses `SearchkickSerializer`, which returns raw Elasticsearch `_source` (`app/models/application_record.rb`, `app/serializers/searchkick_serializer.rb`). The shape comes from `ElasticIndexes::InvoiceIndex#search_data`:

- **Fields present:** `id` (obfuscated), `number`, `hostel_id`, `kind`, `currency`, `total` (decimal string), `total_minor` (an integer; never use it, per the money rule), `period_start`, `period_end`, `expires_at`, `paid_at`, `voided_at`, `invoice_pdf_url`, `created_at`, `plan {id, code, name}`, `hostel {id, name}`, `lines [{description, amount}]`, and `_score`.
- **Fields absent:** `payments`, and `plan.features`.
- **Status shape:** `status: {id, name, slug, position, color: {id, primary, secondary, tertiary}}`. The id, name and slug match `BillingStatus`. The colour is an object with extra fields, not a string. The detail serializer returns `{primary, secondary, tertiary}`.
- **Consequence:** the table can show number, date, kind, period, total and currency, status and PDF from the list alone. The payments list needs the detail call.
- **Timestamps:** these come from an index document, so they are probably UTC ISO strings. I did not verify the exact format.

##### `GET /api/invoices/:id` (`app/controllers/api/invoices_controller.rb`)

- It returns `{invoice: Invoice.serialize_json(@invoice)}`.
- The invoice is loaded with `Invoice.includes(:lines, :payments, :plan).find`.
- It uses `authorize!(:show, @invoice)` (`core:Invoice:show`), and the model scopes to `hostel.host_id` or `manager_id`.
- `InvoiceSerializer` attributes are `id, number, kind, currency, total, period_start, period_end, expires_at, paid_at, voided_at, created_at, invoice_pdf_url, plan, lines`, plus `has_many :payments`.
- `PaymentSerializer` attributes are `id, status, payment_method, amount, currency, reference, gateway_reference, failure_reason, proof_url, verified_at, succeeded_at, created_at, invoice_id`.
- Payments are ordered by `created_at, id` (oldest first).

##### `invoice_pdf_url` and the PDF job timing (`app/models/invoice.rb`, `app/jobs/invoice_pdf_job.rb`, `app/services/pdf_service.rb`)

- `after_commit :generate_pdf` runs when `status_id` changed and the invoice is paid. It enqueues `InvoicePdfJob.perform_later`.
- The job returns early unless the invoice is paid and has no PDF. `PdfService.store` renders with WickedPdf, attaches the file, then calls `@record.reindex`.
- So:
- `invoice_pdf_url` is `null` for open and void invoices.
- It is `null` on a paid invoice for a short window while the job runs.
- After the job, the detail payload and the list index both carry the URL (the reindex refreshes the list).
- `url` is `invoice_pdf&.url`, a plain string with no auth header. An admin grant also produces a PDF (the comment says "or an admin grants the plan").
- **Risk:** if the PDF job fails, the invoice stays paid with a `null` URL forever. The 60 s cap and a "Check again" button cover that case, but the copy needs a "couldn't prepare, try later" state.
- **Risk:** the list reads Elasticsearch. Its `invoice_pdf_url` can lag the detail slightly (index refresh latency).

- **`payment_method`:** `safepay`, `bank_transfer`, `cash` and `admin_grant` (per 96.md's backend read).
- The FE needs labels for all four. Only `safepay` and `bank_transfer` come from checkout. An admin-granted invoice may have an `admin_grant` payment.
- No i18n labels for payment methods or payment statuses exist today.
- **`failure_reason`:**
- It is free text and can be an admin rejection reason, "Safepay declined the payment", "The Safepay checkout ended unpaid (TRACKER_…)", "Invoice voided", or "Expired".

#### 6. Contradictions and gaps

1. **#97 card versus #96 D8.** The card says "each payment attempt with method, status and failure reason". #96 D8 says "never `failure_reason`" because the text can carry internal wording and a tracker id ("Charged at Safepay (<tracker>); refund it from the Safepay dashboard"). Needs a decision at the 2d gate. Options:
 - Show `failure_reason` except when it matches `/Charged at Safepay/`, where the existing `chargedNotApplied` copy is used instead.
 - Show our own generic copy per status and keep the "never render" rule.
 - The risk with raw text is the tracker id, and the internal wording on voided or expired reasons. Admin rejection reasons are written for hosts but only occur for bank transfer, which this UI does not offer.
2. **List shape.** Rows come from Elasticsearch and have no `payments` and no `plan.features`. The card's "…" hides this. Status colour is an object with extra keys. Keep the list row type separate from `BillingInvoice`.
3. **`status.color` type.** `BillingStatus.color: string | null` does not match the API. This is harmless today, but a list-row type should not inherit it.
4. **The card's detail path.** `GET /api/invoices/:id` returns the same shape as the one already used by the pay page. Reuse `BillingApi.invoice()`.
5. **PDF edge cases.** The card says "Open and void invoices never have a PDF". A paid invoice with a permanently `null` URL (the job failed) would show "Preparing receipt…" forever unless the poll has a cap and a fallback state.
6. **Date format.** Dates are UTC (#95 D4). The list date column is also UTC from the index. Use date-only formats.
7. **KB staleness.** The area file `host-billing-and-subscription.md` describes billing as a placeholder. The code and run files win. 95.md noted four drafted entries not yet applied.
8. **Cross-tenant access.** The list route is guarded by CanCan only. The 403 shape is `{error}` (singular). The error interceptor already reads both shapes (95.md).
9. **Page size.** The backend default is 30. The admin tables use 10 (`PAGE_SIZE` in `util/pagination.ts`). Pick one for this table.
10. **Live API.** Not probed. The list shape is source-derived, so a first authenticated call should confirm the timestamp format and the status object.

#### Edge cases and failure modes

**List and filters**
- **The list lags behind the detail.** After a payment, the Elasticsearch row can still say `open` or have a null PDF URL. The detail page is the source of truth. The list never polls, and paid rows without a URL link to the detail page.
- **The PDF job fails for good**, leaving a paid invoice with a null URL forever.
- Detail: polls for 60 s, then shows "We couldn't prepare the receipt yet…" with **Check again** (subscribe to the poll again).
- List: a paid row without a URL shows "Preparing…" as a link to the detail page. That is honest in the short window. The permanent case is cosmetic and is flagged in the risks.
- **Elasticsearch down or not reindexed.** `safe_search` probably comes back empty, which would show "No invoices yet". The frontend cannot tell the difference. This is a backend risk, noted.
- **`?status=` not in `possible_statuses`, or junk.** The server returns nothing, so show the no-match state with "Show all" (`common.showAll`), which clears the param. No chip is active.
- **`?page=` beyond the last page, or junk.** Parse it to an integer ≥ 1; anything else counts as 1. If the rows are empty with `page > 1` and `total_count > 0`, `replaceUrl` with `page` removed.
- **No statuses offered.** If `possible_statuses` is empty, hide the chips. Keep the last `possible_statuses` in a signal across reloads so the chips don't flicker while the next page loads.
- **Stale responses.** Fetch with `switchMap` over `{hostelId, status, page, refresh}`. Changing hostel, filter or page cancels any request still in flight.

**Hostel switch**
- List: the switcher drops the query string. Because status and page are derived from `queryParamMap` (not a snapshot), the filter resets to All and page 1 on its own.
- Detail: `invoiceId` stays the same while `hostelId` changes, and the invoice belongs to the previous hostel. The serializer has no `hostel_id` (96 D14), so ownership cannot be checked. On a `hostelId` change **after the first value**, `router.navigate(['/host', newId, 'subscription', 'invoices'], {replaceUrl: true})`.
- `PaymentStep` has the same problem today (snapshot `hostelId`, so its back link is stale). Report it; don't fix it here.

**Detail and money**
- **403 / 404 / other errors** follow `PaymentStep.loadFailed`:
- 403 → `hostBilling.noAccess*`, no retry.
- 404 → `hostPayment.notFound*`.
- Anything else → `invoiceLoadError` with retry and `networkError`.
- **Poll error ticks** are ignored, but a 403 or 404 tick stops the poll (put it in `until`).
- **Currencies stay separate.** Each row and each attempt uses its own `currency` through `billingMoney`. There are no totals, sums or comparisons anywhere. An attempt's amount uses `payment.currency`, not the invoice's.
- **Zero-total or admin-grant invoices.** `billingMoney('0.00', 'PKR')` gives "PKR 0". Show it, don't hide it. An `admin_grant` payment shows the method label "Granted by HostelHive" and status succeeded. A PDF is generated for these too.
- **Cash** gets its own label. **An unknown method** shows a generic "Other" label (never the raw string). **An unknown status slug** shows the server's `status.name` with a neutral tone.
- **Void invoices.** No PDF, no Pay. Show a "Voided on {date}" line if `voided_at` is set. Earlier pending attempts come back failed with the reason "Invoice voided"; show the generic failed note, never the reason.
- **Expired invoices** are void in the backend, so they are covered by the void case.
- **Open invoice without `core:Invoice:create_payment`.** Show the `hostPayment.payForbidden` line instead of Pay.
- **Charged at Safepay but not applied.** This can be any attempt, including on a paid invoice (a double charge). It gets `hostPayment.chargedNotApplied` with `{number}` and a contact link. The tone is danger, whatever the invoice status.
- **Payments come oldest first.** Display newest first using `[...payments].reverse()` in a `computed`, never mutating the original.
- **Attempt dates.** Use `succeeded_at ?? created_at`, date only (UTC until the backend timezone fix lands, 95 D4).
- **Never shown:** `failure_reason`, `gateway_reference`, `reference`, `proof_url`.
- **Timestamps from the index** may be `…Z`, `+05:00` or a bare `YYYY-MM-DD`. `apiDate` handles all three (`util/api-date.ts:17-22`). A null `period_*` shows "—".
- **Unknown `kind`.** `billingInvoiceKindLabelKey` returns null, so show "—".
- **PDF link.** Use `target="_blank" rel="noopener noreferrer"`. Do not add a `download` attribute: browsers ignore it cross-origin, and the URL has no extension. The per-row accessible name includes the invoice number.

#### Technical requirements

#### Recommended implementation approach

**Table.** Build it by hand rather than with `hh-data-table`. Reasons:
- The footer prints English ("bills · Page 2 of 3") in all 18 locales, which breaks the billing parity standard.
- Its cells are strings precomputed in TypeScript. Every date, money amount and label would have to move out of `apiDate` / `billingMoney` / `transloco` pipes into TypeScript, with the `locale.ready()` workaround, and `<bdi>` would be lost.
- Its no-results row carries an expenses i18n key.
- Mobile is sideways scrolling only.

A feature-local `<table>` (`<caption class="sr-only">`, `scope="col"` headers) at `sm` and up, with a `<ul>` of cards below `sm`, keeps money as strings in pipes. It also matches the "Payment history" layout of mockup `18-host-subscription.html`. Use the existing `hh-status-pill`, `hh-skeleton`, `hh-empty-state`, `hh-error-state` and `hh-pagination` (bind `[page]` / `(pageChange)`; it is i18n-clean).

**Filter chips.** Either option is fine:
- Reuse `hh-filter-chips`, with labels built in TypeScript through the `search-filters.ts` `t()` pattern.
- Avoid that pattern by reusing the chip markup with `aria-pressed` in the page template, so labels stay in pipes.

I lean to reusing `hh-filter-chips`, and adding `[attr.aria-pressed]` to the shared component is a one-line change worth proposing separately.

**State.** Derive everything from route observables, as `BillingPage` does: `combineLatest(pathFromRoot paramMaps)` → `hostelId`, and `queryParamMap` → `status` and `page`. Then a single `toSignal(… switchMap(load) …)` with `startWith({kind: 'loading'})` and `catchError` → view union. That one pipeline handles a hostel switch, browser back/forward and stale responses with no extra code.

**Detail page.**
- Model the load on `PaymentStep.load` / `loadFailed` (copy the pattern; do not import from the payment step).
- Read `invoiceId` from a live `paramMap`, not a snapshot.
- Start the receipt poll from an `effect` or `toObservable` on `invoice()` matching "paid with no URL", guarded so only one poll runs.
- Expose `receipt: 'none' | 'ready' | 'preparing' | 'timedOut'` as a `computed`.

**Keep money, notes and names honest.**
- Put no money logic anywhere.
- `attemptNote` is the only code that reads `failure_reason`, and only through a regex.
- Prefix every new symbol with `billing`, or keep it local to `subscription/`. Never import from `util/table-configs/invoice-table-cols.ts`; an ESLint restricted-import rule is optional.

**Avoid:**
- Polling the list.
- Converting `total` to a number.
- Rendering `status.color`.
- Showing `reference` / `gateway_reference` / `proof_url` / `failure_reason`.
- Adding a route guard.
- A `download` attribute.
- `hh-data-table`'s `pagination` input.
- `afterNextRender`.

- get a receipt for the accounts;
- find out why a payment didn't go through;

An open invoice gives one way to pay.

#### 2. Acceptance criteria

Routes: `/host/:id/subscription/invoices` (history) and `/host/:id/subscription/invoices/:invoiceId` (detail). **Never** `/host/:id/invoices`, which is renter bills.

##### A. How to get there

1. **Link from billing.** Given a host on `/host/:id/subscription` whose billing has loaded:
 - a "Billing history" row shows below the payment-due box (or below the current-plan card when nothing is due) and above Plans;
 - the row reads "See past invoices and download receipts." with a **View billing history** link to `subscription/invoices`;
 - it is hidden only when the session's permission flags are loaded and lack `core:Invoice:index`. When the flags are absent, it shows (`hasPermission` lets everything through when no flags are loaded).
2. **Nav stays lit.** Given any history or detail URL, the "Billing" nav entry is active, and the page frame is `app-dashboard-layout` titled "Billing".
3. **Back links.**
 - History has **Back to billing**, which goes to `/host/:id/subscription`.
 - Detail has **Back to billing history**, which returns to the list with the filter and page the host left (`?status=&page=` kept).
4. **Detail to pay and back.**
 - **Pay** on the detail links to `/host/:id/subscription/pay/:invoiceId` with the id as returned.
 - The pay step's paid state gains a **View receipt** link to the detail (Q8).
 - The pay step keeps its existing **Back to billing**.

##### B. History list

5. **Request.** Given the page opens, it calls `GET /api/hostels/:id/invoices?page={p}&limit=10` (plus `f[status.slug]={slug}` when filtered), suppressing the error toast. Default sort is the server's `created_at desc`. No client-side sorting.
6. **Columns.** Each row shows:

 | Column | Content |
 |---|---|
 | Invoice | The `number` as returned, as a link to the detail |
 | Date | `created_at`, `d MMM yyyy` |
 | Type | Kind label without the period: New plan, Renewal or Upgrade. An unknown kind shows "—". |
 | Period | `period_start – period_end`, `d MMM yyyy` each. A missing end shows "—". |
 | Total | `billingMoney(total, currency)` inside `<bdi>`, e.g. `PKR 5,000` or `$18` |
 | Status | A pill using our label for a known slug and tone from `invoiceStatusTone`. An unknown slug shows `status.name` with a neutral tone. |
 | Receipt | See AC 7 |

 Clicking anywhere on a row (other than the PDF link) opens the detail.
7. **PDF cell.**
 - With `invoice_pdf_url` set: a plain `<a href target="_blank" rel="noopener noreferrer">` reading "PDF", with aria-label "Download receipt for invoice {number}". No auth header. A click does not open the detail.
 - Paid with a null URL: muted text "Preparing…". The list does **not** poll.
 - Open or void: "—".
8. **Status filter.**
 - Chips read **All** followed by one chip per `possible_statuses` entry, in server order, labelled as in AC 6.
 - Selecting a chip sets `?status={slug}` (All removes it), resets to page 1, and refetches.
 - The filter survives a reload and a round trip to the detail.
 - An unknown slug in the URL is still sent. The server decides, and it shows the filtered-empty state.
9. **Pagination.**
 - Built from `pagination` (`current_page`, `total_pages`, `total_count`). It shows "Page {page} of {total}" with previous and next.
 - It is hidden when `total_pages <= 1`.
 - A page change sets `?page=` and scrolls to the top of the table.
 - A `?page=` past the last page shows the filtered-empty state with **Go to first page**.
10. **Loading.** A skeleton table (header plus about 5 rows) shows on the first load and on every filter or page change. The chips stay usable.
11. **Empty, unfiltered.** Given `total_count == 0` with All selected, the page shows "No invoices yet / Your HostelHive invoices will appear here after you choose a plan." and **Go to billing**. The chips are hidden.
12. **Empty, filtered.** Given `total_count == 0` with a status selected, it shows "No invoices match this filter." and **Show all**.
13. **Errors.**
  - A 403 shows `hostBilling.noAccessTitle/noAccessMessage`, with no retry and no toast.
  - Any other failure (5xx, network, 404 hostel) shows "We couldn't load your invoices." with **Try again**.
  - Back to billing is always present.
14. **No money arithmetic.** There is no page or footer total, nothing is summed across rows, and `total_minor` is never read. Rows in different currencies sit side by side, each in its own currency.
15. **Small screens.** At 360 px the list is usable without the page scrolling sideways. Rows may stack as cards, or the table may scroll inside its own container. The number, total, status and PDF stay visible without opening the row.

#### 6. Product risks and open questions

##### Risks

- **P1. The PDF job can fail silently.** A paid invoice can keep a null URL forever. AC 23's cap and "Check back later" cover the UI, but nobody is alerted. Suggest a backend follow-up: retry the job, or regenerate on demand.
- **P2. The list's index can lag.** A just-paid invoice may still show "Unpaid" or no PDF in the list for a moment. The detail is authoritative, so this is accepted.
- **P3. Receipt URLs are public and permanent.** Anyone who has the link can open the receipt (it is UUID-based, so not guessable). This is acceptable for a receipt; it is a backend decision if tighter access is wanted.
- **P4. The PDF can show a different date from the screen.** The PDF uses the hostel's time zone; the screens use UTC until D4 lands. A paid-at-midnight invoice can show different dates in the two places. This goes away with D4.
- **P5. Cross-hostel access is unverified.** The list authorises `Invoice :index` on `@hostel.invoices.new`. Nobody has confirmed that the Ability limits this to hostels the user owns or manages. QA or the PE should check with a manager of hostel A asking for hostel B. It is a backend issue if it leaks.
- **P6. The detail URL carries a hostel id the invoice can't confirm.** The invoice has no `hostel_id`, so a multi-hostel host could open hostel B's invoice under hostel A's URL. The data is still correct; only the back link goes to A. This is low risk; `hostel_id` was already requested (96.md D14).
- **P7. Mixed languages.** Line descriptions, plan names and the PDF itself are English in every locale. This is the same accepted trade-off as #95 P3 and #96 P5.
- **P8. Some hosts will have both currencies.** A hostel whose country changed can have PKR and USD invoices side by side. That is correct per R2; never add a total.
