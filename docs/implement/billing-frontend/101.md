### Ticket (Trello #101, as retrieved 2026-10-18)

> Part of #93, section 9. Independent and small. Backend: merged in PR #26.
>
> The booking's confirmation PDF moved from a URL string to an attachment object. **Before:** `booking.confirmation_pdf_url` (string), now removed. **Now:** `booking.confirmation_pdf`, an attachment object `{id, file_name, content_type, url, …}`, or `null` until the booking is confirmed. It appears on host and guest booking payloads, and in booking search results.
>
> **Change:** link **Download confirmation** to `booking.confirmation_pdf.url`, and hide the link when `confirmation_pdf` is `null` (pending bookings).
>
> **Acceptance:** confirmed bookings show a working Download confirmation link, on host and guest screens. Nothing reads `confirmation_pdf_url` any more.

### What exists

**Frontend.** Nothing reads either field today, so this is an addition rather than a rename.
- **Guest:** model `ApiMyBooking` → `GuestBooking` (`features/user/bookings/my-bookings-api.ts:55-92`, `:172-214`); detail page `booking-detail.html`.
- **Host:** model `ApiHostBooking` → `HostBooking` (`features/host/bookings/host-bookings-api.ts:532-609`, `:627-665`); detail panel `booking-details-panel.html`.
- **Pattern to reuse:** the host invoice PDF button (`features/host/subscription/billing-invoice-detail.html:123-136`): `<a hh-button … target="_blank" rel="noopener noreferrer">` with `ti-download`, inside `@if (url)`.

**Backend** (`origin/main` @ `38ff508`).
- **Single bookings** (guest show/create, host show/create/update) carry `confirmation_pdf` through `AttachmentSerializer`: `id, file_name, content_type, url, …` (`booking_serializer.rb:11`).
- **Lists and search** carry the slimmer `{id, file_name, content_type, url}` from `search_data` (`booking_index.rb:77`). `PdfService.store` reindexes after storing.
- **When it becomes non-null:**
  - It is set asynchronously by `BookingConfirmationJob`, after commit, when the **disposition** becomes `confirmed` (`booking.rb:112-121`). That is not the payment status slug.
  - A failed store is swallowed, so a confirmed booking can stay `null` forever. Bookings confirmed before PR #26 are `null`.
  - The attachment survives check-in, check-out and cancel.
- **URL:** `IMAGES_HOST/unprocessed/<ns>/documents/<uuid>`, unsigned, no auth header.
- **Old field:** `confirmation_pdf_url` is dropped by migration `20261004160000`.

### Prior decisions in this area

- **#97:** PDF links are plain `<a>` with no auth, shown only when the URL is set.
- **#97 contrast:** invoices show "Preparing receipt…" while a paid invoice has no PDF. That works because "paid" is known. Here the card says to hide the link.
- **Copy:** `docs/knowledge-base/area/i18n.md` and the locale parity specs require every key in all 18 locales.

### Understanding

Add an optional `confirmationPdfUrl` (string | null) to `GuestBooking` and `HostBooking`, mapped from `confirmation_pdf?.url` and tolerant of both the list and the single shape. Render a **Download confirmation** link on:
- the guest booking detail page;
- the host booking details panel.

The link is shown only when the URL is present, and keyed off the field itself, not off any status. It opens in a new tab with `rel="noopener noreferrer"`. The new copy key goes into all 18 locales.

### Assumptions (stated at 1b)

1. **Placement:** detail screens only (guest booking detail, host booking details panel), not list rows or cards. That matches the invoice precedent and keeps the lists light.
2. **Visibility:** hidden whenever `confirmation_pdf` is `null`, including the short window after confirming and the permanent failure case, as the card says. No "Preparing…" state.
3. **Data source:** only the `url` field is read, so the list and single shapes both work.

## Plan

### Merged plan

1. **Wire and view field.**
   - Add `confirmation_pdf?: { url?: string | null } | null` to `ApiMyBooking` and `ApiHostBooking`.
   - Add `confirmationPdfUrl: string` (`''` when absent) to `GuestBooking` and `HostBooking`.
   - Map it with `confirmation_pdf?.url?.trim() ?? ''`. Only `url` is read, which fits both the list shape and the single shape. The attachment `id` is never read.
2. **Rule.** A pure helper per side, `confirmationLink(booking): string`, returns the URL or `''`. Whether a stage gate applies is decision D1 below.
3. **Guest.** A text link in the booking-detail reference strip (`booking-detail.html:92-112`), which is always visible.
   - It sits **outside** `@if (!finished())`, so checked-out guests keep the link.
   - Style: the local "Open in Maps" text-link style, with `ti-download`, `target="_blank" rel="noopener noreferrer"`, and the sr-only `userBookings.opensInNewTab`.
4. **Host.** A new "Confirmation" section in `booking-details-panel.html`, between the stay history and the invoice section, built the same way as the invoice block (uppercase label, then a brand text link).
5. **Copy.** `userBookings.downloadConfirmation`, `hostBookings.confirmation` and `hostBookings.downloadConfirmation`, in all 18 locales.
   - Add the host keys to `host-ops-locale-parity.spec.ts` `TRANSLATED_KEYS`.
   - Add a new parity spec for the user key.
6. **Fixtures.** The new field is required on `HostBooking`, so these literals get `confirmationPdfUrl: ''`: `testing/host-builders.ts`, `assign-rooms-panel.spec.ts`, `booking-calendar.spec.ts`, `booking-details-panel.spec.ts` and `host-bookings-table-cols.spec.ts`.
7. **Tests.**
   - Both mappers: list shape, single shape, `null`, missing key, `""`, and the legacy `confirmation_pdf_url` alone.
   - Both screens: shown, hidden, checked-out shown, plus the D1 and D2 cases.
   - The parity specs.
8. **Knowledge base.** A note in the area files that the link appears only on the next open after confirming, because the PDF job is asynchronous.
9. **Not in scope:** list rows; admin screens; email; a "Preparing…" state; polling; a regenerate button; a shared `Attachment` model; the `download` attribute (cross-origin, so ignored).
