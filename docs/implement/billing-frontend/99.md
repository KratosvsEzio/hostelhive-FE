1. **Banners on every host page**, driven by `billing.subscription`; dates in `hostel.timezone`.

   |---|---|

   A host API answering **400** "You need to subscribe to avail the services" also shows the blocking banner.
2. **CRM lock.** `has_crm` and `accepts_bookings` are on hostel **detail** payloads only (`/api/hostels/:id`, `/api/host/hostels/:id`, `/public/hostel_detail/:id`).

   - Nothing is deleted; buying a CRM plan unlocks at once and the flags update immediately.
3. **Guest Book button:** on the hostel detail page, **Book** only when `accepts_bookings` is true (else creating a booking → 422 "This hostel does not accept bookings").
- **Acceptance:** right banner per status on every host page, past-due and expired not dismissible · no-CRM hostel sees locked menu items and the upgrade screen, and a 403 `crm_required` the same · Book only when `accepts_bookings` · after paying for a CRM plan, locks disappear without logging out.

- A toast is shown for every status except 401 unless the request sets `SUPPRESS_ERROR_TOAST` (`core/tokens.ts:41`). A 400 or 403 from a host page currently toasts.

#### 2. Backend contract (`azeem-hamza/hostelhive@main`)

**Where the flags are serialized.**

- Source for `has_crm` in the host shell: `billing.features.includes('crm')` is equivalent.
  - `HostBilling.features` is `subscription.features` (`listing`, `boost`, `crm` where `feature?` is true).

  - `Hostel#feature?(:crm)` is the same call.
  - So the billing summary already carries what `has_crm` says, in one request, no extra fetch.
  - `/api/host/hostels/:id` is not usable for an expired hostel, because the 400 below fires first.

**CRM gate.** `app/controllers/api/host/host_controller.rb`:
```ruby
before_action :validate_hostel!
before_action :is_hostel_active?
before_action :require_crm!
def require_crm!
  return if current_user.admin? || @hostel.feature?(:crm)
  render_error_response({ code: "crm_required" }, :forbidden, ["Your plan does not include CRM"])
end
```
- The body is `{code:"crm_required", success:false, errors:["Your plan does not include CRM"]}` (`render_message_template.rb:16`).
- It covers every controller inheriting `Api::Host::HostController`:
  - bookings, booking_occupancies, dashboard, expenses
  - meal_confirmations, meal_types, mess_dashboard
  - renters, renter_bills, rooms, staffs
  - utility_bills, weekly_menus
- `HostelsController` (host) does `skip_before_action :require_crm!`. That is the hostel's own details and `index`.
- Admins bypass it.
- The `Api::Host::PaymentsController` named in `is_hostel_active?` was not found in `app/controllers/api/host`.

**Subscription gate.**
- The source is `is_hostel_active?` in the same controller: `render_400(["You need to subscribe to avail the services"]) unless @hostel.is_active || admin`.
- It is skipped only for `index` on `api/host/hostels` and `api/host/payments`.
- `is_active` is a stored copy of `subscription.live?`, written by `Billing::HostelSync` (`is_active: subscription&.live? || false`).
- `live?` is `status_slug_in?("active","past-due")`.
- So the 400 fires for no subscription, `incomplete`, `expired` and `canceled`. It does not fire for `past-due` or `active`.
- Order matters: the 400 runs before the CRM 403.
  - Expired plus CRM gives 400, matching the card.
  - A hostel with Listing only (no CRM) and an active status gives 403 `crm_required`.
  - A hostel with no plan gives 400, so the gate never shows `crm_required` for it.
- It applies to every `/api/host/hostels/:id/*` route, including `show`. The host `hostels#show` is also gated by `is_active`.

**Statuses and grace** (`subscription.rb`, `billing/lifecycle.rb`, `billing.rb`).
- Status slugs: `incomplete | active | past-due | expired | canceled`.
- `GRACE_PERIOD = 3.days` and `RENEWAL_LEAD = 7.days`.
- `grace_until = current_period_end + 3.days`.
- A past-due subscription is still live. Listing and CRM stay on and Boost drops (`feature?("boost")` requires `active?`).
- Lifecycle:
  - Active with the period over goes to `canceled` if `cancel_at_period_end`, else to `past-due`.
  - Past-due with `current_period_end <= now - 3 days` goes to `expired`.
  - `HostelSync` takes `is_active` false and, if the disposition is `active`, moves it to `inactive/subscription-ended`.
- So a canceled hostel is not live after the period end.
  - `cancel_at_period_end` with `status` still `active` is the "ends on" state, from #98.
  - The "canceled" banner (the card's `canceled` row) therefore appears only after the period end. At that point the host APIs already answer 400.
- The card's `expired` and `canceled` rows are both offline: the blocking 400 applies to each. They differ only in copy and CTA.

#### 5. Contradictions and gaps vs the ticket

1. **`code: "crm_required"` is dropped by the FE.** `error-interceptor.ts` sets `code` from the status only, so a 403 `crm_required` is not distinguishable from any 403 unless the interceptor or `ApiError` is extended. Fall back on the message text "Your plan does not include CRM" if not. Needs a decision (the mock side of `isSubscriptionError` has no CRM case either).
2. **Dates "in `hostel.timezone`" vs UTC.** The billing payload has no timezone and the controller serialises UTC.
   - `apiDate` renders in the offset the string carries, so with `Z` it shows UTC.
   - Prior decision (99.md house rules): "dates UTC until the backend timezone change".
   - Only a backend change (`include HostelTimeZone` after `load_hostel`) or a second fetch of `HostelsApi.getForEdit` fixes this.
   - The second option adds a request, is CanCan edit-gated and duplicates `apiDate`.
   - The countdown (days to `grace_until`) uses an instant, so it is unaffected. The date text can be a day off for a hostel in a far zone.
3. **"Which payload carries `has_crm` for the host shell" has no answer in the existing store.**
   - The host list (`HostListing`) lacks it, as does `HostBilling` (no flag, but it has `features`).
   - Choose between `billing.features.includes('crm')` (zero extra calls, once billing is a shared store) and fetching a hostel detail. The first is the cheaper source. Both are code-proven only, not live-verified.
4. **"Every host page" vs pages that already load nothing from billing.**
   - A banner needs a hostel-level billing fetch from the shell, not from each page. The shell currently fetches none.
   - `BillingApi` calls on `/api/hostels/:id/billing` need `core:Subscription:show`.
     - The backend authorises `show` on a `Subscription`, and non-owners (managers, wardens) usually lack it.
     - Managers would get a 403 and the shell would have no billing to render.
     - A banner then cannot show.
     - 99.md's "`core:Subscription:show|update` permissions fail open" applies to the nav entry, not the server.
   - Billing's own routes and payment-return pages are also under `/host/:id/…` and would show the banner. That may be undesired on the checkout page.
   - Hostels with no hostel selected, and `/host/hostels/new`, have no id. Mobile hosts see no sidebar (tab bar only), so the lock icon must also be in `More` and the tab bar.
5. **"Lock" vs the existing 400 paywall.** The two states already differ on the server. A no-plan hostel gets 400 on every host page, including pages that currently render `<hh-subscription-gate>` ("Unlock Dashboard overview… View plans & subscribe"). The card asks for the blocking banner on a 400, and "expired" shows the offline banner. It does not say whether the inline gate stays. This is a product decision.

#### Architecture

##### 1. Shared store and access events

**(a) `core/host-access/host-access.ts`**, with no `@services` imports, so there is no import cycle:
- A pure function `classifyHostAccess(url, err: ApiError)` that returns `{hostelId, kind: 'inactive' | 'crmRequired'} | null`.
- It matches the URL against `/\/api\/host\/hostels\/([^/?#]+)(?:[/?#]|$)/`.
- It returns `inactive` when the status is 400 and a server message matches `/need to subscribe/i`.
- It returns `crmRequired` when the status is 403 and `serverCode === 'crm_required'`. As a fallback, it also accepts the exact message "Your plan does not include CRM".
- `HostAccessEvents` (root): a signal of observations keyed by `{owner, hostelId}`. The owner comes from `SessionStore.user()?.id`.

**(b) `core/interceptors/host-access-interceptor.ts`**
- It records observations only.
- Register it in `app.config.ts:70-76` immediately before `errorInterceptor`. Errors travel outward through the chain, so it receives the normalized `ApiError`.

**(c) `services/host-billing-store.ts`**, `HostBillingStore`, root, modelled on `HostPropertyStore`:
- State is `{owner, hostelId, view: idle|loading|ready|forbidden|error, billing|null}`. Reads return nothing when the owner is not the session user.
- `track(hostelId)` fetches when the hostel changes. `refresh()` re-fetches.
- It skips the request and sets `forbidden` when `hasPermission('core:Subscription:show')` is false. That check fails open.
- It keeps the last billing visible while reloading the same hostel, so the banner does not flicker.
- `accept(hostelId, billing)` applies only if the hostel and owner still match. A successful load or `accept` clears that hostel's observations.
- It is a browser-only no-op on the server (`typeof window` guard, like the shell).
- **Derived values:**
- `live`: the status is `active` or `past-due`.
- `offline`: billing is ready and either there is no subscription or the status is `incomplete`, `expired` or `canceled`; or an `inactive` was observed.
- `crmLocked`: (live and `!features.includes('crm')`) or a `crmRequired` was observed; and never when `offline`; and never for frontend admin roles (backend `admin?` bypasses both gates).

**Refresh triggers**
- **Shell entry:** the `HostLayout` constructor runs `track(routeHostelId)` from an effect.
- **Hostel switch:** the same effect, because the `:hostelId` param changes on the same `HostLayout`.
- **Return from Safepay:** `/billing/payment/*` is outside the shell (`app.routes.ts:230-236`), so coming back re-creates `HostLayout`, which re-fetches. No special hook is needed.
- **Optional:** a throttled (60s or more) `visibilitychange` refresh. It covers a bank transfer verified while the tab stays open. Without it, "unlocks without logging out" needs a navigation in that case.

**`BillingPage` sharing.** Push from the page into the store; do not make the page read from the store. That leaves #98's `loaded` identity and epoch guard untouched.
- In the load pipeline: `switchMap(({id}) => api.billing(id).pipe(tap(b => store.accept(id, b)), …))`.
- In `runChange` `next`, inside `if (current())`: call `store.accept(id, billing)`.
- **Do not use an effect on `billing()`.** `toObservable` emits asynchronously, so for a moment `hostelId()` is already B while `state` still holds A. An effect would file A's billing under B.
- The cost is one duplicate GET when the billing page loads. That is acceptable and matches the page's "nothing cached" contract.

**When billing returns 403** (staff without `core:Subscription:show`):
- The store is `forbidden`. Banner and lock rely on observations only.
- The offline banner appears after the first 400 any page receives. Lock icons appear after the first `crm_required`.
- Calls to action switch to "ask the owner" text, because the billing page would only show its own 403 state.

##### 2. Banner and where it mounts

**Banner state** comes from a pure `bannerFor(billing, observed, nowMs)` in `shared/billing/billing-banner.ts`. One banner shows at a time, in this precedence:

| Kind | Condition | Tone | Dismissible | Call to action |
|---|---|---|---|---|
| `offline-expired` | status `expired` | danger | no | Renew |
| `offline-canceled` | status `canceled` | danger | no (recommended) | Choose a plan |
| `offline-none` | subscription null / `incomplete`, or observed 400 with billing unknown | danger | no | Choose a plan (incomplete: reuse `awaitingFirstPayment`) |
| `past-due` | status `past-due` | warn | no | Renew + countdown to `grace_until` |
| `cancel-pending` | `active` and `cancel_at_period_end` and less than 7 days to the end | info | yes | Resume (to billing) |
| `renewing` | `active` and not `cancel_at_period_end` and 0 < end − now < 7 days | info | yes | Renew |

**Time math is instants only**, so it is not money:
- `Date.parse(x) - now`, compared against `7*864e5`.
- The countdown shows whole days when 1 day or more remains, otherwise hours, otherwise "less than an hour". Format it with `Intl.NumberFormat(locale, {style:'unit', unit:'day'|'hour', unitDisplay:'long'})`. There is no Transloco plural plugin, so this gives correct plurals without per-count keys.
- `now` is a signal ticking every 60s through `setInterval`, cleared via `DestroyRef`. Never use `afterNextRender`.
- The clamp after `grace_until` is reached: show "less than an hour" and run `store.refresh()` once.
- Dates use the `apiDate` pipe and are UTC until the backend change in 95 D4.

**Dismissal**: store the key in sessionStorage as `{owner, hostelId, kind, current_period_end}`, so a new period shows the banner again.

**Exclusions**: hide the banner when `hostPagePath(router.url)` starts with `subscription`. The billing page shows the same state with the actions. The payment-return pages are already outside the shell.

**Layout change** (`host-shell.html:349-354`):
- The content div becomes `flex flex-col`.
- The banner is `shrink-0`.
- `<router-outlet/>` moves into a new wrapper `<div class="relative min-h-0 flex-1">`. Do **not** make the outlet a direct flex child. That would turn the routed host element into a flex item with auto height, and `app-dashboard-layout`'s `h-full` would compute to auto, which kills the inner scroll on every page. A flex item that has been sized is treated as having a definite height, so the existing percentage-height chain keeps working.
- This must be checked in the browser on desktop and on a mobile width with the tab bar.

**How pages report the 400**: through the interceptor (option 1), not per page. Mess, expenses and team never call `isSubscriptionError`, and only the interceptor covers them without touching those pages.

#### Technical requirements
1. No banner, lock or Book decision ever computes money. Time differences between server instants are the only arithmetic.

### Product framing: Trello #99 (grace and renewal banners, CRM lock, guest Book button)

#### Problem and intent

Billing (#95–#98) now sells three plans: Listing, Listing + Boost, and Listing + Boost + CRM. But the console still behaves as if there were only "has a plan" or "has none". This leaves three gaps:

1. **Hosts don't see trouble coming.** Nothing outside the Billing page says a plan is about to renew, is past due, or that the hostel has gone offline. The first sign is a failed page load, an error toast, and in some pages a paywall reading "Unlock Dashboard overview" with hard-coded English benefits.
2. **Listing-only hosts hit dead ends.** A host on a plan without CRM opens Rooms and gets a generic error. Today the frontend cannot tell a `403 crm_required` from any other 403, because the error interceptor drops the body's `code`.
3. **Guests can start a booking the hostel can't take.** A nightly hostel without CRM shows **Book**, and the guest only finds out at the end with a 422 "This hostel does not accept bookings".

The goal is that every host page says plainly what state the plan is in and what to do next. A Listing-only host should understand CRM as an upgrade, not a fault. And guests should only see Book where a booking can actually be made.

#### Who is affected and how

| Party | Today | After #99 |
|---|---|---|
| **Owner** (has `core:Subscription:show`) | No status signal outside Billing; generic errors or the old paywall | One banner on every host page; lock icons on CRM pages; a locked screen with **Upgrade**; locks clear right after paying |
| **Staff** (manager, warden; no `core:Subscription:show`, so the billing call returns 403) | Same generic errors | No billing data, so nothing shows in advance. When the server refuses, they get an "offline" banner or the CRM locked screen worded as "ask the hostel owner", with no buttons that lead to pages they can't open |
| **Guest** | Book shows on a nightly hostel without CRM, then fails with a 422 | Book only when `accepts_bookings` is true; otherwise the same enquiry path monthly hostels already have |
| **Admin** | The server never applies the CRM gate to admins (`host_controller.rb` `require_crm!`) | No lock icons for admins, because the pages work for them |

#### Banner rules

- **Data source.** A shared billing store for the active hostel feeds all banners. It loads `GET /api/hostels/:id/billing`, which is not behind the CRM or `is_active` gates.
- **At most one banner at a time**, in this priority order: offline (no plan, expired, canceled, or a 400) > past due > ending (cancel pending) > renewing.
- **Placement.** The banner sits at the top of the content column, above the page, and never scrolls the page's own content out of view.
- **Chrome.** Use the tone rows in `design-mockups/31-overlays.html:349-351`: info is sky, warn is `warn/5`, danger is `danger/5`. The CTA is a small button on the right, as in `30-design-system.html:452`.
- **Dates and countdown.** Dates use `apiDate`, which shows UTC until the backend timezone change lands (95 D4). The countdown is worked out from instants, so it is correct in any timezone.

#### Acceptance criteria

##### A. Banners

1. **Renewing soon.**
 - Given an owner on hostel H with `status.slug = active`, `cancel_at_period_end = false`, and `current_period_end` less than 7×24h away.
 - When any host page under `/host/H/…` loads (except the billing pages, AC 14), an info banner reads "Your plan renews on {date}." with a **Renew** button that goes to `/host/H/subscription`.
 - If `scheduled_plan` is set, the text is instead "Your plan switches to {plan} on {date}."
2. **Renewing, not yet due.** Given the same, but 7 days or more remain, no banner shows.
3. **Renewal date already passed.** Given `active` with `current_period_end` in the past (the lifecycle job hasn't run yet), the info banner reads "Your plan is due for renewal." with **Renew**. It never shows a negative or past countdown.
4. **Renewing banner can be dismissed.**
 - Given the renewing banner, when the owner clicks × (aria-label "Dismiss"), it disappears.
 - It stays hidden after reloads, logging out and back in, and visiting other pages, for that user, that hostel, and that `current_period_end`.
 - It comes back for the next period, and on another browser.
5. **Plan ending (cancel pending).**
 - Given `active` with `cancel_at_period_end = true` and `current_period_end` less than 7 days away, an info banner reads "Your plan ends on {date}. After that your hostel goes offline." with **Resume plan** going to `/host/H/subscription`.
 - It can be dismissed under the same rules as AC 4.
 - No "renews" text ever shows while a cancel is pending.
6. **Past due.**
 - Given `past-due` and `grace_until` in the future, a warn banner shows with no ×.
 - It reads "Your subscription ended on {current_period_end}. Your hostel stays live until {grace_until}."
 - Then " Boost is paused." is added **only** if `subscription.plan.features` includes `boost`.
 - Then a countdown and a **Renew** button.
7. **Countdown wording.** Let `ms = grace_until − now`:
 - `ms` ≥ 48h: "{n} days left", where n = ceil(ms / 24h).
 - 24h ≤ `ms` < 48h: "1 day left". Note that ceil gives 2 for anything over 24h, so this range needs its own rule; state it explicitly in the code.
 - 0 < `ms` < 24h: "Less than a day left".
 - The countdown refreshes at least once a minute while the page is open, and on returning to the tab.
8. **Grace ended, but the job hasn't run.**
 - Given `past-due` and `grace_until` ≤ now, the warn banner (no ×) reads "Your grace period is over. Your hostel goes offline shortly. Renew now to keep it live." with **Renew**.
 - No countdown shows.
 - The pages still work, because the server still treats the hostel as live.
9. **Expired.** Given `expired`, a danger banner with no × reads "Your hostel is offline. Renew to go live again." with **Renew**.
10. **Canceled.** Given `canceled`, a danger banner with no × reads "Your plan ended on {current_period_end}. Choose a plan to put your hostel back online." with **Choose a plan**.
11. **No plan.**
  - Given `subscription = null`, or `incomplete` with no open invoice, a danger banner with no × reads "Your hostel isn't live yet. Choose a plan to list it on HostelHive." with **Choose a plan**.
  - Given `incomplete` with an `open_invoice`, the text is "Your hostel goes live once your plan is paid." with **Pay**, going to `/host/H/subscription`.
12. **400 "You need to subscribe…".**
  - Given any `/api/host/hostels/H/*` request returns 400 with an `errors[0]` matching "You need to subscribe", the page shows the offline banner. Its wording follows the refreshed billing status (AC 9–11), and the billing store is fetched again.
  - If billing can't be read, the owner sees "Your hostel is offline. Renew or choose a plan to put it live." with **Go to billing**.
  - In every case there is no error toast for that 400, and the page body shows the offline locked state (AC 19), not a generic error.
13. **Staff and the offline state.**
  - Given a session known to lack `core:Subscription:show` (or one whose billing call returned 403), no proactive banners show (AC 1–11).
  - On a 400 as in AC 12, the banner reads "This hostel is offline. Ask the hostel owner to renew its plan." with **no** button.
14. **Billing pages.**
  - Under `/host/H/subscription/**` (billing page, pay step, billing history), no banner shows. Those pages already show the status, and the button would link to the page the host is on.
  - The public payment-return pages are outside the console shell and show no banner either.
15. **Switching hostel.**
  - Given banners for hostel A, when the host switches to B, A's banner is removed immediately.
  - Nothing shows until B's billing loads, then B's banner (if any) appears. A dismissal for A never hides B's banner.
16. **Mobile.**
  - Below 768px, the banner appears above the page and wraps to at most three lines plus its button.
  - It never covers the bottom tab bar or the header.
  - The page underneath still scrolls fully, including its last row.
17. **Accessibility.**
  - The banner is a landmark labelled "Plan status".
  - A change of banner while on the same page is announced politely. Simply moving to another page is not re-announced.
  - Icons are hidden from screen readers. The × has the accessible name "Dismiss".

##### B. CRM lock

18. **Lock icons.**
  - Given an owner whose hostel billing `features` does not include `crm`, the sidebar, the mobile More page and the bottom tab bar show a lock icon on these entries: Rooms, Bookings, Tenants, Team & staff, Utilities, Mess, Expenses, Invoices, and Overview (see Q2).
  - Each locked entry's accessible name ends with "needs a plan with CRM". Hostel profile and Billing never get a lock.
  - While billing is loading or unknown (staff, error), no locks show. This fails open, like the permission flags.
19. **Locked entries are still links.**
  - Given a locked entry, when it is clicked, the page opens and its body shows the CRM locked screen.
  - Title: "Upgrade to unlock CRM".
  - Body: "Upgrade to a plan with CRM to manage rooms, bookings, tenants, bills and staff."
  - Reassurance line: "Nothing you've added is deleted. It's all here when you upgrade."
  - Button: **Upgrade**, going to `/host/H/subscription`.
  - There is no error toast and no generic error state.
20. **Any 403 `crm_required`.**
  - Given any host API returns `403` with body `code: "crm_required"`, the same locked screen shows (Q4 covers the fallback).
  - The billing store is fetched again, so stale locks fix themselves.
  - Other 403s, such as a staff permission refusal, never show the locked screen or the old paywall.
21. **Staff and the CRM lock.** Given staff hit a 403 `crm_required`, the locked screen reads "This hostel's plan doesn't include CRM. Ask the hostel owner to upgrade." with no button.
22. **400 comes before CRM.** Given an expired hostel whose plan included CRM, opening Rooms shows the offline banner and offline body (AC 12), not the CRM screen. The server answers 400 first; the frontend must not swap the order.
23. **Unlocking without logging out.**
  - Given a no-CRM hostel, when the owner pays for a CRM plan and comes back to the console, the locks are gone with no reload and no logout.
  - "Comes back" means the success page's **Go to billing**, or any page next visited in the same tab.
  - Opening Rooms then loads the rooms list.
  - The same applies after any billing write in the billing page; the store takes the response.
24. **Nothing is lost.** Given a host who had rooms, tenants and similar records before losing CRM, after upgrading those records reappear unchanged. The frontend never clears cached host data on lock.

##### C. Guest Book button

25. **Book only when allowed.** Given `/public/hostel_detail/:id` returns `accepts_bookings: true` and the hostel bills nightly, the booking rail with **Book now** or **Sign in to book** shows, as today.
26. **Not accepting bookings.**
  - Given `accepts_bookings: false`, no booking rail and no room-picker booking controls show.
  - The room cards and the call/WhatsApp enquiry path show, exactly as for a monthly hostel.
  - There is no "not accepting bookings" message.
27. **Field missing.** Given `accepts_bookings` is absent from the payload (older cache or serializer), the current nightly rule applies unchanged. This fails open, matching the reasoning in the `billing_frequency` decision.
28. **Late 422.** Given a guest who opened the page while booking was allowed, a 422 "This hostel does not accept bookings" on confirm shows verbatim in the summary modal, as today.
