#### 3. Backend contract

`hostel_billing_controller.rb` (`Api::HostelBillingController`, `include ::BillingAccess`):

```ruby
before_action -> { authorize!(:update, subscription) }, only: [:schedule_downgrade, :unschedule_downgrade, :cancel, :resume]
def schedule_downgrade; Billing::PlanChanges.new(@hostel).schedule_downgrade(find_plan); show; end
def unschedule_downgrade; Billing::PlanChanges.new(@hostel).unschedule_downgrade; show; end
def cancel;  Billing::PlanChanges.new(@hostel).cancel;  show; end
def resume;  Billing::PlanChanges.new(@hostel).resume;  show; end
def find_plan; Plan.active.find(params.require(:plan_id)); end
```

| Endpoint | Method | Params | Service call |
|---|---|---|---|
| `/api/hostels/:hostel_id/subscription/schedule_downgrade` | POST | `plan_id` (required, obfuscated id) | `schedule_downgrade(plan)` |
| `/api/hostels/:hostel_id/subscription/schedule_downgrade` | DELETE | none | `unschedule_downgrade` |
| `/api/hostels/:hostel_id/subscription/cancel` | POST | none | `cancel` |
| `/api/hostels/:hostel_id/subscription/cancel` | DELETE | none | `resume` (the controller action is `resume`) |

- **Authorization:** CanCan `Subscription :update` on `@hostel.subscription || @hostel.build_subscription`. A failure is a 403 with the `{error}` shape. The permission is `core:Subscription:update`.
- **Response:** All four end with `show`, which renders the full `{ billing: Billing::Summary.new(@hostel).as_json, success: true }` with status 200, the same object as `GET /billing`.
  - The plain `BillingEnvelope` map in `BillingApi.billing()` works.
  - The summary is built after the change, so `subscription.scheduled_plan` / `cancel_at_period_end` and each plan's `scheduled` reflect it.

**422 messages (`Billing::Error`, rendered as `{errors:[msg], success:false}` by `BillingAccess`)**

| Operation | 422 messages (verbatim) |
|---|---|
| All four | `There is no active subscription` (raised by `require_active!` when the subscription is missing or its status is not `active`, which covers past-due, expired, canceled, incomplete and none) |
| `schedule_downgrade` | `This plan is not available` (plan is nil or not active) |
| | `This plan is not available in #{currency}` (no price in the subscription's currency) |
| | `Only a cheaper plan can be scheduled; upgrade through checkout` (new price >= current price, so scheduling the current plan also hits this) |
| `unschedule_downgrade` | None for "nothing scheduled". It returns the subscription unchanged and **succeeds** (idempotent). |
| `cancel` | None for "already cancelled". It just sets the flag again and succeeds. |
| `resume` | None for "not cancelled". It succeeds. |

- **Other statuses:**
  - An unknown `plan_id` gives a 404 via `Plan.active.find`: `{errors:["Requested resource not found."]}`. This is inferred from the shape in the 95 report.
  - A missing `plan_id` gives a 400 or 422 from `params.require` (not verified; the report assumes a 400).
- **Interaction between downgrade and cancel:** There is **no** interaction in the code.
  - `schedule_downgrade` does not check or clear `cancel_at_period_end`, and `cancel` does not clear `scheduled_plan_id`. Both can be set at once.
  - In `Lifecycle.advance_subscriptions`, `cancel_at_period_end` wins at period end (transition to `canceled`).
  - `issue_renewals` skips subscriptions with `cancel_at_period_end: true`, so the scheduled plan never takes effect.
  - So the card UI can legitimately show "Ends on …" and "Switches to …" together. That is misleading, so it needs a UX decision (see section 7).
  - The same goes for offering Cancel while a downgrade is scheduled, and the reverse.
- **Events:** `record!` writes `downgrade_scheduled`, `downgrade_unscheduled`, `cancel_scheduled`, `cancel_unscheduled`. These are not exposed to the FE.
- **Downgrade eligibility:** Which plans are `action: "downgrade"` is decided by `Summary` (a cheaper plan). The server re-validates the same rule.
- **Active only:** An `active` subscription is the only one that can use these. The `past-due` / `expired` / `canceled` / `incomplete` / none cases get "There is no active subscription".
  - The FE gets `action: renew` / `buy` for those, not `downgrade`, so downgrade buttons rarely appear then.
  - A Cancel/Resume control still needs a gate on `sub.status.slug === 'active'`.

#### 7. Contradictions, gaps, staleness

1. **Billing state cannot be set from a response.** `state` is a `toSignal` over a pipeline. The card requires re-rendering "from each response without a reload". The page needs a writable override. This is the main structural change.
2. **`switchesTo` has no date.** The card and the ticket want "Switches to {plan} on {date}". The key's current value is "…at renewal". The key, its 18 translations and `current-plan-card.spec.ts` need to change (or add a new key and retire the old one).
3. **Downgrade and cancel can coexist on the server, with no clearing either way.**
   - Neither the controller nor the service guards it.
   - When cancel wins at period end, the scheduled plan is dead.
   - The ticket is silent. Decide in the 2d interview: hide Cancel while a downgrade is scheduled, auto-undo one when the other is applied, or show both lines and let the server decide.
   - Likewise, scheduling a downgrade while `cancel_at_period_end` is set is allowed server-side.
4. **Idempotent no-ops.** Undo with nothing scheduled, a second Cancel, and Resume when not cancelled all return 200 with the current billing. The ticket's "no scheduled plan to undo" and "already cancelled" errors **do not exist**. Only these 422s exist: "There is no active subscription", "This plan is not available", "This plan is not available in {currency}" and "Only a cheaper plan can be scheduled; upgrade through checkout".
5. **Permission.** The backend gates on `core:Subscription:update`. The FE gates on `core:Invoice:create` (`canCheckout`) and the copy `ownerOnly` for checkout. Plan changes should probably use `core:Subscription:update` with its own 403 copy; `checkoutForbidden` says "buy plans", which is wrong here. This is a decision for 2d.
6. **Mockup is the legacy model.** It matches only in layout (a quiet text-link "Cancel plan").
7. **Ticket vs code on the Undo for the scheduled plan:** the ticket wants the scheduled plan's button to show "Scheduled" plus Undo. Today the badge is separate from the button (a neutral `hh-status-pill` above a disabled "Switch at renewal" button). The new state needs a design: keep the disabled button plus the badge and add an Undo link, or replace the button.
8. **Staleness:** The knowledge base area file `host-billing-and-subscription.md` is known to be stale (95 report), and its decision `lapsed-hostel-keeps-three-pages-open.md` is Superseded. Neither conflicts with this ticket.
9. **Conflicts with prior decisions:** None. D6's "#98 enables it in one handler" still holds, and the handler is `onPlanAction`'s `kind !== 'checkout'` early-return.
10. **Injection attempts:** None seen.

#### 1. Re-rendering from an action response

**Recommendation: a `linkedSignal` over the existing pipeline, plus a load epoch.** Do not restructure the pipeline.

```ts
private readonly loaded = toSignal(/* existing pipeline unchanged */, { initialValue: { kind: 'loading' } as BillingView });
protected readonly state = linkedSignal<BillingView>(() => this.loaded());
// on success, after the guard:
if (this.loaded() !== epoch) return;      // epoch = this.loaded() captured at click time
this.state.set({ kind: 'ready', billing });
```

**Why this design works:**
- Every reload makes `loaded` emit a new object: a hostel switch, `retry()`, or the 404/transfer refresh, each of which starts with a `loading` object. That resets `state` and discards the override automatically.
- `billing`, `planViews` and the template keep reading `state`, so their code does not change.

**Why use an epoch rather than `hostelId() !== id`.**
- The existing guard misses A→B→A. A response from the first visit to A would land on top of the fresh GET from the second visit, and could overwrite newer data.
- It also misses a `retry()` that happens while an action is in flight.
- Capturing `this.loaded()` identity at click time covers all three cases with one comparison.
- Keep the `hostelId` guard as well for readability. Also clear pending/error on a mismatch, which the `linkedSignal` already does for a hostel change.

**`retry()` interaction:**
- An override is dropped on the next reload, which is correct because the GET is fresher.
- An action response that arrives after a reload is dropped. This is safe because the server change is already committed and the GET reflects it.
- If that GET started before the commit, the page could show stale data. In practice this is unreachable, because only one action can be pending at a time and the UI cannot trigger `retry()` from the ready state.

**Rejected alternatives:**
- `retry()` after each action: an extra GET, a skeleton flash, and it fails the "render from the response" acceptance.
- A separate `WritableSignal<HostBilling|null>` override: it needs manual resets on hostel and refresh, which is the job `linkedSignal` already does.
- Rewriting into `resource()`/`rxResource`: churn, and the forbidden/network-error mapping would have to be re-derived.

#### 6. Downgrade and cancel can both be set on the server

Neither endpoint clears the other's flag. At period end `cancel_at_period_end` wins, and `issue_renewals` skips cancelling subscriptions, so the scheduled plan never takes effect.

#### Edge cases and failure modes

- **Response for an old hostel or an old load:** dropped by the epoch guard, with pending and error reset by the `linkedSignal`. The server change is already committed and the next GET shows it.
- **Scheduling plan C while plan B is scheduled:** the server replaces the schedule, and the response re-renders B as `downgrade` and C as `scheduled`. Leave B's button enabled.
- **Focus loss:** after Undo or Resume the clicked control disappears, so focus drops to `<body>`. Move focus to the card heading, or make the card's status lines `aria-live="polite"`. Recommend `aria-live` on the line container, which is the cheapest.
- **Dialog dismissal:** a backdrop click emits `cancel`. The handler only clears the dialog signal, with no side effects.
- **Missing period end:** if `current_period_end` is null, the `apiDate` pipe yields an empty date. Hide Cancel plan and the downgrade button when there is no `current_period_end` rather than show "on ." (this is theoretical for an active subscription).
- **Status other than active with `scheduled_plan` set:** for example past-due. Keep the line, as today, with no Undo (the server would return 422).
- **Open upgrade invoice plus a scheduled downgrade:** the server allows both. This is out of scope; note it for PM.

#### Technical requirements

1. There is no extra GET after a successful action; the page renders from the action's response.
2. A response is applied only if `loaded()` is the object captured at click time.
3. At most one billing write is in flight per page. Every entry point checks `busy()`.
4. All four calls use `quiet()` and send ids exactly as returned.
5. A 403 never shows server text. A 422 shows `errors[0]` verbatim.
6. Dates use `apiDate: 'd MMM yyyy'` and money still goes through `billingMoney`; no computation.
7. Gates pass: `npx nx test web`, `npx nx build web` (i18n-check), `npx tsc -p apps/web/tsconfig.app.json --noEmit`, eslint.
8. All 18 locales gain the new keys with matching params, and none carries `switchComingSoon`.
9. No `afterNextRender`. No ticket references in code comments.

### Product Manager report (2b)

### Product framing for Trello #98: plan changes (schedule a downgrade, cancel and resume)

The backend has two flaws that matter most here. A **renewal invoice that is already open stays open after a host schedules a downgrade, undoes one, or cancels** (Q2 and Q3 below), and the server lets a downgrade and a cancellation both be set at the same time (Q1). Both need a decision at the 2d gate.

#### Problem and intent

A host on an active paid plan should be able to pay less from the next period, or stop paying, without contacting us. Today the "Switch at renewal" button is a disabled stub with "contact us", and there is no way to cancel at all. Both changes take effect at the end of the current period, need no payment, and nothing is refunded.

The deeper intent is trust. The host must see exactly what will happen and when, be able to change their mind (Undo / Resume), and never be surprised by a charge or by the listing going offline.

#### Affected parties and impact

- **Hostel owner** (`core:Subscription:update`):
  - The plan grid gets a working "Switch at renewal" on cheaper plans.
  - The current-plan card gets "Switches to {plan} on {date}" with Undo, "Ends on {date}" with Resume, and a quiet "Cancel plan".
- **Staff without `core:Subscription:update`**: they see the states but get no controls, plus the existing "Only the hostel owner can change the plan." line.
- **Renters and seekers**: after a cancellation reaches the period end, the listing goes offline. A cancelled subscription goes straight to `canceled` with **no 3-day grace**, unlike an unpaid one (`lifecycle.rb` `advance_subscriptions`). Listing, CRM and Boost all switch off (`subscription.rb` `live?`, `feature?`), and the listing is moved to inactive / subscription-ended (`hostel_sync.rb` `listing_state`).
- **Communications**:
  - Nothing is sent when a host schedules, undoes, cancels or resumes (`plan_changes.rb` only writes events).
  - At the period end, the existing `subscription_ended` email announces the cancellation (`lifecycle.rb` `transition`).
  - Renewal invoices are not issued while a cancellation is pending (`issue_renewals` skips `cancel_at_period_end`). Reminders for a renewal invoice that is **already open** are still sent (`send_renewal_reminders` checks only `active?`). See R2.

#### Acceptance criteria

**Downgrade: schedule and undo**

1. **Given** an active subscription and a plan whose `action` is `"downgrade"` and `scheduled` is false, and the session does not lack `core:Subscription:update`, **when** the host clicks "Switch at renewal", **then** a confirm dialog opens with the downgrade title and message (copy below), naming the target plan, the current plan and `current_period_end` (UTC, `d MMM yyyy`).
   - The "Replace the unpaid invoice?" dialog (#95 D5) is never shown for a downgrade.
2. **Given** the downgrade dialog is open, **when** the host confirms, **then**:
   - exactly one `POST /api/hostels/:id/subscription/schedule_downgrade {plan_id}` is sent with the plan's id as returned;
   - the confirm button shows a loading state and is disabled until the response arrives.
3. **Given** that request returns 200, **then**, without any `GET /billing` and without a page reload:
   - the dialog closes;
   - the current-plan card shows "Switches to {scheduled_plan.name} on {current_period_end}" and an **Undo** control;
   - that plan's button reads "Scheduled" (disabled) with an **Undo** control under it;
   - every other downgrade plan still shows "Switch at renewal".
4. **Given** the host dismisses the dialog (the Cancel button, the backdrop or Esc), **then** no request is sent and nothing changes.
5. **Given** a downgrade is scheduled, **when** the host clicks Undo (on the card or on the plan), **then**:
   - exactly one `DELETE …/schedule_downgrade` is sent, with no confirm dialog;
   - on 200 the "Switches to" line and both Undo controls disappear;
   - that plan's button returns to "Switch at renewal", re-rendered from the response alone.
6. **Given** the schedule request fails with a 422, **then** `errors[0]` is shown verbatim in the alert block under that plan's button, and the dialog is closed. Examples: "Only a cheaper plan can be scheduled; upgrade through checkout", "This plan is not available", "This plan is not available in {currency}", "There is no active subscription".
   - For "There is no active subscription", "Only a cheaper plan…" and a 404, the billing data is refreshed so the screen shows the true state, and the message stays visible after the refresh.

**Cancel and resume**

7. **Given** an active subscription with `cancel_at_period_end: false`, **then** a quiet "Cancel plan" control shows at the bottom of the current-plan card. It is never shown for past-due, incomplete, expired or canceled statuses, or when there is no subscription.
8. **When** the host clicks "Cancel plan", **then** a danger-toned confirm opens with the cancel copy below. The dismiss button reads "Keep my plan", never a bare "Cancel".
9. **When** the host confirms, **then**:
   - exactly one `POST …/subscription/cancel` is sent;
   - on 200, from the response alone: the card's "Renews on {date}" becomes "Ends on {current_period_end}", "Cancel plan" disappears, and **Resume plan** appears.
10. **When** the host clicks "Resume plan", **then**:
    - exactly one `DELETE …/subscription/cancel` is sent, with no confirm dialog;
    - on 200 the card shows "Renews on {date}" again, Resume disappears, and "Cancel plan" returns.

**Shared**

11. **Re-render without reload.** For each of the four actions, a 200 response's `billing` object replaces what the page shows, with no extra `GET /billing` and no navigation:
    - the current-plan card;
    - the plan grid (buttons, badges, `scheduled`);
    - the open-invoice card;
    - the features list.
12. **403 handling.** A 403 on any plan-change action shows "You don't have permission to change this hostel's plan." The server's 403 text is never shown.
13. **Generic failures.** A network error, a 5xx, or a 4xx with no message shows the per-action generic copy below.
    - Errors for Undo, Cancel or Resume render in an alert under the control in the current-plan card.
    - Errors for a schedule render under the plan's button.
14. **One action at a time.** While any plan-change request is in flight, every plan-change control and every checkout button on the page is disabled. A double click sends one request.
15. **Hostel switch:**
    - switching hostel while a confirm dialog is open closes it and sends nothing;
    - a response that arrives after a switch is discarded and never renders onto the new hostel;
    - pending, error and dialog state reset per hostel.
16. **Permissions:**
    - When the session's flags show `core:Subscription:update` is absent: Undo, Cancel plan and Resume plan are hidden, the downgrade buttons are disabled, and "Only the hostel owner can change the plan." is shown.
    - When the flags are missing entirely (fail open), the controls show and a 403 falls through to AC 12.
17. **Retired copy.** The "coming soon — contact us" hint no longer appears anywhere. `hostBilling.switchComingSoon` is removed from all 18 locales and added to `RETIRED_KEYS`.
18. **Past-due.** On a past-due subscription, no Undo, Cancel or Resume is shown, and no "Switches to …" line is shown. The date would be in the past, and the open renewal invoice is what decides the plan.
19. **Downgrade and cancel together.** Behaviour follows the decision on Q1. With my recommendation:
    - while `cancel_at_period_end` is true, the card shows only "Ends on" plus Resume;
    - downgrade buttons are disabled with "Resume your plan to switch at renewal.";
    - a cancel confirm while a downgrade is scheduled adds the "won't happen" line.
20. **Screen readers.** The current-plan status lines are inside an `aria-live="polite"` region, so the change is announced after each action. Both Undo controls have the accessible name "Undo the switch to {plan}".

#### Recommendation on downgrade and cancel at the same time

**Recommend:** show Cancel always, hide downgrading while a cancellation is pending, and explain in the cancel dialog.

- **Never hide Cancel.** Making it harder to leave (option "hide Cancel while a downgrade is scheduled") forces an extra Undo and reads as a dark pattern.
- **While `cancel_at_period_end` is true:**
  - the card shows only "Ends on {date}" plus Resume;
  - the "Switches to" line, both Undo controls and the "Scheduled" state are suppressed, because they won't happen;
  - downgrade buttons are disabled with "Resume your plan to switch at renewal.".
- **Cancel confirm while a downgrade is scheduled** adds "Your scheduled switch to {plan} won't happen."
- **Reject "auto-clear the other".** That is two non-atomic requests, with partial-failure states the FE would have to explain.
- **Reject "show both with a note".** It shows a promise the server will break.
- **Resume caveat:** Resume brings the scheduled switch back on the server. The card re-renders from the response and shows it again, which is honest.
- **Backend follow-up (Hamza):** `cancel` should clear `scheduled_plan_id`, so Resume doesn't revive a switch the host was told "won't happen". After that, the FE needs no change.

#### Cancel as a quiet text link

**Recommend yes.** Use `hh-button variant="text" color="default" size="sm"` labelled "Cancel plan", left-aligned at the bottom of the current-plan card (the existing `<ng-content />` slot). Make it a real `<button>`, not an anchor, with a touch target of at least 44 px.

#### Product risks (backend facts, verified in source)

- **R1 (high).** Scheduling a downgrade after the renewal invoice is issued, which happens from 7 days before the period end:
  - the open invoice stays on the **old, more expensive** plan until `grace_until`;
  - `issue_renewals` won't issue a new one while it is open;
  - paying it renews on the old plan and **clears** `scheduled_plan`.
  - The switch silently never happens and the host pays more. Undo has the mirror problem: an open renewal invoice for the cheaper plan still downgrades when paid.
- **R2 (medium).** Cancelling after the renewal invoice is issued: the invoice stays open with Pay visible, and reminders are still emailed 3 days and 1 day before. Paying it extends the period, but `cancel_at_period_end` stays true.
- **R3.** A cancellation goes offline at the period end with no grace period. The copy says "after that your hostel goes offline", which is accurate.
- **R4.** If the scheduled plan is deactivated, the renewal invoice fails to issue (only logged) and the hostel drifts to past-due.
- **R5.** Dates are UTC until the backend timezone fix. A period ending late UTC can show the day before the PKT date.

## Summary

Plan changes are live on the billing screen.
- **Downgrade:** a host can schedule a downgrade for renewal (with a confirm), and undo it from the current plan card or from the plan.
- **Cancel / resume:** a host can cancel at period end (with a danger confirm) and resume.
- **Rendering:** every action renders from the response with no reload. One billing write is allowed at a time per page, and a late answer can never land on another hostel or on a newer load.
- **Downgrade and cancel together:** cancelling hides the switch line and Undo. While cancelling, downgrades are disabled with a resume hint (D1).
- **Open renewal invoice:** the confirms warn when a renewal invoice is already open (D2).
- **Errors:** a 403 shows our own copy; a 422 or 404 shows the server message verbatim and triggers a refresh (D4).
