   - A payment whose `failure_reason` says "refund it from the Safepay dashboard" needs a manual refund — **highlight it**.
   - Date filters: see #90 (admin dates are UTC).
3. **One hostel's billing:**
   - `GET /api/admin/hostels/:id/billing` → `{billing: {…same as host /billing…}, billing_currency_override, events: [{kind, data, invoice, created_at}]}`.
   - `POST …/grant {plan_id, months}` (creates a free paid invoice); `PUT …/billing_currency {currency}` (`""` clears; applies from next renewal).
   - Show the summary + an **events** timeline (activated, renewed, upgraded, payment_failed, granted …).
4. **Plan price editor:** `GET /api/admin/plans` → `{plans: [{id, code, name, active, position, features, prices: {PKR, USD}}]}`; `PUT /api/admin/plans/:id {plan: {name, active}, prices: {PKR, USD}}`. New prices apply to new invoices only.
- **Revenue is always shown per currency. Never add PKR and USD together.**
- **Acceptance:** queue verifies and rejects (with reason), row leaves the queue · payments and invoices lists filter by status and paginate · hostel billing page shows summary + events; grant and currency override work · plan editor saves PKR and USD prices.

##### 3. Backend contract (`azeem-hamza/hostelhive@main`)

**Routes** (`config/routes.rb:66-86`)
```
namespace :admin
resources :payments, only: [:index, :show] { put :verify; put :reject }
resources :invoices, only: [:index, :show]
resources :plans, only: [:index, :update]
scope 'hostels/:hostel_id', controller: :hostel_billing { get :billing => show; post :grant; put :billing_currency }
```

**Authorization**
- `AdminController#authenticate_admin!` is `render_403 unless current_user.admin?`.
- `admin?` is `roles.any?(&:is_admin?)`.
- There is no CanCan on these controllers. Moderators get 403 on every endpoint. Super-admin is assumed to have `is_admin`; I did not read the roles seeds.

**Payments index: `GET /api/admin/payments`**
- **Params:**
- `page`, and `limit` (default 30; the frontend's `pageParams` sends `limit`).
- `f[...]` filters, `s[...]` match queries and `sort[...]`. The default sort is `created_at desc`.
- Date filters are `f[created_at][gte]` and `f[created_at][lte]`. A hash with `gte` or `lte` becomes an ES range with no `time_zone` (`search_helper.rb`).
- **Response:** `{payments, possible_statuses, pagination}` with `success`.
- `possible_statuses` is `[{id, name, slug, dispositions: [...]}]`.
- `pagination` is `{current_page, next_page, prev_page, total_pages, total_count}`.
- There is no `aggs`.
- **Row shape.** `load: false` means each row is the raw search document, not `PaymentSerializer`. The document contains:
- `id`, `hostel_id`, `invoice_id`, `payment_method`, `currency`
- `amount` (decimal string via `to_major`) and `amount_minor`
- `reference`, `gateway_reference`, `failure_reason`
- `verified_at`, `succeeded_at`, `created_at`
- `verified_by: {id, name}`
- `invoice: {id, number, kind, status, plan: {code, name}}`
- `hostel: {id, name, host_id}`
- `status: {id, name, slug, position, color: {id, primary, secondary, tertiary}}`
- `_score`
- **No `proof_url` in the list rows.** It exists only on the show endpoint. Filterable keys in the mapping are `id`, `hostel_id`, `invoice_id`, `payment_method` and `currency`. Anything else filters through dynamic templates.

**Payment detail: `GET /api/admin/payments/:id`**
- Returns `{payment, invoice}`.
- **`payment`** comes from `PaymentSerializer`: `id`, `payment_method`, `amount`, `currency`, `reference`, `gateway_reference`, `failure_reason`, `proof_url`, `verified_at`, `succeeded_at`, `created_at`, `invoice_id` and `status`. It has no hostel.
- **`proof_url`** is a string URL or `null`, from `Attachment#url`.
- **`invoice`** comes from `InvoiceSerializer`, with `payments[]`, `plan`, `lines` and `invoice_pdf_url`. It has no hostel either.
- So hostel name and id must come from the list row the user clicked.

**`PUT /api/admin/payments/:id/verify` and `/reject`**
- Both return the same `{payment, invoice}` as show. Both live in `BillingAccess`, so a `Billing::Error` is a 422 with `errors: [message]`.
- **`verify`:**
- Not awaiting verification gives 422 `"Only a payment awaiting verification can be verified"`.
- Otherwise it calls `BillingService.apply!`. That path is idempotent and takes a lock.
- A mismatch (amount or currency differs, invoice already paid or voided) does not raise a 422. The payment becomes `failed` with `failure_reason` set to one of:
  - `"Invoice HH-… is already paid"`
  - `"Invoice HH-… was voided"`
  - `"Amount or currency does not match invoice HH-…"`
- The response then shows a failed payment with HTTP 200. The UI must branch on the returned `status.slug`, not on the HTTP status.
- **`reject`:**
- The same 422 applies, with `"…can be rejected"`.
- `reason` comes from `params.require(:reason)`. I found no `rescue_from ParameterMissing` in `api_controller.rb`, so a missing reason may not be a clean 422. Unverified: the UI should block an empty reason client-side.
- The payment becomes `failed` with `failure_reason = reason`, and an email goes to the host. The invoice stays open.

**Invoices index: `GET /api/admin/invoices`**
- Same envelope with `invoices`. Rows are search documents with `id`, `number`, `hostel_id`, `kind`, `currency`, `total`, `total_minor`, `period_start`, `period_end`, `expires_at`, `paid_at`, `voided_at`, `invoice_pdf_url`, `created_at`, `plan: {id, code, name}`, `hostel: {id, name}`, `lines[]` and `status`.
- That matches the existing `BillingInvoiceRow` almost exactly.
- `GET /api/admin/invoices/:id` returns `{invoice}` in the full serializer shape, which is `BillingInvoice`.
- Statuses are `open`, `paid` and `void`.

**Hostel billing: `GET /api/admin/hostels/:hostel_id/billing`**
- Returns `{billing, billing_currency_override, events}`.
- **`billing`** is `Billing::Summary.as_json`, the same shape as the host `/billing`. Its `plans` carry the host action fields, which are noise for an admin.
- **`billing_currency_override`** is a string or `null`.
- **`events`** is the last 100 events in oldest-to-newest order. `.last(100)` keeps the 100 newest and preserves ascending order, so the UI must reverse for a newest-first timeline.
- **Event row** from `SubscriptionEventSerializer`: `{id, kind, data, created_at, invoice_number}`.
- **Ticket mismatch:** the ticket says `invoice` is on each event. It is a flat `invoice_number` string, with no invoice id.
- **Event kinds** (14): `activated`, `renewed`, `upgraded`, `downgrade_scheduled`, `downgrade_unscheduled`, `downgraded`, `cancel_scheduled`, `cancel_unscheduled`, `past_due`, `expired`, `canceled`, `payment_failed`, `currency_changed`, `granted`.
- **`data` shapes** (from `record!` calls):
- `activated` / `granted`: `{plan: code}`
- `renewed`: `{plan, period_end}`
- `upgraded` / `downgraded`: `{from, to}` (plan codes)
- `payment_failed`: `{payment_id, reason}`
- `currency_changed`: `{from, to}`
- The scheduling, cancel, `past_due`, `expired` and `canceled` shapes were not read.

**Grant: `POST /api/admin/hostels/:hostel_id/grant {plan_id, months}`**
- Returns the same `{billing, billing_currency_override, events}`.
- **Validations:**
- A plan that is not active or not found gives 404 (`Plan.active.find`) before the service runs, so the `"This plan is not available"` 422 is effectively unreachable.
- `months` must be 1 to 24, else 422 `"Months must be between 1 and 24"`.
- An open invoice with a bank transfer awaiting verification gives 422 `"Invoice HH-… has a bank transfer waiting for verification"`.
- Any other open invoice is voided ("Replaced by an admin grant").
- **What it creates:** a zero-total invoice paid by an `admin_grant` payment. A live subscription gets a `renewal` starting at its period end. Otherwise it is `new`, starting now.
- **Missing params:** `params.require` has the same ParameterMissing caveat as `reject`.

**Currency: `PUT /api/admin/hostels/:hostel_id/billing_currency {currency}`**
- A blank value clears the override.
- Allowed values are exactly `PKR` and `USD`.
- Anything else gives 422 `"Currency must be one of PKR, USD"`.
- Returns the same envelope as show.
- The override applies at the next renewal, and `currency_changed` is recorded when an invoice is paid in a different currency.

**Plans: `GET /api/admin/plans`**
- Returns `{plans: [{id, code, name, active, position, features, prices: {PKR: "5000.00", USD: "18.00"}}]}`.
- It is not paginated and is ordered by `position, id`.
- `prices` includes only currencies that have a row. A plan with no USD price has no `USD` key, so the editor must handle absent keys.

**Plan update: `PUT /api/admin/plans/:id {plan: {name, active, position}, prices: {PKR, USD}}`**
- Returns `{plan}`.
- **Validations:**
- `name` must be present.
- `prices` accepts only `PKR` and `USD`; other keys are dropped.
- Each price must be a number, else 422 `"Prices must be numbers"`.
- Each stored `amount_minor` must be an integer greater than 0, so `0` or a negative gives a 422 from `RecordInvalid`.
- `RecordInvalid` has no explicit `rescue_from` in the parts I read; the `errors` shape for it was not verified.
- **Limits:** you cannot clear a price; there is no delete. `features` and `code` are not editable.
- **No client-side arithmetic:** the backend computes `amount_minor`. The frontend must send `"5000"` or `"5000.50"` strings.

**Manual-refund marker**
- Written by `Billing::SafepayPayments.flag_for_refund`:
`"<original reason>. Charged at Safepay (<gateway_reference>); refund it from the Safepay dashboard"`.
- The status is `failed`. The host-side regex `/Charged at Safepay/i` matches it.
- The ticket's phrase "refund it from the Safepay dashboard" is also in the string.

**Payment methods and currencies**
- Methods are `safepay`, `bank_transfer`, `cash`, `admin_grant`. Hosts can use only `safepay` and `bank_transfer`.
- Currencies are `PKR` and `USD`.

**Invoice flow facts**
- Invoice numbers have the form `HH-YYYY-000123`.
- A paid invoice triggers a PDF job and a receipt email.
- Open invoices carry `expires_at`: 24 hours online, 72 hours for bank transfer.

#### 3. Contradictions, gaps, staleness

1. **"Replacing `/admin/contracts`":** that page no longer exists (removed by #94). The real change is `/admin` → verification queue (§1), and `/admin/payments` becomes a plain payments list or merges into a tabbed view. Needs a decision: keep a separate "All payments" route, or make the queue and the list two views of one page.
2. **Hostel and invoice number are not on the detail payload.** `GET /api/admin/payments/:id` has neither. They are present only on the list row (search document). A deep link to a payment detail therefore cannot show the hostel unless the page keeps the row or re-queries the list with `f[id]`.
3. **Proof (`proof_url`):** a string or `null`, but only on the detail endpoint, not in the list. The ticket's "each row … proof (`proof_url`)" cannot come from the list. The queue needs a detail fetch per row or an open-on-click drawer. Whether it is a downloadable image, a PDF or neither is unknown (it is an `Attachment#url`).
4. **Events:** `invoice` in the ticket is really a flat `invoice_number`. The list is also the last 100 only, oldest to newest.
5. **Revenue per currency:** there is no aggregate endpoint, and the old `aggs` is gone. The frontend must not sum amounts; per the "never add PKR and USD" rule, any total has to come from the backend, and none exists. Options: show no totals, or show only per-page counts per currency (counts only, not amounts). Decide where this appears.
6. **Admin only, not moderators.** Every endpoint 403s for moderators, so the ticket's "admin" is literally `is_admin`. #### 0. Corrections to the 1a context, plus new findings

These change the design. Each one is labelled certain (read in code) or unverified.

1. **Only the role with slug `admin` passes the backend gate (certain).**
 - `Role#is_admin?` is `slug == 'admin'` (backend `app/models/role.rb`), and `User#admin?` is `roles.any?(&:is_admin?)`.
 - `CurrentUserSerializer` sends only `id, name, email, phone, is_active, permissions` and `roles` as `{id, name, slug}`. **It never sends `is_admin`.** So `CurrentUser.is_admin` (`util/models/auth.ts:76`) and the `primaryRole(..., u.is_admin)` fallback (`core/auth/auth.service.ts:331-335`) are always undefined.
 - The exact client-side mirror of the backend gate is `session.hasRole('admin')`. `allRoles` is built from the slugs (`auth.service.ts:320`).
 - Permission flags are the wrong proxy, for three reasons:
   - `admin:Payment:*`, `admin:Invoice:*` and `admin:Plan:*` exist only if `permission:reload` has run (`lib/tasks/permission.rake`).
   - `HostelBilling` cannot be classified, so it has **no flag at all**.
   - The admin role's own permission set is probably empty. `hasPermission` then fails open (`session-store.ts:132-139`), while a moderator who was granted the flag would see pages that 403.
2. **`ApiClient.put` takes no `HttpContext` (certain, `core/api-resource.ts:42-44`).** All four PUTs (verify, reject, billing_currency, plan update) need `quiet()`, so `put` needs an optional `context` argument, as `post`, `patch` and `delete` already have.
3. **`InvoiceSummary` is pure and can be imported (certain).** Its only input is `invoice` and it has no injections (`features/host/subscription/invoice-summary.ts:1-80`). The 1a note grouped it with `BillingInvoiceDetail`; that is wrong. `PaymentAttempts` is also pure, but its copy is written for hosts and deliberately hides `failure_reason`, references and proof (`payment-attempts.ts:60-66`), so admins need their own attempts list.
4. **In the payment search document, `invoice.status` is a plain slug string, not an object (certain).** The index has `invoice: { …, status: invoice.status_slug }` (backend `payment_index.rb`). Typing it as `BillingStatus` would be a bug.
5. **The payment list row does carry `failure_reason` (certain).** The manual-refund highlight therefore works from list rows with no detail fetch: `billingPaymentCharged(row)` at `shared/billing/billing-labels.ts:175-182`.
6. **`events[].data.payment_id` is a raw database integer, not an obfuscated id (certain).** `Payment#fail!` records `payment_id: id`. Never render it, link it or send it.
7. **Event kinds produced by a grant (certain, `billing_service.rb:56-77`).**
 - A grant with no live subscription records `granted`.
 - A grant with a live subscription is a `renewal` invoice, so it records **`renewed`**, plus `upgraded` or `downgraded` if the plan changed.
 - Because the grant total is 0, `cheaper = 0 < previous price` is always true. **Granting a higher plan to a live subscription is recorded as `downgraded`.** This is a backend bug to pass on (code-proven, not live-proven). The frontend shows events as recorded.
 - Event data shapes:

   | Kind | `data` |
   |---|---|
   | `downgrade_scheduled` | `{to, at}` |
   | `cancel_scheduled` | `{at}` |
   | `downgrade_unscheduled`, `cancel_unscheduled` | `{}` |
   | `past_due`, `expired`, `canceled` | `{}` (`lifecycle.rb:60`) |
   | `payment_failed` | `{payment_id, reason}` |
8. **No web path creates a bank transfer (certain).**
 - #96 D1 made host payment Safepay-only. The backend accepts `bank_transfer` through `Billing::Payments#bank_transfer`, but nothing in the web app or the Capacitor build calls it.
 - **The verification queue will be empty in practice.** Live verification in 5e needs a host to create a transfer through the API by hand. This is flagged in §10.
9. **Missing parameters and invalid records (certain).**
 - `Api::ApiController` rescues only `CanCan::AccessDenied`, `RecordNotFound` and `RecordNotDestroyed`.
 - So `ParameterMissing` (reject without `reason`, grant without `months`) and `RecordInvalid` (plan with a blank name or a zero price; `PlansController` does not include `BillingAccess`) fall through to Rails' default exception handling. You get a 400 or 422 **with no `errors` envelope**, so `serverMessages` is empty.
 - The UI must block these cases on the client and fall back to its own copy when no message comes back.
10. **The ES index is not refreshed after a write (certain).** `apply!` and `reject` call `@payment.reindex` inline. Searchkick does not force a refresh, so a list fetched immediately after Verify can still return the row (about 1 second of lag). "Row leaves the queue" must not rely only on that refetch.
11. **A race between Verify and Reject (backend, code-proven).** `reject` checks `awaiting_verification?` without a lock and then calls `fail!`. A Verify that completes between the check and the write can leave a succeeded payment marked failed. The frontend cannot fix this; pass it to Hamza. A double Verify is safe: `apply!` locks, and `next false if succeeded?` makes the second call return 200 with a succeeded payment.
12. **The staff tab bar holds at most five entries and has no overflow (certain, `layout/components/mobile-tab-bar/staff-tab-bar.ts`, class doc).** The admin nav has 4 entries today (`staff-shell.ts:40-57`). Four separate billing entries would make 7. This is the deciding argument for a single "Billing" entry.
13. **`hh-data-table` restrictions (certain).**
  - `CellCurrency` takes `amount: number` (`lib/src/ui/lib/data-table/data-table.ts:33-40`). Billing code must never use it; money goes into `text` or `composite` cells, pre-formatted with `BillingMoneyPipe`.
  - Column labels and the footer `itemLabel` are rendered raw (`:240`, `:593`, which appends an English "s").
14. **The admin billing summary has no hostel name (certain, `Billing::Summary#as_json`).** The hostel billing page needs the name from router state, or a fallback lookup through `AdminApi.listings(…, {id})`, which already sends `f[id]` (`services/admin-api.ts:123-124`).

#### 4. Verification queue (§3 of the brief)

- **Route and list.**
- Route: `/admin/billing/verification`, the landing page.
- List: `f[status.slug]=awaiting-verification&sort[created_at]=asc`, oldest first. This is a FIFO queue; the backend default is desc.
- Columns: Hostel (link to the hostel billing page), Invoice number, Amount (`billingMoney` in `<bdi>`, payment currency), Reference, Submitted (`apiDate`), and a "Review" affordance.
- **Detail drawer.** Proof is not on the list row, so a row click opens `AdminPaymentDrawer` with `{row}`. The drawer fetches `payment(row.id)`; the hostel name and id come from the row (§0.14).
- **Proof** is a plain link that opens in a new tab with `rel="noopener noreferrer"`. The type of `Attachment#url` is unknown, so an `<img>` preview is optional with a fallback to the link on `(error)`. `null` shows "No proof attached".
- **Body:** `InvoiceSummary [invoice]`. The payment amount and currency sit next to the invoice total as two formatted strings with **no client-side "matches" check**; the server decides a mismatch. The invoice's other attempts are listed with the admin wording.
- **Verify.**
1. `hh-confirm-modal` asks "Mark invoice {number} paid and activate {plan}?".
2. On HTTP 200, **branch on `payment.status.slug`**:
   - `succeeded`: inline success, and the row leaves.
   - `failed`: a danger alert "Not applied: {failure_reason}" (admins see the reason verbatim; #97 D1 is host-facing), and the row leaves (it is no longer awaiting).
   - Anything else: refetch.
- **Reject.**
- A modal with a required textarea. The reason is trimmed and must be non-empty, with a maximum length (suggest 500).
- `confirmDisabled` stays set until the reason is valid. The copy says "The host receives this reason by email."
- On 200 the row leaves.
- **Removing the row (§0.10).** Keep a page-local `handled = signal<Set<string>>` and filter it out of the rows. Then bump `refresh`. If the page becomes empty and `page > 1`, go to `page - 1`.
- **Errors.**

| Response | Handling |
|---|---|
| 422 | `errors[0]` verbatim (for example "Only a payment awaiting verification can be verified" when another admin acted first), then refetch the detail and the list |
| 404 | Our "no longer exists" copy, then refetch |
| 403 | Our own copy |
| 400, or 422 with no messages | Our generic copy |
| Network | Our network copy |

- **Concurrency.** One action in flight per drawer, enforced by a `busy` signal. A double Verify is idempotent server-side. A double Reject gets a 422 and is handled as above.
- **Empty state.** "No transfers waiting". Bank transfers are not offered in the app yet (§0.8).

- **Response:** on 200, re-render from the envelope. On 422, show `errors[0]` verbatim. On 404 (inactive or unknown plan), use our own copy and refetch.

**Currency override.**
- A radio for Automatic (`""`), PKR or USD. Save only when the value changed.
- Copy: "New invoices use this currency; a live plan keeps its currency until it renews." This follows `Summary#currency`: the subscription currency while live, else the hostel's `billing_currency`.
- On 200, re-render.

**Concurrency.** One `busy` signal for the whole page covers grant and currency. Use an epoch guard so that a response for an older `hostelId` is ignored (the same pattern as #98 D6).

#### 7. Plan price editor (`/admin/billing/plans`)

- **Layout.** A table, with one row per plan in `position` order: Code (read-only), Name, Active toggle, PKR price, USD price, and Save (per row).
- **Position.** Do not edit it. It is not in the ticket, and it changes the order of the public pricing page.
- **Absent USD key.** Show an empty input labelled "No USD price yet". Empty means "do not send"; the backend cannot clear a price.
- **Validation.**
- Name: trimmed and non-empty.
- Price: `^\d{1,9}(\.\d{1,2})?$` and not all zeros, matching `^(?=.*[1-9])`. Pattern checks only; no numeric parsing.
- **Payload.** `plan: {name, active}` plus `prices` containing only the currencies whose **string** changed. Send them as strings exactly as typed.
- **Response.** On 200, replace the row from `{plan}`. On 422, show `errors[0]` (for example "Prices must be numbers"). A 422 or 500 with no messages gets our own copy.
- **Confirmations.** Deactivating asks for confirmation ("Hosts can't choose this plan"). Every save notes "New prices apply to new invoices only".
- **Concurrent editors.** Last write wins; there is no locking. That is acceptable.

#### 1. Problem and intent

Billing moved to plans per hostel (Listing, +Boost, +CRM), monthly, in PKR or USD. HostelHive admins currently have no way to:

- confirm money that arrives outside Safepay;
- see what was paid, failed or still needs a refund;
- fix one hostel's plan by hand (grants, comps, corrections);
- change prices.

The legacy Payments page reads a model that no longer exists. The intent is an **operational back office** with five parts:

1. Act on transfers waiting for verification.
2. Audit payments and invoices without ever mixing currencies.
3. Look into one hostel's billing history and correct it.
4. Maintain the price list.

None of this should ever compute money.

#### 2. Affected parties and impact

| Who | What they notice |
|---|---|
| **Admins** (role `admin`) | The new landing page and four new screens. Verify, reject, grant and the price editor change other people's money and access, and none of these actions can be undone. |
| **Super-admin and support without the `admin` role** | Today they see Payments in the nav. After this change they should not see the billing entries at all (F1). If they reach a URL directly, they get our own 403 copy, never a broken table. |
| **Moderators** | No change. They never see `ADMIN_NAV`, and the billing endpoints 403 for them. |

| **Hosts after a reject** | The payment shows as failed. They are emailed the admin's reason (ticket; not verified in the email template). The invoice stays open, so they can pay again. In-app wording never shows the raw reason (#97 D1). |

#### 3. Acceptance criteria

The same conventions apply throughout:

- **Money** is `billingMoney(amount, currency)` wrapped in `<bdi>`, and is never summed.
- **Dates** are UTC, shown with a "UTC" suffix on date-times.
- A **422** shows `errors[0]` exactly as returned.
- A **403** shows our own copy.

##### A. Access and navigation

1. **Billing nav for admins.** Given a session holding the `admin` role, when it opens `/admin`, then the nav shows a "Billing" group containing Payments, Invoices and Plans & prices.
2. **Hidden for others.** Given a staff session *without* the `admin` role (super-admin only, support, or moderator), then those three entries are hidden. `/admin` lands on the first admin page that user can see, never on a page that 403s.
3. **403 copy.** Given any billing endpoint returns 403, then the page shows `adminBilling.forbidden` in place of its content, with no error toast, no table and no retry loop.
4. **Spec updated.** The route list in `admin.routes.spec.ts` matches the new routes, and `redirectTo` points at the landing chosen in section 6.

##### B. Verification queue

5. **Fetch.** Given an admin opens the queue, then it requests `GET /api/admin/payments?f[status.slug]=awaiting-verification`, oldest first so the longest wait is on top (`sort[created_at]=asc`), paginated.
6. **Row content.** Each row shows:
 - the hostel name, linking to the hostel's billing page;
 - the invoice number;
 - the plan name;
 - the amount in the payment's own currency;
 - the method label;
 - the reference, or "—" when there is none;
 - the submitted date and time in UTC.

 There is **no** proof in the row, because the list payload has none.
7. **Detail panel.** When the admin opens a row, then `GET /api/admin/payments/:id` loads and the panel shows:
 - the same fields as the row;
 - the invoice total, period and lines;
 - the other attempts on that invoice;
 - **proof**: "View proof" opens `proof_url` in a new tab (`rel="noopener"`), or "No proof attached" when it is `null`.

 The hostel name comes from the row that was clicked.
8. **Verify needs confirmation.** When the admin clicks Verify, a confirm dialog (`verifyTitle` / `verifyMessage`) must be accepted before `PUT …/verify` is sent. While the request is in flight, Verify and Reject are disabled.
9. **Verify succeeded.** Given the response has `payment.status.slug === 'succeeded'`, then:
 - a success notice reads `verifiedNotice` with the invoice number;
 - the panel closes;
 - the row leaves the queue (the queue reloads);
 - the queue count drops.
10. **Verify returned 200 but failed (mismatch).** Given the response has `payment.status.slug === 'failed'`, then:
  - the panel stays open;
  - it shows a danger alert `verifyNotApplied` containing the server's `failure_reason` as given;
  - it shows the line `verifyNotAppliedNext` (the host has not been told; refund or contact them);
  - the row leaves the queue on reload.

  The UI must **never** show the success notice for this case.
11. **Reject needs a reason.** Clicking Reject opens a dialog with a required reason field (max 500 characters) and the hint `rejectHint`. The Reject button stays disabled while the trimmed reason is empty. Submitting sends `PUT …/reject {reason}`.
12. **Reject succeeded.** Given the reject succeeds, then the notice `rejectedNotice` shows, the panel closes and the row leaves the queue.
13. **422 on verify or reject.** For example, another admin already handled the payment and the server says "Only a payment awaiting verification can be verified". Then the message shows as returned, the queue reloads, and the panel closes if the row is gone.
14. **Empty queue.** Given the queue is empty, it shows `queueEmptyTitle` / `queueEmptyBody` and a link to All payments.
15. **Load error.** Given the load fails with anything other than 403, it shows `loadError` with a Retry button.

##### C. Payments list

16. **Default view.** All payments, newest first (`created_at desc`), with `limit` and the page in the URL.
17. **Filters, all combinable.** Every change resets to page 1, and the filter state survives a reload through query params.
  - **Status:** chips "All" plus `possible_statuses`, labelled with our admin labels and falling back to `status.name`.
  - **Method:** Safepay, Bank transfer, Cash, Admin grant (`f[payment_method]`).
  - **Currency:** All / PKR / USD (`f[currency]`).
  - **Created date range:** naive `dayRangeStart` / `dayRangeEnd`, which the server reads as UTC days, with the hint `datesUtc`.
  - **Hostel name search:** debounced, `s[hostel.name]`.
18. **Columns.** Hostel, Invoice, Method, Reference, Safepay tracker (`gateway_reference`, or "—"), Amount, Status, Created, Succeeded. Sortable on created and succeeded. **Amount is sortable only when one currency is filtered**, because sorting PKR next to USD is meaningless.
19. **No totals.** The header shows `paymentsCount` ("{{count}} payments" from `pagination.total_count`). It shows **no** amount total, summed or otherwise.
20. **Manual-refund highlight.** Given a row whose `failure_reason` matches `/Charged at Safepay/i` or contains "refund it from the Safepay dashboard", then:
  - the row has a danger tint and a "Refund needed" badge beside its status;
  - the detail shows `refundNeededBody` with the Safepay tracker (copyable) and the full `failure_reason`.

  No other failed payment gets the badge.
21. **Detail.** Clicking a row opens the payment detail: the fields above plus `failure_reason` as given (admins see internal wording), verified at, verified by (from the row's `verified_by.name`), and links to the invoice and to the hostel billing page. When the status is awaiting-verification, the detail offers Verify and Reject exactly as in criteria 8–13.
22. **Empty results.** No rows for a filter → `noPaymentsMatch`. No rows at all → `paymentsEmpty`.

##### D. Invoices list and detail

23. **Filters.** Same filter pattern as payments: status chips (Open / Paid / Void), currency, created date range (UTC), hostel name search.
24. **Columns.** Invoice number, Hostel, Plan, Type (New plan / Renewal / Upgrade), Period, Total, Status, Issued, Paid, PDF. A paid invoice without a PDF yet shows "Preparing…". The count is shown and there is **no** total.
25. **Detail.** Clicking a row opens `/admin/invoices/:id` (`GET /api/admin/invoices/:id`) and shows:
  - number, status, type, plan, period, lines, total;
  - expires at (when open), paid at (when paid), voided at (when void);
  - the PDF link;
  - every payment attempt: method, amount, status, reference, tracker, `failure_reason` as given, and the refund highlight per criterion 20;
  - a link to the hostel billing page.
26. **Unknown values.** An unknown kind shows "—", and an unknown status shows `status.name`.

##### E. Hostel billing (`/admin/hostels/:id/billing`)

27. **Summary.** The page shows `hh-current-plan-card` in read-only mode (no `canChange`) with plan, status, period, renewal or end date, and features. It also shows the open invoice when there is one (number, total, expiry, "Transfer awaiting verification" when `awaiting_verification`) and the billing currency with the override state:
  - `currencyAuto` ("Based on the hostel's country") when `billing_currency_override` is `null`;
  - `currencyOverridden` otherwise.
28. **Timeline.** Events appear **newest first** (the frontend reverses the array). Each event shows the human label from section 5, its detail, the invoice number when present, and the date and time in UTC. Plan codes are shown as plan names from `GET /api/admin/plans`, falling back to the raw code. A footnote `eventsLimit` appears when there are exactly 100 events. With no events the page shows `eventsEmpty`.
29. **Grant dialog.**
  - **Fields:** Plan (active plans only, in `position` order) and Months (1–24, default 1, a select so nothing out of range can be entered).
  - **Live subscription:** the confirm states it extends from the current period end, plus `grantSwitchNow` when the plan differs.
  - **No live subscription:** it states the plan starts today.
  - **Warnings:** `grantVoids` when there is an open invoice, `grantKeepsCancel` when the plan is set to end, and `grantDropsSwitch` when a downgrade is scheduled.
30. **Grant blocked.** Given `open_invoice.awaiting_verification` is true, the Grant button is disabled with `grantBlockedTransfer` and a link to that payment in the queue. If the server still returns the 422, it is shown as returned.
31. **Grant succeeded.** The page re-renders from the response envelope (no extra GET) and shows the notice `grantedNotice`. A 404 (plan deactivated meanwhile) shows `grantPlanGone` and reloads the plan list.
32. **Currency override.** A select offers "Automatic (from country)", PKR and USD, and Save sends `PUT …/billing_currency` with `""`, `"PKR"` or `"USD"`.
  - The confirm always says `currencyNextRenewal`.
  - It adds `currencyOpenInvoice` when an invoice is open.
  - It adds `currencyPlanNoPrice` when the current plan has no price in the chosen currency.
  - On success, the summary re-renders and the notice `currencySaved` shows.
33. **Entry points.** The page is reachable from the hostel name on queue, payment and invoice rows and details, and from a "Billing" row action on All listings. A deep link loads the page on its own. The title is the hostel name when known (router state), otherwise `hostelBillingTitleFallback`.

##### F. Plan price editor (`/admin/plans`)

34. **Layout.** Plans are listed in `position` order. Each plan has:
  - an editable Name;
  - read-only Code and Features (feature labels from `sharedBilling`);
  - an Active toggle;
  - PKR price and USD price inputs prefilled with the server strings;
  - one Save per plan.
35. **Missing price.** Given a plan has no `USD` (or `PKR`) key, that input is empty with the placeholder `priceNotSet` and a warn line `missingPriceWarn`.
36. **Validation before sending.**
  - Name: trimmed, 1–60 characters → `nameRequired`.
  - Each price that is filled: matches `^\d+(\.\d{1,2})?$` and is not all zeros → `priceInvalid`.
  - An empty price that was previously set → `priceCannotClear`, because the backend cannot clear a price.
  - The request sends only changed prices, as **strings exactly as typed**. There is no arithmetic and no number conversion.
37. **Notice.** `pricesNewInvoicesOnly` is always visible above the list.
38. **Deactivating.** Turning Active off and saving requires a danger confirm, `deactivateMessage` (F4). Turning a plan back on needs no confirm.
39. **Save succeeded.** That plan's row re-renders from the response `{plan}` and the notice `planSaved` shows. A 422 shows `errors[0]` under that plan. Other plans' unsaved edits are kept.

#### 4. Product rules to respect (with sources)

- **Never compute or sum money, and never add PKR to USD.** Every amount is the server string plus its currency (ticket; `100.md` preflight; `billing-money.pipe.ts`). Prices are sent as typed strings (`plans_controller.rb` does `BigDecimal(amount.to_s)`).
- **A 422 shows `errors[0]` as returned. A 403 shows our own copy** (95 D?, 96 D10, 98 D4).
- **Admin dates are UTC.** Date ranges use `dayRangeStart` / `dayRangeEnd` (`100.md:60`, memory note on date-range filters). There is no ES `time_zone`, so a day is a UTC day.
- **Status labels are ours for known slugs, falling back to `status.name`** (97 D7). Admins get admin wording (Open/Void, Awaiting verification, Admin grant). The host wording ("Unpaid", "Closed", "Under review", "Granted by HostelHive") is for hosts.
- **Obfuscated ids are used exactly as returned.** Hostel billing is keyed by `hostel_id` from the row.
- **Grant:** active plans only (`Plan.active.find`), 1–24 months, blocked by a transfer awaiting verification, and it voids any other open invoice (`grant.rb`).
- **Currency override:** `""`, `PKR` or `USD`. It applies when the next invoice is issued (`checkout.rb:40,49`). An open invoice keeps its currency.
- **Prices:** must be greater than 0 (`plan_price.rb:8`). They cannot be removed. They apply to invoices issued after saving. An existing open invoice keeps its total, but if the host checks out again it is replaced at the new price (`checkout.rb:88-92`).
- **Verify is idempotent and locked; the outcome is read from `status.slug`, not from the HTTP status** (`billing_service.rb`).

#### 6. Recommendations

**R1 — Admin landing and the queue's home**

- *Option A (recommended):* a single Payments page at `/admin/payments` with two tabs, "To verify ({{count}})" (the default) and "All payments", using `?view=`. `/admin` redirects there.
- It keeps one nav entry and the existing URL, and it shares the table and drawer code.
- Its empty state points to All payments, which softens F2 (an empty queue is the normal case for now).
- *Option B:* a separate `/admin/verify` landing page plus a separate Payments page. This is the ticket's literal wording, but it means two nav entries and an empty landing almost every time until bank transfers ship.

**R2 — Revenue totals**

- *Recommended:* show **no amount totals**. Show only `total_count`, and per-row amounts in their own currency.
- Ask the backend for per-currency sums over the filtered set, for example `aggs: {PKR: "…", USD: "…"}` from `amount_minor`. Per-page sums are ruled out: they are computed money and misleading.
- Per-currency *counts* add little, so skip them.

**R3 — Where hostel billing is reachable from**

- The hostel name on queue, payment and invoice rows and details.
- A "Billing" row action on All listings. That table's row click stays on review.
- Not in the nav, since it is a per-hostel page.

**R4 — Who sees the nav entries**

- Gate the billing nav entries and route guards on `hasRole('admin')`, mirroring `User#admin?` (F1). Do not use the `admin:Payment:*` flags, which fail open.
- Moderators see nothing new.
- Ask the backend whether super-admin should pass `authenticate_admin!`.

**R5 — Confirmations**

- Confirm Verify, Grant, Currency and Deactivate.
- Reject has its own dialog.
- Re-activating a plan and saving prices or names need no confirm; the permanent notice covers prices.

#### 7. Edge cases

| Case | Behaviour |
|---|---|
| Two admins verify the same payment | The second gets the 422 "Only a payment awaiting verification can be verified" as returned. The queue reloads, and the payment detail shows Succeeded and who verified it. If both requests race past the check, `apply!` is idempotent and the second simply sees succeeded. |
| Verify does not match the invoice (already paid, voided, or amount or currency differs) | Criterion 10. The host is not notified (F7). The admin is told to refund or contact the host. |
| Grant while a transfer awaits verification | Pre-empted by disabling the button (criterion 30). The 422 shows as returned if the screen was stale. |
| Grant voids an open invoice | **Yes, warn** (`grantVoids`). The host loses a payable invoice, and a Safepay payment in flight on it would come back as "was voided" and need a refund. |
| Grant to a past-due subscription | It starts at the old period end, so part of the granted time has already passed. Show `grantExtends` with that date so the admin sees it. |
| Grant with a different plan on a live subscription | The plan switches now. The timeline shows "Renewed" plus a wrong "Downgraded" (F3). |
| Currency override while an invoice is open | The invoice keeps its currency (`currencyOpenInvoice`). If the host checks out again, it is replaced in the new currency. |
| Override to a currency with no price on the current plan | Warn (`currencyPlanNoPrice`). The renewal will fail (F5). |
| Plan deactivated | Criterion 38 and F4. It is also excluded from grant (a stale list gets a 404 → `grantPlanGone`). |
| Price changed mid-period | Current subscribers keep their period. The next renewal invoice uses the new price. A renewal invoice already issued keeps the old price unless it is replaced. Upgrades are prorated at the new prices. Hosts get no notice. |
| Reject or grant without required parameters | `params.require` has no clean 422 (unverified). Client validation must make these requests impossible. |
| Proof URL expired or unreachable | The link opens whatever the storage returns. We fetch the detail when the panel opens, so the URL is fresh. |

Query-to-parameter mapping:
- `pageParams(page ?? 1, limit ?? 20)`
- `status` → `f[status.slug]`
- `from` / `to` → `f[created_at][gte]` = `dayRangeStart(from)`, `f[created_at][lte]` = `dayRangeEnd(to)`
- `hostelName` → `s[hostel.name]`; `hostelId` → `f[hostel_id]`
- `method` → `f[payment_method]`; `currency` → `f[currency]`
- `invoiceNumber` → `s[invoice.number]` on payments, `f[number]` on invoices
- `sort` → `sort[<field>]=<dir>`
- `payments()` returns `{rows, statuses, page: toPageInfo(...)}`

Mapping:
