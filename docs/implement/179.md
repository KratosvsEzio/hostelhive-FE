## Ticket understanding

Source manifest: Trello #179 (ready), Trello #180 (ready, context only), KB `docs/knowledge-base/area/auth-and-session.md` and `decisions/auth-and-session/forgot-password-answers-unknown-email-neutrally.md` (ready), prior run `docs/implement/Bugs/150.md` (ready).

Backend PR #61 (azeem-hamza/hostelhive): every email gets the same 201; any repeat within 10 minutes gets 422 "A reset link was sent recently. Retry after 10 minutes"; rate limit (BE PR #60) answers `429 {"errors":["Too many requests. Please try again in 31 seconds."],"code":"rate_limited","retry_after":31}`, forgot password limited to 3/hour per email (so `retry_after` can approach 3600).

Acceptance (card):
- Known and unknown emails look identical on screen.
- Resend is disabled for 10 minutes after a send, with a countdown.
- A 422 or 429 on Resend shows a friendly message.
- Copy is updated in every language.

What is already on `main` (commit 0b01a3e0, Trello #150 / PR #123):
- Neutral sent copy `authForgotPassword.sentIfAccountExists` in all 18 locales; `weSentAPasswordReset` retired, parity spec guards it.
- A 422 shows the sent screen with an `alreadySent` notice (`role="status"`, tinted, not red).
- A 429 shows a generic "Too many attempts. Please wait a few minutes" error.

Left to do:
1. Resend disabled with a live countdown for 10 minutes after a send.
2. 429 shows "Try again in N" using `retry_after` from the body. `errorInterceptor.normalize` drops the body today, so `ApiError` has to carry it.
3. The KB decision's "Consequences" are stale (BE now neutral; 422 is for every address; `retry_after` now in the body).

## Plan

Merged plan (PE + PM):
- **T1 shared layer:** optional `retryAfter` (seconds, finite > 0) on `ApiError`, set in `errorInterceptor.normalize()` from the body's `retry_after`. Behaviour for other requests unchanged (#180 owns that).
- **T2 classifier:** a 429 carries `retryAfter` through to the page.
- **T3 page:** absolute deadlines per normalised address (`cooldownUntil` = send + 10 min on a 201 or 422; `rateLimitedUntil` = now + retry_after on a 429). One `now` signal ticks every second only while a deadline is live; also refreshes on `visibilitychange`; interval cleared on destroy. Resend disabled with "Resend in m:ss". Ticking text stays out of live regions; one static announcement.
- **T4 copy:** new keys in all 18 locales, with the parity spec extended.
- **T5 KB:** rewrite the stale Consequences in the forgot-password decision and the area file.
- No persistence across reloads (would store an email in storage; a reload costs at most one neutral 422).

PE notes: `forgotPassword` sends `inlineErrors()` (`auth-api.ts`), so the interceptor never toasts its 429 — #180's global handler must respect `SUPPRESS_ERROR_TOAST`. About ten `forgot-password.spec.ts` tests click Resend right after a Send and need fake timers.

Open questions for 2d: retryAfter on the shared `ApiError`; same address still in cooldown (skip the request or call it); keep or drop the dead 404→sent mapping; time format; Send disabled on a 429.

## Decisions

| # | Question | Decision | By |
|---|---|---|---|
| D1 | How the page gets `retry_after` | Optional `retryAfter` on `ApiError`, set in `normalize()`; no behaviour change elsewhere | user (recommended) |
| D2 | Same address re-sent while its 10 min run | Skip the request; show the sent screen with the countdown still running (saves one of 3/hour) | user (recommended) |

| D5 | Persist across reload | No (would store an email; a reload costs one neutral 422) | assumed, PE + PM agree |
| D6 | 429 on Send | Send held back for that address until `retry_after`; editing to another address re-enables it | assumed (PE; #180 asks forms to wait) |
| D7 | 422 with no local record | Countdown a full 10 min from now (never earlier than the server) | assumed (PE + PM) |
| D8 | Screen readers | Ticking text never in a live region; the button's visible time is `aria-hidden`, with a static label | assumed (PE + PM) |
| D9 | Implementation routing | One engineer (the orchestrator) in sequence: five small tasks in a chain (T1→T2→T3), one spec file per task; a fan-out would collide | orchestrator |

## QA results

### Round 1
- Focused: `npx vitest run src/app/features/auth/forgot-password src/app/core/interceptors/error-interceptor.spec.ts src/app/core/i18n/forgot-password-locale-parity.spec.ts`. 20 existing Resend tests failed, as expected (Resend now waits); the test defect was fixed by advancing the faked clock 10 min.
- One new test (`stops its clock when the page goes away`) failed, because `vi.getTimerCount()` also counts other code's intervals. It was rewritten to spy on `setInterval`/`clearInterval` and match the page's one-second timer.

### Round 2
- Focused set: **310 / 310 passing**.
- Mutation checks, each caught by exactly one test: removing `stopClock()` on destroy; dropping the 1-minute drift wait; dropping the same-address skip; dropping the `visibilitychange` catch-up.
- Source-scanning specs (35 files, `readdirSync|readFileSync|existsSync|locale-files-testing`): **2250 / 2250 passing**.

### Browser (personal Chrome, worktree served on :4379, staging API)
User approved sending for a made-up address `qa-179-test@example.com`; 2 requests were sent.
- First Send → **201** (an unknown address gets the same answer live; BE #61 confirmed on staging). Neutral sent screen; Resend disabled, "Resend in 9:54".

- Reload → same address → Send: **422** live → "already sent" info notice (not red), "Resend in 9:54" (a full 10 min).
- No console errors. A 429 was **not** triggered live, which would have needed more requests than approved; it is unit-tested only.
