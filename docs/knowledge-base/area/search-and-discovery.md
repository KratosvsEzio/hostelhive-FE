# Search and discovery

How a seeker finds hostels: the header search bar, the `/search` list + map page, its filters, the listing card, and the curated SEO landing pages (`/hostels/:place[/:gender]`) that embed the same search. Ends where a card is clicked — the hostel page is [listing-and-booking](./listing-and-booking.md). The home page's own sections are [landing-page](./landing-page.md).

## How it works
- **URL is the state.** Every control writes query params with `router.navigate([], { queryParamsHandling: 'merge' })`: `place`, `city`, `lat`, `lng`, `zoom`, `gender`, `propertyType`, `roomType`, `minPrice`, `maxPrice`, `amenities` (comma list of slugs), `sort`, `everywhere` (worldwide search, below), and, on `/search`, the viewport `ne_lat/ne_lng/sw_lat/sw_lng`. `SearchMap.query()` derives the request from them and compares by `JSON.stringify`, so writing the viewport back into the URL does not refetch. A landing page keeps its viewport in memory instead (below).
- **Request pipeline** (`SearchMap.result`): a 600 ms debounce, written as `switchMap` onto `timer(600)` so a search still pending when the page goes is dropped (`debounceTime` flushes it on completion, which fired one last search for the box being left) → `ListingsApi.list` via `switchMap`; page 1 replaces, later pages append (deduped by id) through an `IntersectionObserver` sentinel. A 429 starts a 60 s cooldown that suppresses new queries; a 5xx/network error shows an inline "Try again".
- **Geography priority** in `ListingsApi.list`: map `bounds` → `near` (lat/lng ± radius) → whole world. With no place in the URL, `setup()` frames the visitor's country (`CountryBounds.forVisitor`, `apps/web/src/app/core/geo/country-bounds.ts`); "Search everywhere" (`searchEverywhere()`) drops every geographic constraint.
- **Filter contract sent to `GET /public/hostels`** (as coded in `listings-api.ts`): `f[bounding][north|south|east|west]`, `s[city]` (full-text fallback), `f[gender_type]` (`co-living|boys|girls|backpacker`), `f[property_type]`, `f[room_types.occupancy_type]` (`shared|private_room`; the URL/app value `private` is mapped via `OCCUPANCY_WIRE_VALUE`, raw `private` matches nothing), `f[<shared|private>_occupancy_price_from.currency_price_hash.<CODE>][gte|lte]`, `f[offers.id][]`, `sort[created_at|starting_price]=asc|desc`, `page`, `limit`.
- **Prices on cards**: `toListing` picks the requested occupancy's "from" block, falls back to the other occupancy, then to the hostel's own currency; `discounted_price: 0` means "no discount".
- **Landing pages** render `<hh-search-map [seed] [genderRoutes]>`; `seed` sits *under* the query params in `SearchMap.params()` (`mergeSearchParams`, `search-params.ts`), so a visitor's own filter wins, `gender` included. The exception is geography: the seed owns `place`, `city`, `lat`, `lng` and `zoom` (`SEED_GEOGRAPHY`), so a hand-made `/hostels/lahore?place=Karachi&lat=…&lng=…` still searches and frames Lahore under the Lahore head (Trello #204). A landing page's place is its path. When seeded, `SearchMap` leaves the `<head>` to `PlaceLanding`, and neither restores a viewport from the URL nor writes one into it (`seeded`: `urlBounds` reads none, `syncBoundsToUrl` returns early). The camera opens on the place, the list searches `near` it, and a pan re-searches the box on screen in memory, so a landing link carrying a viewport shows exactly the clean page and keeps its self-canonical. See decisions.
- **One reader of filter state.** `SearchMap.params()` is the only place the URL and the seed are read; `SearchFilters` gets it through its required `params` input (`search-filters.ts`) and never reads `ActivatedRoute` for filters itself. A query `gender` counts only if `isAccommodationType` accepts it — an unknown or empty value is treated as absent, so a landing page's own type applies.
- **Changing the type on a gender page changes the page.** `PlaceLanding.genderRoutes` (`genderRoutesFor`, gender pages only) maps every type to its URL: Any type → `/hostels/<place>`, girls/boys/co-living → the sibling page, backpacker → `/hostels/<place>?gender=backpacker`. `SearchFilters.onApply` goes there in one localised navigation (`localiseCommands`, `queryParamsHandling: 'merge'`). City, campus and `/search` pages pass no routes and keep the query merge. See decisions.
- **On a landing page, any change of geography leaves for `/search`.** A place pick (`onPlaceSelected`), Near me (`locateMe`) and "Search everywhere" (`searchEverywhere`) go through `SearchMap.startSearch`: one localised push navigation, to `/search/<slug>`, `/search?place=My location` or `/search?everywhere=1`. It merges the visitor's filters plus the page's own filters as explicit params (`seededFilters`), and nulls the viewport, place and retired keys (`search-scope.ts`). A landing page writes no viewport, but its link may have arrived carrying one.
- **A new place is a new search, on every page.** The place pick and Near me always use `startSearch`. On `/search` too, they go to `searchRouteFor(label)` rather than merging on the current path. The header bar's `search()` also nulls the viewport keys. Old `ne_*/sw_*` would otherwise be restored by a newly built search page's `SearchMap` (the viewport is read once, on its first pass) over the new place.
- **Only a bare `/search` widens in place.** "Search everywhere" merges with `replaceUrl` there alone. A landing page or a `/search/<slug>` path leaves for `/search?everywhere=1` through `startSearch` (a push; `searchEverywhere`, `seed() || locationSlug()`). A path that names a place can't be widened by a query merge: the slug is held off only while `everywhere` is set, and the first pan clears it, after which the slug comes back in both place fields, and as the heading wherever the map frames it (Trello #128, PR #133). `''` and `:location` are separate route configs, so leaving builds a new `SearchMap`, which reads `everywhere` at construction.
- **The header bar keeps unsubmitted edits through map viewport writes.** `SearchBar` records the URL (`url`: query plus the routed slug) from both its `queryParamMap` and `NavigationEnd` subscriptions. Each field group is a `linkedSignal` over a key: place (`place, city, lat, lng, zoom` + slug), budget (`minPrice, maxPrice`) and type (`gender`). Only a change of a group's key overwrites the visitor's edit, so `syncBoundsToUrl`/`recenterTo` writes never do (Trello #130, PR #133). The slug is part of the place key, so a pasted `/search/lahore` still fills the bar at `NavigationEnd`, and leaving it for `/search?everywhere=1` empties it. Consequences: Back to an entry with the same place keys, a language switch, and a link to the same place search all keep an unsubmitted edit (`docs/implement/Bugs/128.md` D4).
- **The canonical follows the query's place.** `canonicalPlace` prefers `toLocationSlug(place || city)` over the path slug, so links shared with a stale slug canonicalise correctly. A pasted `/search/lahore` with no query still maps to `/hostels/lahore`. The canonical is written only for an arrival with no viewport in its link, and only while the map frames the place; otherwise the page is `noindex` (below).
- **`/search` has no static route `title`.** The SEO effect owns the tab title; Angular's title strategy would otherwise re-apply the static one after every navigation, including viewport writes (`search.routes.ts`).
- **Landing pages clear their JSON-LD on destroy.** `PlaceLanding` removes `place-breadcrumb` / `place-faq` through `Seo.clearOnDestroy` (the same helper home, blog, blog article and listing use). This is safe for SSR because the server serialises the document before destroying the platform. `apps/web-e2e/src/search-new-place-and-landing-head.spec.ts` checks the raw HTML. The `place-breadcrumb` trail is in the page's language and every item comes from `Seo.pageUrl` (Home, the city page, then the gender or campus page), so its last item equals the canonical; `head-canonical-and-structured-data.spec.ts` checks it on `/ur` (Trello #202).
- **Worldwide search is a URL state, `everywhere=1`** (`EVERYWHERE_KEY`). A bare `/search` frames the visitor's own country (`setup()`), so worldwide needs saying.
  - It is read once at construction (`everywhereInUrl`; `unbounded` is a `linkedSignal`, false whenever there is a seed). Explicit `lat`+`lng` beat it, but a slug-only centre doesn't narrow the request (`query()`).
  - `syncBoundsToUrl` mirrors it, and it is the only writer. A landing page writes neither it nor the viewport, so a stale `everywhere=1` stays in a landing URL, inert. A pan (`leftHomeCountry`), a new place (`recenterTo`) or a header search (`SearchBar.search()`) clears it.
  - Back within `/search` doesn't re-apply it, like the viewport keys.
- **Price sort is withdrawn while the type is "Any".** `starting_price` is one unit-less number, and only backpacker hostels are nightly, so "Any" mixes nightly and monthly prices. `sortsFor(type)` (`search-sort.ts`) decides what is offered, and `isPriceSort` decides what is dropped. Every surface asks them: the inline Sort dropdown (`SearchFilters.sortOptions`), the Filters modal (`SearchFilterModal.sortOptions`), `SearchFilters.onApply` (a backstop), `SearchBar.search()` and `SearchMap.startSearch()`. The rule used to be four hand-written `startsWith('price-')` copies; the modal never got one (Trello #112, PR #141).
- **The Filters modal derives the sort it shows and applies.** `effectiveSort` reads Recommended while `draftGender` is `'all'` and `draftSort` holds a price sort; otherwise it reads `draftSort`. The draft is never overwritten, so a price sort survives a detour through "Any" within one modal session, and a seed or Clear all needs no reset of its own. `apply()` emits `effectiveSort`.
- **A filter value the search can't use is read as absent; only what can come back to life is taken out of the URL.**
  - **`sort`:** `mergeSearchParams` works out the type in force (a valid query `gender`, else a valid seed gender, else "Any"), then drops any `sort` that `isSortOffered(sort, type)` rejects, from the query or the seed. That covers a price sort with no type, `?sort=`, unknown values, wrong case, and a repeated `sort` with one bad value. A gender landing page's own type counts, so `/hostels/lahore/girls?sort=price-asc` keeps its sort. An unknown `gender` is read as absent the same way.
  - **Keys judged on their own (`CHECKED_ALONE`, `search-params.ts`):**
    - `roomType`: `isOccupancyType`, plus the backend's own `private_room` read as `private`.
    - `propertyType`: `isPropertyType`, `util/property-type.ts`.
    - `minPrice`/`maxPrice`: a number, not below zero.
    - `lat`/`lng`: numbers in range, and one bad half discards both.
    - `zoom`: a number in 0–22.
    - A value outside the vocabulary, or any bad value of a repeated key, makes the key read as absent, from the query or the seed. An absent `roomType` means the default, shared. A new key with a fixed vocabulary or range goes into the table.
  - **Amenities:** slugs the catalogue lacks are filtered out of the list, and a list with none left reads as absent. The catalogue is `OffersApi.categories()`, which `SearchMap` passes in as `SearchVocabulary`. While it loads, or if it fails or is empty, amenities pass unchecked.
  - The request, the Filters badge, the controls (neutral placeholders), the modal's seed and SEO `hasFilters` all agree. `/search/lahore?roomType=bogus` reads as the plain page: indexable, canonical `/hostels/lahore`. An explicit `?roomType=shared` is the default, so `hasFilters` doesn't count it either. On a landing page, a bad query value falls back to the seed's.
  - **The URL rule: strip only what can come back to life.** The header bar reads the raw URL, not the reader. It reads `sort` (`SearchBar.activeSort`), the budget (its Budget field) and `lat`/`lng`/`zoom` (its place key), and writes them back on a search. So a discarded value of one of those keys is stripped (`searchUrlCorrections`, `STRIPPED`), and the bar can't see a landing page's seed to know better. `roomType`, `propertyType`, amenities and `gender` stay in the URL, read as absent: no writer reads them raw, and the modal's Apply writes them from the reader.
  - **The strip:** in the browser, `SearchMap` applies the `searchUrlCorrections` patch (`null` per key) with a same-path `replaceUrl` (`urlCorrections` → `stripCorrections`). That leaves no history entry, and GA skips it as a same-page refinement. It re-runs on each URL change while a correction remains, so a strip another navigation superseded is retried.
  - **`startSearch`:** spreads `urlCorrections()` into its merge, so a new search never carries a discarded sort, budget or coordinate along.
  - Trello #171 (PR #145), #176 (PR #157), #184; the boundary translation for a private room landed separately as PR #155 (Trello #183).
- **Modal labels are translation keys.** Type of stay (`searchBar.anyAccommodation` plus `ACCOMMODATION_LABEL_KEYS`, the same names as the header bar), Room type (`search.sharedRoom`/`privateRoom`) and Sort (`SORT_OPTIONS[].key`) render through the Transloco pipe. Property type and the amenity chips are still English (Trello #172).
- **SEO**: an unfiltered search for a curated place, arriving with no viewport in its link, while the map frames the place → canonical `/hostels/<slug>`. Filtered, uncurated, "everywhere", a search link that arrives carrying a viewport, or a map that no longer frames the place → `noindex` with no canonical. No `noindex` branch passes a `path`, so none writes `og:url` either (`Seo.apply`; before Trello #131 it canonicalised to home). An unfiltered viewport link to a curated place that still frames it keeps the place's title and photo (`placeSocialImage`). See decisions.
- **A search link that arrives carrying a viewport (all four `ne_*`/`sw_*` keys valid) is a view: `noindex`, no canonical.** `SearchMap.arrivedWithViewport` holds `urlBounds() !== null`. It is read on the first pass and re-read on every `NavigationEnd` except the page's own same-path refinements (`isSamePageRefinement`, `core/navigation/same-page-refinement.ts`, the predicate GA uses). The server's request URL is the arrival, so the raw HTML carries it. On a search page the map writes all four keys into the URL once its camera moves after load (a fit to results, a resize, the visitor), so the live URL is never the test: that would de-index every pristine place search whose camera moved, and fitting its results is enough, in a crawler that runs JavaScript too. Back/Forward and a language switch are arrivals; a partial or garbage box reads as none. See decisions.
- **Once the map no longer frames the place, the heading and title read "This map area"** (`searchUi.mapArea`, `seo.mapAreaTitle`, `seo.mapAreaDescription`; no new keys), and the head is `noindex`. `locationName` names the place only while `placeFramed()` (`framesPlace`, `search-framing.ts`) holds. The place is out of frame once the view's longitude span is wider than `CAP_TILES` (32) tiles at the place's zoom (about 5.6° for a city at zoom 11); otherwise it is in frame when its centre is in view or within `NEAR_TILES` (2) tiles of the view's centre on each axis. Longitudes are unwrapped. Null bounds (until the map reports a view of its own, after `recenterTo`) and an unknown centre (an uncurated slug, `?place=` without coordinates) count as framed. It is judged on settle (`mapBounds`), never mid-drag. `mapBounds` is seeded from `urlBounds()` on the server too, so a far link server-renders "This map area". The Where inputs keep the search made (below).
- **`search_performed` carries a `trigger`** (`search-trigger.ts`, Trello #157). `SearchMap` compares each emission of the request inputs with the previous one *before* the debounce (`noteSearchInputs` → `triggerForChange`), keeps the strongest change pending, and the next page-1 request takes it. The URL's place keys plus the slug count as a place, because the camera can settle on a new place in the same tick and leave only a new viewport in the request. "Search everywhere" in place marks itself, since it reads like a pan. A navigation that builds a new search page says what it was in `state.searchTrigger` (`startSearch`, `SearchBar.search()`), read once at construction (`arrivalTrigger`); otherwise the first search is `arrival`. A viewport change on its own, the camera settling included, is `map`.

## Reuse, don't rebuild
- `toListing()` for any `/public/hostels`-shaped payload (`favourites-api.ts` already does).
- `searchRouteFor(place)` to navigate to a search; `resolveSearchSlug` / `findPlace` / `findUniversity` for curated places.
- `BUDGET_MIN/MAX/STEP` — the bar and the modal must share one scale.
- `ACCOMMODATION_LABELS` / `ACCOMMODATION_LABEL_KEYS` instead of a gender ternary; `isAccommodationType` (`search-params.ts`) to validate a `gender` value; `isOccupancyType`, `DEFAULT_OCCUPANCY_TYPE`, `isPrivateOccupancy` (both spellings), `OCCUPANCY_WIRE_VALUE` (the index's name for each type); `isPropertyType` (`util/property-type.ts`).
- `mergeSearchParams` for any filter reading — never a second `queryParamMap` subscription; `genderRoutesFor` for where a type lives, seen from a gender page.
- `search-scope.ts` — `VIEWPORT_KEYS_NULLED`, `PLACE_KEYS_NULLED`, `RETIRED_KEYS_NULLED`, `EVERYWHERE_KEY`, `seededFilters` — whenever a navigation changes place or leaves a landing page.
- `apps/web-e2e/src/support/stubs.ts` (`stubListings`, `stubPhoton`) for e2e: the app sends credentials, so a listings stub must echo the origin; a wildcard puts the page in its error state. `apps/web-e2e/src/support/map.ts` (`waitForMap`, `dragMap`, `dragMapOnce`, `waitForQuiet`, `urlHasViewport`) for any test that pans; `dragMapOnce` drags exactly once and waits for that drag's own viewport write, because a place search with no results writes no viewport until its camera moves. On a landing page the URL never changes after a drag, so `dragMapOnce` and `urlHasViewport` time out there: detect the pan from the request's bounds (`ListingsStub.bounds`), with results stubbed inside the place, or the camera never moves. After a drag, wait for the request matching the URL's `ne_lat` before resetting the stub, or the debounced search lands late (see `pickKarachiThenPan`). `search-trigger-and-map-area-heading.spec.ts` checks the `search_performed` trigger with `support/analytics.ts` (`captureAnalytics`, `gaEvents`). It also stubs the visitor's country, so bare `/search` frames Pakistan.
- `search-sort.ts` (`SORT_OPTIONS`, `isPriceSort`, `sortsFor`, `isSortOffered`) for any surface that offers, applies, reads or carries a sort. Never another `startsWith('price-')`.
- **Translating a label:** in a component's own template, use the Transloco pipe on a key. Use `t()` (gated on `LocaleStore.ready()`, see `search-filters.ts`) only for strings handed to another component, such as `hh-dropdown` `[options]`. Under `provideI18nTesting`, `ready()` is false, so `t()` renders `''`, while the pipe renders the key.
- `OffersApi.categories()` is cached app-wide; don't fetch `/api/offer_categories` yourself.
- `hh-listing-card` for any listing tile.

## Traps
- **A seeded key can be overridden by the query but never removed by it** — writing `null` falls back to the seed. Every action that changes the type or the geography on a landing page therefore changes page (above). A new action that writes a seeded key must do the same.
- **`SearchBar`'s keys need their structural `equal`** (`sameKeys`). A key computed afresh is a new object on every read; without the `equal`, every viewport write counts as a change and resets the visitor's edits again (the pre-PR #133 bug). `search-bar.spec.ts` "SearchBar edits against URL writes" catches it.
- **A `noindex` search branch must pass no `path`.** `Seo.apply` drops the canonical and `hreflang` for `noindex`, but still writes `og:url` from a path, and Facebook reads `og:url` as the page's canonical. With no path it writes none of the three; there is no `'/'` default any more (`SeoConfig.path`, `core/seo.ts`). Before Trello #131 (PR #94) every `noindex` search canonicalised to the home page.
- **A pan renames a place search once the map no longer frames the place, and only the heading, title and head follow it.** Panning `/search/lahore` (or `?place=Lahore&lat=…&lng=…`) far away, or zooming far out, reads "This map area" and `noindex`; panning back restores "Lahore", and the canonical too if the link arrived with no viewport. A place with no known centre (an uncurated slug, a `/search?place=Lahore` with no coordinates) keeps its name however far the map goes. The Where inputs (the mobile field, the header bar) keep "Lahore" on purpose: they show the search made, and `SearchBar.search()` would submit "This map area" as a place. One e2e drag (`dragMapOnce`, 300 × 100 px, about 0.2° at zoom 11) stays inside the frame, as `search-viewport-head.spec.ts` measures; `dragMapOnce` fails rather than drag twice, because a second drag can take a small place out of frame. On bare `/search`, a search that names no place, the heading and title read "This map area" once the visitor has chosen the area: a pan or zoom, or a link carrying a viewport (`areaChosen`, `searchUi.mapArea`, `seo.mapAreaTitle`; Trello #161). Before that they read the framed country, or "Pakistan". `areaChosen` never resets, which is why it is not the fallback for a named place with no known centre (see decisions).
- **What counts as the visitor moving the map:**
  - a `dragstart`;
  - a `zoomend` that isn't one of ours (`programmaticMove`);
  - a `keydown` on a key Leaflet's keyboard handler moves the camera for: the arrows, and `+`/`-` without Alt, Ctrl or Meta (`isMapKeyboardMove`, Trello #212).

  Each sets `userInteracted`, which stops the next results from refitting the camera (`fitTo`), and calls `leftHomeCountry`. A keyboard pan raises no `dragstart`, so before #212 the next results snapped the camera back. The keypress is caught rather than `movestart`, because a scripted fit that Leaflet runs before `setup()` registers listeners leaves `programmaticMove` set until the next `moveend`. `SharedMap.listen` passes the Leaflet event to the handler.
- **Chrome MCP's synthetic drags don't move the Leaflet map.** In a browser check, pan by calling the component: `ng.getComponent(...)` → `map.fire('dragstart'); map.panBy(...); map.fire('dragend')`. Playwright's `page.mouse` drags work (`apps/web-e2e/src/support/map.ts` `dragMap`).
- **`SearchCapacity.active` is never set** anywhere — capacity pricing in `listing-card.ts` and the map pins always falls back to `priceFrom` (`apps/web/src/app/services/search-capacity.ts`). `SearchBar` still injects it unused.
- **A spec that finds a button by its English text proves nothing about translation.** `provideI18nTesting` renders every key as itself, so `choose('Any type')` matched *only because* the label was an untranslated literal (Trello #113). Look buttons up by key. Lookup helpers must throw on no match: `search-filters.spec.ts` `choose()` once did nothing silently. `i18n-check` cannot see literals.
- **A landing page's `seed` must be known on the first pass.** `SearchMap` strips a sort the type doesn't offer, and the strip cannot be undone. Today the seed comes from `toSignal(route.paramMap)` and is there at once, so `/hostels/lahore/girls?sort=price-asc` keeps its sort. A seed that arrived late (fetched from the API, say) would make the first pass see "Any" and strip a legitimate price sort for good. The first pass is also the earliest the seed exists: inputs are set after construction, so **a field initialiser must not read seed-dependent state**. `mapBounds`, `areaChosen` and `arrivedWithViewport` were `signal(this.urlBounds())`, read the URL before the seed landed, and so restored a landing link's viewport (Trello #201). They are `linkedSignal`s on `seeded` now, reading the URL `untracked`, and `unbounded` is a `linkedSignal` on the seed for the same reason (`search-map.ts`).
- **`seededFilters` would bring back a discarded *seed* value** (`sort`, `roomType`, `propertyType`) in `startSearch` (`params.get(key) ?? seed[key]`, `search-scope.ts`). That can't happen today, because landing seeds carry only place, lat, lng, zoom and gender (`place-landing.ts`). Keep it that way, or route the seed through the reader.
- **`sort[starting_price]`** is still what price sort sends, while `listings-api.ts` documents `starting_price` as dropped from the search document. Verify before trusting price order.
- **The app and the index spell a private room differently.** The URL, the controls and `OCCUPANCY_TYPES` say `private`; the index and `GET /api/hostels/new` say `private_room` (backend `room_type.rb` enum). Translate only at the API boundary (`OCCUPANCY_WIRE_VALUE`). Until Trello #183 every Private room search sent `private` and matched nothing (checked live: `=private` gave 0, `=private_room` gave 1). The price band and card price still use the app's word (`private_occupancy_price_from`).
- **`PROPERTY_TYPES` must match the backend enum** (`hostel.rb`: apartment, room, building, house). The host form offers the API's list, but search checks the static one, so a type the backend adds is read as absent in search until it is added here.
- **Search only lists hostels that have room types.** Every request sends `f[room_types.occupancy_type]` (shared by default; there is no "Any"). A live probe on 2026-10-18 found 10 of 405 hostels with any room types, so 395 never appear in search. Whether those are real listings is unconfirmed.
- **The amenity check is only as good as the catalogue.** Amenities go to the API as slugs (`f[offers.slug][]`), and unknown ones are read as absent only once `/api/offer_categories` has loaded. `offers-api.ts` calls it authed, but it answered a request with no credentials with 200 (checked 2026-10-18). If it ever needs a session, guests' amenity links pass unchecked again. A filter chip (`popularAmenities`) whose slug isn't in the catalogue would never read as selected. All six were in it on 2026-10-18; keep new chips to catalogue slugs. `AMENITIES` (`ac`, `security`, `cctv`… which are not catalogue slugs) is only the modal's fallback when the catalogue fails, and then nothing is checked.
- **Zero-area boxes** (`hasArea`) must never be queried or written to the URL — Leaflet returns one before layout.
- The header bar reads the `:location` slug only, so it shows no place on `/hostels/:place` pages (`search-bar.ts` `routedLocationSlug`). It reads `?gender=` itself (validated with `isAccommodationType`) because it sits outside `SearchMap`.
- `/hostels/:place/:gender` serves both gender segments and campus slugs; gender wins (`place-landing.ts` `segment`). Backpacker has no segment.
