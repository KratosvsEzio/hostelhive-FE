# Host console

The signed-in host's workspace at `/host/:hostelId/…`: overview dashboards, hostel profile, rooms, tenants, bookings, renter bills ("invoices"), utilities, expenses, mess and team. It covers the shell, navigation, per-page permission and billing-cycle gates, and the host data services. Paying for HostelHive itself is a separate area — see [host-billing-and-subscription](./host-billing-and-subscription.md).

## Where it lives
- `apps/web/src/app/features/host/host.routes.ts` — the route table and its guards (`hostRootRedirect`, `createHostelGate`, `knownHostelGate`, `bookingsGate`, `monthlyOnlyGate`).
- `apps/web/src/app/layout/host-shell/host-shell.ts` — the shell: sidebar, property switcher flyout, URL→store sync.
- `apps/web/src/app/layout/host-shell/host-nav.ts` — `hostNav`, `hostTabBar`, `tabBarSuffixes`, `splitNav`: the single source for sidebar, bottom tab bar and the mobile More page (`apps/web/src/app/features/host/more/more.ts`).
- `apps/web/src/app/layout/host-shell/host-route.ts` — `hostPagePath` (URL → page below the hostel).
- `apps/web/src/app/services/host-property-store.ts` — `HostPropertyStore`: the signed-in user's hostels, the selected id (persisted per user in localStorage `hh:host-property` as `{ owner, id }`), `activeHostel`, `isMonthlyBilled` / `isNightlyBilled`.
- `apps/web/src/app/services/host-shell-api.ts` — `GET /api/host/hostels` (`listings()`) and the manager-login endpoints.
- `apps/web/src/app/services/host-ops-api.ts` — rooms, renters, renter bills (including booking bills: `toInvoice`, `invoice`, `bookingInvoices`), utility bills.
- `apps/web/src/app/services/staff-api.ts` — staff employment records (`/api/host/hostels/:id/staffs`).
- `apps/web/src/app/services/overview-api.ts` — overview cards and the revenue / occupancy / movement charts.
- `apps/web/src/app/services/hostels-api.ts` — hostel CRUD, form options, mess (meal types, weekly menus, confirmations) and expenses.
- `apps/web/src/app/features/host/bookings/host-bookings-api.ts` — host bookings, the stay moves, `get` (one booking from the database) and `bookingsInRoom` (owned by [listing-and-booking](./listing-and-booking.md)).
- `apps/web/src/app/features/host/bookings/` — the bookings page (`bookings.ts`), its details panel (`booking-details-panel.ts`) and `booking-move-failure.ts` (refusal → translation key).
- `apps/web/src/app/features/host/rooms/room-calendar/room-stays.ts` — how a booking fills a room's nights.
- `apps/web/src/app/util/host-links.ts` — `bookingPath`, `invoicePath`.
- `apps/web/src/app/features/host/hostel-form/hostel-form.ts` — the one hostel form, used by `new-hostel/`, `hostel-profile/` and the moderator review screen.
- `apps/web/src/app/util/tenant-status.ts` — tenant status label and tone; `apps/web/src/app/util/table-configs/` — column definitions for every console table.

## How it works
- **Entering.** `/host` runs `hostRootRedirect`, which waits for `HostPropertyStore.load()` and lands on the selected (or first) hostel, or on `/host/hostels/new` when the user holds `core:Hostel:create` (`apps/web/src/app/features/host/host.routes.ts`).
- **The store belongs to the signed-in user.** `HostPropertyStore` keys on `SessionStore.user()?.id`: its `properties`, `hostels` and `loaded` read as nothing loaded the moment the user changes (same tick, so the guards refetch instead of trusting the previous user's list); an effect clears on sign-out, cancels the previous user's request on an account switch and reloads only if one was in flight; a token-only restore and a same-user refresh change nothing. A bare id saved by older builds under `hh_property` is adopted once by whoever is signed in (`apps/web/src/app/services/host-property-store.ts`). See the decision below.
- **Multi-property switching.** The URL's `:hostelId` is authoritative. `knownHostelGate` refuses an id the host does not own; `HostLayout._syncStore` copies the route id into the store; `onPropertySelect` keeps the current page and swaps the hostel segment through `hostPagePath` (`apps/web/src/app/layout/host-shell/host-shell.ts`). See the decision below.
- **Permissions per page.** Nav entries carry a `group:Subject:action` flag and are filtered by `SessionStore.hasPermission`; routes repeat the flag with `permissionGuard` (`apps/web/src/app/core/auth/guards.ts`). Map: profile `host:Hostel:show`, rooms `host:Room:index`, tenants `host:Renter:index`, team `host:Staff:index`, utilities `host:UtilityBill:index`, mess `host:WeeklyMenu:index`, expenses `host:Expense:index`, invoices `host:RenterBill:index`, subscription `core:Hostel:subscription`. Overview is ungated by design.
- **Billing-cycle split.** A hostel's `billing_frequency` (`month` / `night`) decides which half of the console exists: Bookings for nightly hostels, Tenants / Utilities / Mess for monthly ones, enforced in `hostNav`, `hostTabBar` and the two gates.
- **Deep links.** `bookings/:bookingId` (a sibling of `bookings`, because the gate and page read `hostelId` from `route.parent`) opens that booking's panel. `invoices/view/:billId` opens that bill's preview and fetches it when it is off-page. Build both with `util/host-links.ts`. List and drawer routes carry `data: { drawerHost: true }`, so `AppRouteReuseStrategy` keeps the page instead of rebuilding it; it reads route data and imports no page (`apps/web/src/app/route-reuse-strategy.ts`, `host.routes.ts`).
- **Stay flow (bookings).** The panel shows the booking's invoice: loading, none, the invoice with View invoice, or failed. One `bookingInvoices` lookup per page feeds it. Generate invoice is offered only for checked-in and checked-out bookings, and the panel keeps the bill the server returns. A checked-out or cancelled booking shows its rooms read-only under "Stayed in", labelled "Checked out" or "Released" (`stayRowLabel`); a room released early on a checked-out stay still says "Checked out", because an occupancy only has `active`. A Release refused as already released counts as a release: the room is marked released and the page re-reads the booking (Trello #167, #168). Opening a booking re-reads it from the database ([index-backed reads](../decisions/api-and-data/index-backed-reads-lag-trust-db-and-local-writes.md)). Paying either the booking or its invoice offers the other ([cross-pay](../decisions/host-console/cross-pay-checkbox-ticked-by-default.md)). Refusals show translated keys from `booking-move-failure.ts`, never server text, and every call whose error the page reports itself (every stay move, confirm included; release; `create` for the booking drawer) opts out of the global toast. Confirm has no dialog of its own, so its refusal goes to the panel footer when the panel shows that booking **as the reply lands**, otherwise one translated error toast (`refusalSurface` / `reportRefusal` in `bookings.ts`; a 401 never toasts, since sign-out takes over; Trello #175).
- **Booking confirmation PDF.** The panel shows a "Confirmation" section with a Download confirmation link between "Stayed in" and the invoice, drawn from `confirmationLink(booking)` (`apps/web/src/app/features/host/bookings/host-bookings-api.ts`): the stored `confirmation_pdf.url`, only when the disposition lane is `confirmed`, `checked-in` or `checked-out` (a pending, cancelled or no-show booking may still carry a PDF and shows nothing). The PDF is stored by an asynchronous job after the booking is confirmed, so the section appears on the next open of the booking, not in the reply to Confirm; a failed store or a booking confirmed before the field existed never shows it.
- **Invoices.** Bills are `rental`, `utility` or `booking`; a booking bill shows a Booking badge, is "Billed to" the guest with a link to the booking, and is never editable. The page's cards, filters and Add invoice follow the hostel's billing mode ([decision](../decisions/host-console/invoices-page-follows-billing-mode.md)).
- **Utilities.** Deleting a bill also deletes its tenants' renter bills on the server (checked live 2026-10-18). The page hides the row at once and puts it back if the delete fails. Once the delete succeeds, `reloadTotals` re-reads the list quietly to refresh only the summary cards (`aggs`), the status counts and the footer's bill count (`listTotal`, a `linkedSignal` that the next list read resets). It doesn't bump `refresh`, which would flash the table back to a skeleton (`apps/web/src/app/features/host/utilities/utilities.ts`). The list reads the search index, so this re-read is correct only because the backend refreshes the utility-bill and renter-bill indexes before it answers (`prepend RefreshOnReindex`, be `1c53f15`, BE PR #65, Trello #189). Without that, it returned the totals from before the delete. Verified live on 2026-10-18 (Trello #188): Total Balance and Due dropped by the deleted bill with no reload. The rooms and staff lists follow the same exception to [index-backed reads lag](../decisions/api-and-data/index-backed-reads-lag-trust-db-and-local-writes.md) (BE PR #75, Trello #198). Don't add a timed re-fetch here; that was rejected, and `RefetchDelay` was removed in #198.
- **Rooms.** Room cards show "N free" or "Full" (capacity − the server's `current_occupancy`, which includes booking guests). Room detail lists "Guests on bookings" (`f[occupied_room_ids]`) and counts occupied as active renters plus those guests; its status pill is hidden while that count is unknown (loading or failed). The room calendar charges each room only the guests placed in it ([decision](../decisions/host-console/room-occupancy-counts-per-room-occupancies.md)), and its "today" is the hostel's date, read once when it opens; room detail holds the calendar behind a skeleton until the hostel's zone is known ([decision](../decisions/host-console/console-today-is-the-hostels-date.md)). The rooms index refreshes on write (BE PR #75), including a room's `current_occupancy` after a stay move, so the page reads it fresh with no wait, whether it re-reads after a bulk add on a filtered view or is opened after a move on Bookings.
- **Saves that fail inline.** Outside bookings, the saves that show their own failure also opt out of the global toast and show a translated key, never server text: rooms' create, edit and bulk add (`hostRooms.couldNot…`), the hostel form's room move (`hostelForm.couldNotMoveRoom`), new hostel's create (one line by the Create button, `hostNewHostel.couldNotCreateHostel`), the hostel profile's save with its photo-label and primary writes, and mess's weekly-menu and meal-time saves. The profile's star, sent the moment it is pressed, keeps its toast: its only other sign of failure is the badge moving back (Trello #186). Opening a booking link that fails says the server can't be reached on status 0, and that the booking wasn't found otherwise.
- **Data loading.** Pages read the hostel from the store (`HostPropertyStore.selected()` / `activeHostel()`), not a second fetch; lists page server-side with `pageParams` and `f[status.slug]` filters (e.g. `apps/web/src/app/features/host/team/team.ts`).
- **Time zones.** Each hostel has an IANA `timezone`, picked with `TimezoneSelect` in the hostel form and locked for hosts once the hostel has bookings (`timezoneLocked` in `apps/web/src/app/features/host/hostel-profile/hostel-profile.ts`, which asks for one booking row). The hostel list doesn't carry the zone (the backend index has no `timezone`), so `HostPropertyStore.timeZoneOf(id)` reads it once per hostel from `GET /api/host/hostels/:id` and caches the answer for the session, a `null` (no zone, or the read failed) included. Screens read it through `services/hostel-today.ts` (`hostelZone`, `selectedHostelToday`); every "today" in the console is the hostel's date, including the room and bookings calendars, the booking form's defaults, the overview strip, the tenant leave count and the tenant joining date and time (`wallClockIn`, Trello #190). Booking dates go out as plain days and the server applies the hostel's zone. Naive wall-clock fields are string-sliced, never parsed (`toDate` in `apps/web/src/app/services/staff-api.ts`). Range filters use `dayRangeStart` / `dayRangeEnd`. Details: [dates-money-and-time-zones](./dates-money-and-time-zones.md).

## Reuse, don't rebuild
- `HostPropertyStore.activeHostel()` for currency, room types and billing cycle, and `isMonthlyBilled(id)` / `isNightlyBilled(id)` in guards (pass the route id).
- `hostNav()` for any new destination; it feeds the sidebar, the More page and, through `tabBarSuffixes`, the tab bar.
- `hostPagePath()` for any URL arithmetic below the hostel (it strips the locale prefix); `bookingPath()` / `invoicePath()` for links to one booking or bill (no locale prefix; the link directives add it).
- `bookingMoveFailureKey` / `releaseFailureKey` / `crossPayInvoiceFailureKey` (`apps/web/src/app/features/host/bookings/booking-move-failure.ts`) for any new stay-move error. Pass `{ owner: session.hasRole('host') }`, read when the refusal arrives. A 403 reads as follows:
  - a plan without CRM (`isCrmRequired` in `apps/web/src/app/core/host-access/host-access.ts`, shared with `classifyHostAccess`) → `hostBookings.planHasNoCrm`;
  - a 403 carrying **no** server code (`isPermissionRefusal`, same file: the interceptor's `'unknown_error'` fallback; CanCan's "not authorized" or the not-host-or-manager check) → a permission message: `notAllowed` ("ask the hostel owner") for staff, `notAllowedOwner` ("contact HostelHive support") for an owner;
  - any other coded 403 (Rack::Attack `forbidden`) keeps the generic message.

  A 400 "You need to subscribe…" (`isPlanInactive`) reads as `hostAccess.offline` for an owner and `offlineStaff` for staff (`planInactiveKey`, Trello #194).

  Roles and their permissions are global and edited only by HostelHive admins, so the message never tells anyone to "ask for the role to be changed" (Trello #187). The booking drawer's create follows the same rule through `bookingSaveFailureKey(err, { owner })` (Trello #193).
- **Any other host write the server can refuse** (a save, a delete, Mark paid, a status change): send it quiet (`{ suppressErrorToast: true }`) and report the failure through `injectActionFailureToast()` (`apps/web/src/app/core/host-access/action-failure.ts`). A plan or permission refusal becomes one pinned toast with `actionRefusalKey(err, { owner })` (`host-access.ts`); anything else is handed to the app's own `API_ERROR_NOTIFIER`, so it reads exactly as the global toast would. A screen that reports the failure inline (the rooms dialog, add-bill) shows `actionRefusalKey(...) ?? <its generic key>` there instead. Opening one record the user may not see (a booking or bill by URL) says `pageNotAllowedKey({ owner })`, the panel's sentence (Trello #194).
- **A read whose failure the page draws itself goes out quiet**, so a refused load shows one message, not the page's plus the global toast's "Not allowed: <server English>". The list pages, add-bill, the overview's KPI/chart/strip reads, the bookings list and calendar, and the opened booking do this. A read whose failure the page swallows (falling back to an empty list) stays loud: the toast is its only report (Trello #194). Host pages without the permission panel (team, hostel profile, room detail, tenant profile, expenses, the overview detail pages, billing) still rely on the global toast on a 403.
- **Retry works only if the query's value changes.**
  - A page's reads are `toObservable(query)` over a `computed`, and a computed notifies only when its value changes (`Object.is`). So a query that reads a `refresh` counter but returns the same hostel id never emits again, and Retry re-requests nothing.
  - Build the query as a new object that includes the counter. The overview's `hostelReload` is `{ hostelId, reload: refresh() }`, and every read on the page keys on it, the panels beside the cards included, since they fail with the cards when the server is unreachable and have no Retry of their own (Trello #203).
  - The list pages (rooms, tenants, utilities, invoices) already build an object of page and filters.
- **A page whose load is refused for permission** sets `permissionError: isPermissionRefusal(err)` on its view state, keeps `error` true, and renders `<hh-permission-refused />` (`apps/web/src/app/layout/components/permission-refused/permission-refused.ts`) before its generic `<hh-error-state>`. It says "Access blocked" with `hostAccess.pageNotAllowed` / `pageNotAllowedOwner` ("…see this…"), picks the role itself, and has no Retry, because retrying can't grant a permission. Overview, rooms, tenants, utilities, add-bill and invoices do this (Trello #193), and so do the bookings list, the bookings calendar (its month read replaces the whole calendar; a refused day read shows the panel in the ledger) and add-bill's edit read (Trello #194). A plan refusal shows only the generic error, because the plan lock replaces the page on it (Trello #199): `crm_required` and the 400 "You need to subscribe…" belong to the lock, and a codeless 403 to this panel.
- **A refusal that says the booking is not where the screen shows it counts as the server's state, not a failed move.** `movedOnKind` (same file) sorts them into `'done'` (already checked in, already paid) and `'movedOn'` (wrong stage, no longer changeable). `send` (`apps/web/src/app/features/host/bookings/bookings.ts`) hands these to `onMovedOn`, which:
  - keeps `busy` and re-reads the booking quietly;
  - swaps the fresh copy into the row and the calendar;
  - closes the dialog or room allocation once `refusalBorneOut` agrees.

  How it lands:
  - **`'done'`:** an info toast, and the panel on the fresh copy (check-in always opens it).
  - **`'movedOn'`:** the red panel footer, or an error toast when no panel is open.
  - **Re-read shows no change:** the move stays open with `moveNotAccepted`.
  - **Re-read fails:** a 404 closes everything (`bookingNotFound`); any failure refreshes the list.
  - **The host opened something else meanwhile:** only the row changes.

  Stages compare by lane (`stageChanged`), because older records still carry legacy slugs. Every other refusal is the host's input and stays where it was (Trello #173; #168 is the same rule for Release). With no surface open on the booking (a confirm from the row menu or the calendar), nothing is shown until the read settles, then exactly one toast, and a 404 on the read never closes what the host opened meanwhile (Trello #175).
- **Cross-pay on a booking already paid elsewhere** still pays the ticked invoice, but only when the database agrees on both halves. That means the booking's copy (`GET bookings/:id`) shows it settled and still in `PAYABLE_LANES`, and the invoice's own copy (`HostOpsApi.invoice`, `GET renter_bills/:id`, not the index-backed bills list) shows it still owing. An invoice found already paid is recorded as paid; one that can't be read is never paid blind (`markPaid` in `bookings.ts`, `hostBookings.alreadyPaidInvoicePaid`).
- `PAYABLE_LANES` / `INVOICEABLE_LANES` (`apps/web/src/app/features/host/bookings/booking-month.ts`) for "can this booking be paid / invoiced".
- `tenantStatusLabel` / `tenantStatusTone`, and `invoiceStatusLabel` / `invoiceStatusTone` in `apps/web/src/app/util/table-configs/invoice-table-cols.ts`.
- `dayRangeStart` / `dayRangeEnd` from `apps/web/src/app/util/date-range-filter.ts` for every date-range filter.
- `HostelForm` for anything that edits a hostel.

## Traps
- **Stay moves aren't hidden by permission yet.** The `host:Booking:*` flags have never been checked live. The backend counts a granted "Manage Bookings" parent and ignores the permission group, and newly added actions only get permission rows after a manual `rake permission:reload`. So hiding moves by flag could hide buttons that work. Moves explain a permission refusal instead (#187); hiding waits on a live payload check (Trello #195). Release must never be gated: the backend has no CanCan check on it.
- **"Invoices" are renter bills** (rent, utility, or a booking's stay; `/api/host/hostels/:id/renter_bills`, `apps/web/src/app/features/host/invoices/invoices.ts`), not HostelHive billing invoices.
- **The booking list, calendars and `…/occupancies` read the search index**, which can lag by minutes; `GET bookings/:id` reads the database. Never "refresh" after a write by re-fetching the list ([decision](../decisions/api-and-data/index-backed-reads-lag-trust-db-and-local-writes.md)).
- **`linkedSignal` resets whenever anything its `source` function reads changes, even if the value is the same.** Per-booking panel state (`releaseError`, `releasedIds`) takes its source from the `computed` `bookingId`, so the page's re-read of the same booking keeps it. A `source: () => this.booking()?.id` looks equivalent and silently wipes it (`apps/web/src/app/features/host/bookings/booking-details-panel.ts`; caught by QA in Trello #168).
- **Bookings has no `permissionGuard`**, while its nav entry is gated on `host:Room:index` (`apps/web/src/app/features/host/host.routes.ts` vs `apps/web/src/app/layout/host-shell/host-nav.ts`).
- **One endpoint uses a singular path.** `updateUtilityBill` calls `/api/host/hostel/:id/utility_bills/:billId`; every other call is plural, and `markInvoicePaid`'s comment says plural is what the current backend serves (`apps/web/src/app/services/host-ops-api.ts`). Nobody has checked the singular path on the wire.
- **Dead fixture code.** `HostOpsApi.utilityBatch()`, `occupancyDays()` and `utilityTypes()` have no callers and still read `apps/web/src/app/services/host-ops.fixtures.ts`. `HostelsApi.currentSubscription()` is also unused.
- **A wrong doc comment.** `HostelsApi.getById` says `GET /api/hostels/:id` but calls `/public/hostel_detail/:id` (`apps/web/src/app/services/hostels-api.ts`).
- **Two staff resources.** `StaffApi` covers employment records; `HostShellApi.addManager` / `removeManager` cover login accounts. Neither replaces the other (doc comment in `apps/web/src/app/services/staff-api.ts`).
- **Every staff record needs an email.** The backend validates it on every save, manager or not (`staff.rb`), and answered a create without one with a 422 "Email can't be blank" until the Team form asked for it (seen live 2026-10-31). The form asks for it on create and on an edit of an older record saved without one; once stored it is fixed and not re-sent. Manager access uses it as the login. The password is required only when the record has no stored address. With one, it is optional: the server reuses an existing account and needs a password only when there is none (`staff-form.model.ts` in `apps/web/src/app/features/host/team/staff-form-drawer/`).
- **`loaded` flips true on failure too**, so an empty list can mean "fetch failed". Guards let such hosts through rather than bouncing them (`apps/web/src/app/services/host-property-store.ts`).
- **`properties`, `hostels` and `loaded` are read-only computeds**, gated on the owner. Write through `load()`, `setProperty()` and `clear()` only; anything new that caches per-user host data should read through the store or follow the same owner gating.
- **The shell loads only in its constructor.** An account switch while the host shell stays mounted would leave it loading until the next guard runs; no path does that today (`/confirm_invitation` lands on `/`), but a future in-console account switch must make the shell call `load()` when `loaded()` goes false (`apps/web/src/app/layout/host-shell/host-shell.ts`).
