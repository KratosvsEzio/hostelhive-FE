1. Executive Summary

HostelHive is a two-sided marketplace platform that connects hostel-seekers with verified accommodation providers (hosts). The platform provides a full end-to-end ecosystem covering property discovery, authenticated lead generation, host onboarding, payment verification, content moderation, tenant management, automated billing, and financial analytics.

This Product Requirements Document (PRD) defines the complete functional, technical, UX/UI, and non-functional requirements for the HostelHive web platform, including all five core feature modules and their supporting subsystems.

 |

3. Assumptions, Constraints & Dependencies

3.1 Assumptions
Users have access to a modern web browser (Chrome 90+, Firefox 88+, Safari 14+, Edge 90+).
Hosts have a valid phone number and business email address for account verification.
Payment processing is handled via a third-party provider (e.g., Stripe, JazzCash, or EasyPaisa for Pakistan market).
Google Maps JavaScript SDK and Google Places API access are available under a valid API key.
WhatsApp Business API access is available for automated tenant billing notifications.
All monetary values are stored and displayed in PKR (Pakistani Rupee) by default, with multi-currency support as a future roadmap item.

3.2 Technical Constraints
No more than one in-progress property onboarding per host account at any time (system-enforced).
Image uploads must not exceed 10 MB per file; supported formats: JPG, PNG, WEBP.
A maximum of 20 images per property listing is enforced at the API layer.
Latitude/longitude precision is stored at Decimal(20, 5) for mapping accuracy.
All background billing cron jobs execute daily at midnight server time (UTC+5 for Pakistan).

4.4 Lead Wall Mechanism — Detailed Flow
The Lead Wall is the gated authentication system that protects host contact information from bots and data scrapers while building HostelHive's verified user database.

Unauthenticated visitor clicks the "Show Phone Number" button on a listing detail page.
The UI renders an opaque overlay modal blocking the contact details from view.
The modal presents two tabs: Login (returning users) and Register (new users).
New user completes: Full Name, Email Address, Password (min 8 chars, 1 uppercase, 1 number), Phone Number.
System creates a database user record with status = PENDING.
System dispatches a cryptographically signed, 24-hour-expiry email verification link.
On link click, status transitions to ACTIVE; a session token is minted.
Browser is deep-linked back to the originating listing with phone number now visible.

Edge Cases:
If email already exists: display "Account exists — please login" and redirect to Login tab.
If verification link has expired: display re-send option; re-issue new link on request.
Social login (Google OAuth) bypasses email verification step; account immediately set to ACTIVE.

6.3 Delta Media Inspection Pipeline
For live (published) listings, hosts can upload new images at any time. These images enter a buffered pipeline to protect the live listing from unvetted content:

Host uploads new image(s) through the Host Dashboard image management panel.
New images are written to cloud storage with moderation_status = 'pending'. They are NOT visible on the public listing.
A notification badge appears in the Moderator Panel's secondary media review queue.
Moderator reviews the pending image. Actions available: Approve (sets moderation_status = 'approved', image becomes public) or Reject (sets moderation_status = 'rejected', host notified).
Approved images immediately appear on the live listing without any downtime.

7.4 Automated Billing Cron System Architecture
A background scheduler executes daily at calendar midnight (server time). Execution logic:

System queries all active tenant records where rent_issue_date = today's calendar day number.
For each matched tenant: calculate total due = base_rent + utility_share (if applicable) — any credits.
Generate HTML invoice document using property branding template.
Compile HTML-to-PDF using server-side renderer (Puppeteer or wkhtmltopdf).
Dispatch PDF invoice to tenant via: (a) WhatsApp Business API message with PDF attachment, (b) Transactional email with PDF attachment.
Write invoice record to ledger table with status = 'issued'.
After all tenant invoices are processed: compile daily summary report for the property owner.
Dispatch summary report to property owner via WhatsApp and email.

7.5 Utility Bill Splitting Logic Engine
Property managers enter collective variable utility bills per room per billing period. The pro-rata formula applied by default:

Individual Share = (Total Bill Amount ÷ Total Combined Room Occupancy Days) × Tenant Individual Occupancy Days

10.4 Automated Webhook-Driven Activation Flow
Host selects a subscription plan and clicks "Subscribe" / "Renew" on the Host Dashboard.
System creates a contract record with contract_status = 'draft', then immediately a linked payment record with payment_status = 'pending', and updates contract_status = 'pending-payment'.
Host is redirected to the payment gateway checkout (Stripe / JazzCash / EasyPaisa) with the payment record's amount and reference ID.
Host completes payment on the gateway's hosted checkout page.
Gateway sends an asynchronous webhook to HostelHive's server endpoint containing the transaction outcome and a signed payload.
Server verifies the webhook signature using HMAC validation against the shared gateway secret.
On verified SUCCESS: payment_status → 'paid', gateway_reference and paid_at fields populated, contract_status → 'active', start_date set to today, end_date calculated based on the plan's billing cycle (e.g., +30 days or +365 days).
On verified FAILURE: payment_status → 'failed'; contract remains 'pending-payment'; host sees a "Payment failed — retry" prompt on their dashboard.
On successful activation, the system sends a confirmation email + WhatsApp message to the host with the contract details and an invoice/receipt PDF.
A background job runs daily to check for contracts where end_date is within 7 days; affected hosts receive a renewal reminder notification.
A background job runs daily to check for contracts where end_date has passed without renewal; contract_status → 'expired', and all of that host's property listings transition to status = 'paused' (their data is retained but they are removed from public search).

 | Description

Single hostel scope
 | Each Manager or Warden record maps to exactly one property_id via property_staff_assignments. A sub-user cannot be assigned to more than one hostel at a time.

Host-only creation right

No cross-property visibility

Manager vs Warden distinction
 | Both roles share the same permission set in v3.0. The distinct role labels exist for the host's internal organizational clarity (e.g., "Warden" for on-site residential staff, "Manager" for operational/admin staff) and for future-roadmap differentiation of permissions.

12.2 Security Requirements
All data in transit must be encrypted using TLS 1.2 or higher (HTTPS only).
All passwords must be hashed using bcrypt with a minimum cost factor of 12.
Session tokens must use JWT with RS256 signing; 24-hour expiry for seekers, 8-hour for moderators.
Google Maps API keys must be restricted to specific referrer domains; never exposed in client-side code without domain restrictions.
Payment webhook payloads must be verified using HMAC signature before processing.
File uploads must be scanned for malware using ClamAV or equivalent before storage.
OWASP Top 10 vulnerabilities must be addressed in the production deployment.
Rate limiting: max 60 search requests per minute per IP; max 10 login attempts per hour per IP.
Admin and moderator panel access must require IP allowlisting in addition to credentials.

12.3 Scalability & Reliability
The system must support horizontal scaling of API servers behind a load balancer.
Database replication: read replicas for search-heavy endpoints; write master for billing and state transitions.
Cloud storage (S3 or equivalent) must be used for all media assets; no local disk storage for user uploads.
System availability target: 99.5% uptime SLA (excluding scheduled maintenance windows).
Automated database backups: daily snapshots retained for 30 days; weekly retained for 90 days.

12.4 Accessibility Requirements
Public-facing pages must comply with WCAG 2.1 Level AA standards.
All images must include meaningful alt text (moderators responsible for alt text during review).
Map components must provide a text-based address fallback for screen reader users.
Color alone must not be used as the sole means of conveying information (e.g., status indicators must include text labels).
All interactive controls must be keyboard navigable.

17. Glossary of Terms

Term
 | Definition
 | 
Seeker
 | A platform user searching for hostel accommodation.
 | 
Host
 | A property owner who lists one or more hostels on HostelHive.
 | 
Moderator
 | An internal HostelHive staff member responsible for reviewing and approving listings.
 | 
Lead Wall
 | The authentication gate that blocks phone number visibility for unauthenticated users.
 | 
disposition_id
 | A secondary state field that tracks the editorial/operational stage of a property listing.
 | 
status_id
 | The primary lifecycle state of a property (onboarding, active, paused, inactive).
 | 
moderation_status
 | The approval state of a single image asset (pending, approved, rejected).
 | 
is_primary
 | A boolean flag on the property_images record designating the listing's main thumbnail image.
 | 
Cron Job
 | An automated background task that runs on a scheduled time-based trigger (daily at midnight).
 | 
Pro-Rata
 | Proportional allocation of a bill based on each tenant's number of occupancy days in the billing period.
 | 
Reverse Geocoding
 | The process of converting latitude/longitude coordinates back into a human-readable address using the Google Geocoding API.
 | 
Webhook
 | A real-time HTTP callback sent by the payment gateway to the HostelHive server to confirm a transaction outcome.
 | 
Delta Media Pipeline
 | The buffered image upload system for live listings that prevents unvetted photos from appearing publicly.
 | 
Contract
 | A subscription agreement between HostelHive and a host, created upon plan purchase and activated automatically once payment is confirmed.
 | 
contract_status
 | The lifecycle state of a subscription contract: draft / pending-payment / active / expired / cancelled.
 | 
payment_status
 | The state of a payment transaction linked to a contract: pending / paid / failed / refunded.
 | 
HMAC Verification
 | A cryptographic signature check used to confirm that a payment webhook payload genuinely originated from the payment gateway and was not tampered with.
 | 
Role
 | A named collection of granular permission flags that can be assigned to a user account (e.g., Super Admin, Moderator, Manager, Warden).
 | 
Permission Flag
 | A single granular access-control unit (e.g., contracts.view, listings.approve) that can be combined into roles.
 | 
Manager / Warden
 | A sub-user account created by a host, scoped to exactly one assigned hostel, with operational parity to the host for that property only.
 | 
property_staff_assignments
 | The database table that enforces the single-hostel-scope rule linking each Manager/Warden user to exactly one property_id.
 | 
DXA
 | Document Exa-Unit — the measurement unit used internally in DOCX for spacing and dimensions (1440 DXA = 1 inch).
 |
